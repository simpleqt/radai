# 用户级隔离实施方案

> **文档版本**：v2.4（2026-07-14 当前实现校正版）
> **范围说明**：本文聚焦用户通过智能体 API、对话历史、运行时目录、文件下载和会话附件产生的数据隔离。知识库上传 `/api/v1/uploads/*` 使用独立 KB 权限体系，见本文第六节。
> **关联文档**：MinIO 原生工具隔离见 [原生环境_非沙箱_用户隔离实施方案](./原生环境_非沙箱_用户隔离实施方案.md)；对话附件细节见 [chat_file_upload_design](./chat_file_upload_design.md)。

## 一、当前现状

| 项目 | 状态 | 当前实现 |
|---|---|---|
| 内部 thread key | ✅ | `build_internal_thread_key(user_id, thread_id)` → `u_{uid}__t_{tid}` |
| guest 设备态 thread key | ✅ | `/api/v2/guest/query` 无 token 时使用 `g_{hmac_device}__t_{tid}` |
| 登录用户鉴权 | ✅ | `verify_api_key()` 支持 `X-API-Key`、Bearer token、历史 Bearer API Key |
| 可选访客鉴权 | ✅ | `optional_verify_api_key()`；有凭据则校验，无凭据返回 guest |
| 会话列表/消息隔离 | ✅ | `backend/api/routers/conversations.py` 按 `Conversation.user_id` 过滤 |
| guest 会话列表 | ✅ | `guest_conversations.py` 只返回当前用户在 guest checkpoint 中有消息的会话 |
| 运行时本地目录 | ✅ | `backend/core/config/paths.py` 按 `users/{uid}/threads/{tid}/...` 组织 |
| 会话删除清理 | ✅ | 软删除后清理后台任务、checkpointer、MinIO artifacts、本地线程目录；失败则恢复可见并 503 |
| 删除后同名重建 | ⚠️ | `ConversationStore` 遇到 `is_deleted=True` 会抛 `ConversationDeletedError`，当前不是自动恢复 |

| 对话附件隔离 | ✅ | `UserFile.owner_user_id` + `SessionFile.user_id/session_id` + MinIO `users/{uid}/...` |
| 知识库目录管理 | ✅ | `/api/v1/knowledge_bases/{kb_id}/directories...` 仅管理员 |
| KB 上传隔离 | ✅ | `/api/v1/uploads/*` 走 `require_kb_access()` 与 `PendingFile.created_by` |

## 二、身份、token 与会话边界

### 2.1 认证依赖

`backend/api/dependencies/auth.py` 是路由级鉴权入口：

- `verify_api_key()`：用于需要登录/Key 的路由。
- `optional_verify_api_key()`：用于 guest query，有凭据时仍严格校验。
- `require_admin()`：目录管理、后台等管理员路由。
- `require_kb_access()`：KB 读写权限校验。

`backend/api/routers/auth.py` 的 `_issue_auth_token()` 将登录 token 写入 Redis：

```text
auth:token:{token}
TTL = 24h
payload = user_id / username / display_name / role
```

普通登录、CAS、普通短信注册、访客短信登录/注册最终都使用同一类 Bearer token。

### 2.2 thread key

登录用户：

```text
external thread_id = 前端/会话 API 使用的 ID
internal thread_id = u_{user_id}__t_{external_thread_id}
```

访客设备态：

```text
X-Device-ID = gdev_<uuid> 或 gdev_<timestamp>_<random>
device_scope = HMAC(minio_secret_key, X-Device-ID)[:32]
internal thread_id = g_{device_scope}__t_{external_thread_id}
```

## 三、智能体运行时与本地目录隔离

本地路径由 `backend/core/config/paths.py` 统一生成。登录用户的内部 key 会展开到：

```text
base_dir/users/{uid}/threads/{tid}/
  files/
    artifacts/
```

会话历史、工件登记和下载都使用外部 `thread_id` 展示，但运行时和 checkpointer 使用内部 key。

### Local 与 AIO Sandbox

当前文档只描述隔离语义：

- Local 模式依赖路径校验和受控工具入口。
- AIO Sandbox 模式可提供更强容器边界，但仍不要求“每用户一个容器”；容器池可复用，数据隔离由当前线程目录挂载与路径规则保证。
- 生产环境应避免允许模型直接触达宿主任意路径或宿主 shell。

## 四、会话删除与历史恢复

`backend/api/routers/conversations.py:delete_conversation()` 当前流程：

1. 按 `thread_id + user.user_id` 查询会话，避免横向删除。
2. 设置 `conv.is_deleted=True` 并提交。
3. 尝试取消当前用户、当前会话的 active background task。
4. 调用 `checkpointer.adelete_thread(internal_thread_id)` 清理 LangGraph checkpoint。
5. 使用 `ScopedStorage(user_id, thread_id).delete_all_files()` 删除 MinIO 当前 thread artifacts。
6. 调用 `get_paths().delete_thread_dir(internal_thread_id)` 删除本地运行时目录。
7. 如果任一步清理失败，写入 `metadata_.deletion_cleanup_error`，恢复 `is_deleted=False`，返回 503。

重要边界：

- 当前删除不是物理删除 `Conversation` 行，而是软删除 + 清理运行态。
- 删除后同名 `thread_id` 的会话记录仍存在且 `is_deleted=True`。`ConversationStore` 当前不会自动恢复此记录，而是抛 `ConversationDeletedError`。因此前端新会话应生成新的 thread_id。

## 五、用户文件与对话附件

### 5.1 个人文件夹

`backend/api/routers/my_files.py` 实际路径：

| 方法 | 路径 | 鉴权/隔离 |
|---|---|---|
| `POST` | `/api/v1/files/upload` | `get_current_user`，写 `users/{uid}/personal-files/{file_id}/...` |
| `GET` | `/api/v1/my-files` | 只查 `UserFile.owner_user_id == user.user_id` |
| `PUT` | `/api/v1/my-files/{file_id}` | 只允许 owner 重命名 |
| `DELETE` | `/api/v1/my-files/{file_id}` | 只允许 owner 软删除 |
| `POST` | `/api/v1/sessions/{session_id}/files/attach` | 只允许 owner 绑定到自己的会话 |
| `POST` | `/api/v1/generated-files/save` | 校验 local path 或 MinIO object 必须在当前用户范围 |

### 5.2 对话附件

`backend/api/routers/chat_files.py` 实际路径：

| 方法 | 路径 | 鉴权/隔离 |
|---|---|---|
| `POST` | `/api/v2/chat-files/upload` | 登录用户上传，写 `users/{uid}/threads/{thread_id}/chat-files/{file_id}/...` |
| `GET` | `/api/v2/chat-files/{thread_id}` | `SessionFile.user_id == user.user_id` |
| `DELETE` | `/api/v2/chat-files/{file_id}` | 只解绑当前用户关联；长文档同步移除内存索引 |
| `GET` | `/api/v2/chat-files/{file_id}/images/{image_name}` | 签名 URL；校验 file_id、owner、thread、过期时间 |

长文档索引键为 `(user_id, thread_id)`，`ChatFileIndexManager` miss 时会从 `UserFile + SessionFile` 重建当前用户、当前会话的 long_doc 索引。

### 5.3 文件下载中心

`backend/api/routers/files.py` 注册在 `/api/v2/files`：

- `GET /api/v2/files?thread_id=...`：列当前用户 thread 文件。
- `GET /api/v2/files/{file_id}/meta` / `download`：通过 `resolve_user_file_for_download()` 校验 owner 或 `user_file_permissions`。
- `GET /api/v2/files/minio-artifact/download`：只允许 `users/{current_user_id}/threads/...` 对象。
- 本地下载只允许 `base_dir/users/{owner}/threads/.../files/artifacts/...`，拒绝系统目录和 symlink。

## 六、知识库目录与 KB 上传

### 6.1 知识库目录

`backend/api/routers/directories.py` 注册前缀 `/api/v1`，主要端点：

```text
GET    /api/v1/knowledge_bases/{kb_id}/directories
POST   /api/v1/knowledge_bases/{kb_id}/directories
GET    /api/v1/knowledge_bases/{kb_id}/directories/{category_path:path}
PUT    /api/v1/knowledge_bases/{kb_id}/directories/{category_path:path}
POST   /api/v1/knowledge_bases/{kb_id}/directories/{category_path:path}/rename
POST   /api/v1/knowledge_bases/{kb_id}/directories/{category_path:path}/move
POST   /api/v1/knowledge_bases/{kb_id}/directories/rename       # body: old_path + new_name
POST   /api/v1/knowledge_bases/{kb_id}/directories/move         # body: source_path + target_parent_path
DELETE /api/v1/knowledge_bases/{kb_id}/directories/{category_path:path}
POST   /api/v1/knowledge_bases/{kb_id}/directories/reorder
POST   /api/v1/knowledge_bases/{kb_id}/directories/sync
POST   /api/v1/knowledge_bases/{kb_id}/directories/recalculate
```

所有端点依赖 `require_admin()`。目录树由物理目录、文档 `category_path` 隐含目录和 `document_date` 虚拟日期目录组合而成。虚拟日期目录只能重命名为有效的 `YYYY-MM-DD`（同步文档日期）或移入物理目录，不能删除或排序。

### 6.2 KB 上传

`backend/api/routers/uploads.py` 注册为 `/api/v1/uploads/*`：

- 分块：`init`、`chunks/{upload_id}/{chunk_index}`、`complete/{upload_id}`。
- 批量：`batch`。
- 待入库：`pending`、`pending/batch-move`、`pending/{file_id}`。
- 入库：`ingest`、`ingest/status/{task_id}`。

KB 上传对象写入公共 KB bucket：

```text
pending/{kb_id}/{file_id}/{filename}
```

这是设计例外，不走用户文件桶；隔离依赖：

- `verify_api_key()`
- `require_kb_access(..., access="write")`
- `PendingFile.created_by == auth.user_id`
- KB owner/admin 权限体系

## 七、验收标准

| 场景 | 预期行为 |
|---|---|
| 用户 A 和 B 使用相同外部 thread_id | 内部 key 不同，checkpoint、目录和文件互不串扰 |
| 用户 B 读取用户 A 会话消息 | `/api/v2/conversations/{thread_id}/messages` 返回空或 403/404 语义，不泄露内容 |
| 用户 B 下载用户 A 文件 | `/api/v2/files/{file_id}/download` 403，并写 deny 审计 |
| 删除会话时 checkpointer 清理失败 | 恢复 `is_deleted=False`，返回 503，避免“列表不可见但数据未清”的半删除状态 |
| 对话长文档检索 | 只检索 `(user_id, thread_id)` 绑定的 long_doc 索引 |
| KB 上传 | 非 owner/admin 写入目标 KB 返回 403 |
