## 1. 背景与目标

基础力学课程智能体已上线运行，学生在对话中提出大量课程问题，但这些提问目前只散落在各自会话的 checkpoint 中，教师无法感知整体学情。本功能的目标：

1. **角色体系**：引入「学生（student）」与「教师（teacher）」两个业务角色，与现有 `admin` / `user` 并存。角色**仅由 admin 管理员在后台为用户新增/设置**，注册默认值与现有用户角色一律不变。整套角色与分析能力**仅属于基础力学智能体（fmca）**，其他智能体（ne/csh/audit 等）不涉及。
2. **提问可见**：教师可分页、按时间/关键词检索查看基础力学智能体中的全部学生提问。
3. **智能分析**：对选定时间窗口内的提问，利用模型做语义聚类与汇总，产出高频问题、关键词、趋势与教学建议式总结。
4. **可视化呈现**：在 `frontend_fmca` 新增教师专区，用图表（趋势、TOP-N 高频问题、关键词）与语义簇卡片呈现分析结果。

非目标（本期不做）：按班级/课程分组隔离（当前用户体系无班级概念）；其他智能体的角色与分析；实时流式分析；学生侧的个人学情报告；问题推送给老师（R4，甲方 2026-08-17 明确不需要）。

## 2. 现状调研结论（基于当前 dev 工作树）

### 2.1 认证与角色

- `backend/db/models/account.py:22` `User.role = Column(String(20), default="user")`，角色是自由字符串，无需 DDL 即可扩展取值。
- `backend/api/routers/admin_accounts.py:49` `_ROLES = {"admin", "user"}` 是管理员后台设置角色的白名单，`_normalize_role` 拒绝未知值。
- `backend/api/dependencies/auth.py:161` `require_admin` 依赖是「按角色拒绝 403」的既有模式；`backend/api/dependencies/auth.py:268` 与知识库 ACL（`KnowledgeBaseAcl.subject_type="role"`）也消费 `role`。
- 结论：新增 `student` / `teacher` 只需扩展 `_ROLES` 并新增 `require_teacher` 依赖，无 schema 变更；角色赋值完全走管理员后台既有用户管理链路，存量 `role="user"` 账号语义上视为学生。

### 2.2 会话与提问数据链路

- 提问入口：`POST /api/v2/agent-runtime/query`（`backend/api/routers/agent_runtime_tasks.py:196`），请求体 `AgentRuntimeQueryRequest`（`backend/api/schemas/agent_runtime.py:38`）携带 `question`、`agent_code`、`thread_id`、`model`、`workflow` 等。
- 游客提问走 Guest API `:8083` 的 `/api/v2/guest/query`（`backend/api/guest_http_server.py`），FMCA 前端存在游客模式（`frontend_fmca/src/api/agent-v2.ts:398`）。
- 会话元数据在环境自有的 SQLite 目录中（`backend/application/conversations/local_catalog.py`），`agent_code` 存在 metadata JSON 的 `agent_runtime.agent_code` 键里；消息正文在 LangGraph SQLite checkpoint 中。
- 跨用户查看会话已有先例：`backend/api/routers/admin_conversations.py`（管理员会话管理，读目录 + `serialize_checkpoint_messages` 回放消息）。
- 结论：**不适合**在教师查询时回溯解析全部 checkpoint（成本高、与压缩/归档语义耦合）。应在提问入口同步落一张业务表，与 `message_feedback` 的模式一致。

### 2.3 可复用的既有能力

| 能力 | 位置 | 复用方式 |
| --- | --- | --- |
| 业务表 + 迁移先例 | `backend/db/models/feedback.py`、迁移 `202608130001_add_message_feedback_table`（`backend/db/migrate.py:113`） | 新表照此模式：ORM + `scripts/migrations/` 注册，未执行的迁移仅离线校验 |
| LLM JSON 调用 | `backend/application/explore/explore_llm.py:197` `_llm_json` | 分析服务复用同款「prompt → 解析 JSON → 失败回退」形态（模型走 chat scope 目录，失败关闭） |
| map-reduce 汇总 | 历史压缩 `HistoryCompactor._summarize_pruned_messages` | 大批量提问分批聚类后 reduce 合并的同款模式 |
| 中文分词 | RAG 层 HanLP 封装（`backend/rag/keywords/`、`tokenization.run_tokenization` 专用线程池） | 关键词确定性统计的分词底座 |
| 图表 | `echartsLoader.ts` 按需注册 + `chartHydrator.ts`（`frontend/` 系） | 教师页图表按需加载 ECharts |
| 审计 | `backend/services/admin_audit.py` `write_admin_audit` | 教师查看/生成分析动作写审计日志 |
| 前端角色守卫 | `frontend_fmca/src/router/index.ts:127`（`requiresAdmin` meta + 路由守卫） | 新增 `requiresTeacher` meta 同款守卫 |

### 2.4 约束与纪律（来自项目 Skill / AGENTS.md）

- 新 MySQL 业务表需配迁移并注册进 `backend/db/migrate.py` 的 `MIGRATIONS`，且保持「迁移未对任何库执行、仅离线校验」的发布纪律。
- 测试与生产的会话数据隔离政策不变；本功能新增的是普通 MySQL 业务表，不涉及会话目录搬迁。
- 教师查看的是学生 UGC（含潜在个人信息），必须按 `agent_code` 做对象级授权，并写审计。
- 实现完成后需同步更新 `.agents/skills/radai-project-context/references/`（角色、路由、表、端口等事实变化）。

## 3. 总体设计

```text
学生/游客提问
   │  POST /api/v2/agent-runtime/query (或 /api/v2/guest/query)
   ▼
提问采集点（fire-and-forget 落库，不阻塞流式回答）
   ▼
MySQL: course_question_records ──────────────┐
   │                                          │ 确定性统计（趋势/精确去重/分词）
   ▼                                          ▼
教师 API /api/v2/teacher/analytics/*    分析服务 question_analytics
（require_teacher，agent_code 固定 fmca）（分批 LLM 语义聚类 + reduce 合并）
   │                                          │
   ▼                                          ▼
frontend_fmca /teacher/* 可视化      MySQL: course_question_reports（报告快照）
```

设计要点：

- **采集与回答解耦**：提问写入是独立业务表写入，失败只记日志，绝不影响对话主流程（与 `message_feedback` 的语义一致）。
- **分析是「快照报告」而非实时计算**：教师手动触发一次分析，结果落 `course_question_reports`，反复查看不重跑模型，成本可控。
- **确定性打底 + LLM 增强**：趋势、精确高频、关键词词频用 SQL/分词确定性生成；语义聚类与教学总结用 LLM；LLM 失败时报告降级为纯统计结果并标注。

## 4. 角色设计

### 4.1 角色取值与赋权

| role | 语义 | 赋权方式 |
| --- | --- | --- |
| `admin` | 平台管理员（现状不变） | 现有流程 |
| `user` | 存量通用账号（对基础力学智能体视同学生） | 存量，注册默认值不变 |
| `student` | 学生 | **仅 admin 在后台设置** |
| `teacher` | 教师 | **仅 admin 在后台设置** |

- 角色赋值只发生在管理员后台：`backend/api/routers/admin_accounts.py` `_ROLES` 扩展为 `{"admin", "user", "student", "teacher"}`，管理员通过既有用户管理接口（`POST /admin/users` / `PATCH /admin/users/{id}`，均已接受 `role` 字段）设置角色。**注册默认值保持 `user` 不变，不开放自助选择角色，四端注册链路零改动。**
- 管理 UI 现状：用户管理页在主 `frontend/` 的 `views/admin/system.vue`（角色下拉当前硬编码 `admin`/`user` 三个位置，约 684/706/750 行），需同步补 `student`/`teacher` 选项；`frontend_fmca` 的管理区（dashboard/kbs/prompts/skills）没有用户管理页，管理员经由主前端管理页或直接调 API 赋角色。是否给 fmca 管理区补一个用户管理页列入可选增强，不是本期必须项。
- 角色仍是 `users.role` 全局字段，但 `student` / `teacher` 两个取值**只被基础力学智能体的功能消费**；其他智能体不读取、不响应这两个角色，行为与 `user` 完全一致。
- `backend/api/dependencies/auth.py` 新增：

  ```python
  async def require_teacher(auth: ApiKeyAuth = Depends(verify_api_key)) -> ApiKeyAuth:
      if (auth.role or "").lower() not in ("teacher", "admin"):
          raise HTTPException(status_code=403, detail="需要教师权限")
      return auth
  ```

- 知识库 ACL 的 role 主体机制（`_explicit_kb_grants`）天然兼容新角色，无需改动。

### 4.2 教师授权范围：固定限定 fmca

- 本功能仅属于基础力学智能体，因此教师授权**不建授权表、不做多课程配置**：分析相关接口在后端把 `agent_code` 固定校验为 `'fmca'`（常量 `TEACHER_ANALYTICS_AGENT_CODE = "fmca"`），传入其他值直接 422/403。
- `admin` 与 `teacher` 均可访问教师分析接口；`teacher` 角色的全部能力边界就是 fmca 的提问数据与分析报告。
- 后端 403 是真实安全边界；前端只做入口显隐。其他智能体的对话、数据、前端均不受任何影响。

### 4.3 学生侧

- 学生无需任何新操作：账号角色为 `user` 或 `student` 都按学生看待，提问照常采集；`student` 取值仅为管理员名册管理（标记哪些账号是学生）提供语义，不改变任何前端体验与权限。

## 5. 提问采集设计

### 5.1 新表 `course_question_records`

```text
id               VARCHAR(36) PK (uuid)
user_id          VARCHAR(36) NOT NULL          -- 游客为 'guest'
username         VARCHAR(50) NOT NULL DEFAULT ''  -- 冗余快照，避免联表/改名丢历史
agent_code       VARCHAR(32) NOT NULL          -- 'fmca'
thread_id        VARCHAR(100) NOT NULL
question         TEXT NOT NULL                 -- 原文（路由层截断至 ≤2000 字符）
question_len     INT NOT NULL                  -- 原始长度（截断也可知）
workflow         VARCHAR(32) NULL
model_name       VARCHAR(128) NULL
is_guest         BOOLEAN NOT NULL DEFAULT FALSE
created_at       DATETIME NOT NULL
KEY idx_qr_agent_time (agent_code, created_at)
KEY idx_qr_user_time  (user_id, created_at)
```

设计说明：

- `question` 截断与反馈表 `question_excerpt`(500) 不同：分析聚类需要完整题干，2000 字符足够覆盖学生提问且可控。
- `username` 冗余快照：教师视图要按学生定位问题，避免每次 JOIN；同时保留 `user_id` 供精确筛选。
- 不存回答内容（教师看的是提问画像；看完整对话仍走既有管理员会话查看通道）。
- `agent_code` 列保留是为表结构的通用性；**采集与分析逻辑固定只接受 `fmca`**（见 5.2），其他智能体的提问不入库。

### 5.2 采集点

- **采集门禁（fmca 专属）**：采集服务入口先判 `agent_code == 'fmca'`，其他智能体直接跳过；**角色为 `teacher` / `admin` 的用户提问不采集**（教师试用智能体不应污染学情数据）。
- **认证用户**：`agent_runtime_tasks.py` 的 `query_agent_runtime` 在请求校验通过、`AgentRequest` 组装完成后，以 `asyncio.create_task` fire-and-forget 调用采集服务（独立 DB 会话，不占用请求事务；异常吞掉记 warning）。
- **游客**：Guest API 的 `/query` 同款采集（`is_guest=True`，`user_id='guest'`），同样受 fmca 门禁约束。游客提问纳入聚合但不提供按人筛选。
- **MCP `/query`**：也走同一采集（它同样构造 AgentRequest），保证「智能体中的所有提问」语义完整。
- 幂等/去重：不做写时去重（同一学生反复问同一题本身就是高频信号）；分析阶段做归一化去重计数。
- 历史数据：新表从上线起累积。可选运营步骤：一次性脚本从既有 checkpoint 回放解析 fmca 历史 HumanMessage 回填（标记 `is_guest` 按 catalog 属主），默认不做，列入后续可选工作。

## 6. 分析服务设计

新建 `backend/application/question_analytics/`（编排放应用层，遵守分层纪律）：

```text
question_analytics/
├── models.py        # QuestionCluster / KeywordStat / ReportResult 等数据类
├── collector.py     # 窗口取数、归一化、精确去重、趋势/词频等确定性统计
├── llm_cluster.py   # 分批语义聚类 + reduce 合并 + 教学总结（LLM）
└── service.py       # 报告生命周期编排（生成/查询/删除）
```

### 6.1 确定性统计（无模型，每次报告必出）

- **时间趋势**：按天 `COUNT(*)` 聚合（SQL `DATE(created_at)`），另给按学生去重的活跃数。
- **精确高频**：归一化（去空白/全半角/标点/大小写）后 `GROUP BY` 计数，取 TOP-N（默认 20）。
- **关键词**：HanLP 分词（复用 RAG 分词线程池，不进事件循环默认池）+ 停用词表过滤 + 词频统计；产出 TOP-50 词。

### 6.2 LLM 语义聚类

- **取数上限**：单报告窗口内问题数硬上限（如 5000 条，env 可调），超出按时间均匀抽样并在报告中标注 `sampled=true`。
- **map 阶段**：分批（每批 ≤80 条），每批调一次 `_llm_json` 形态的 chat 模型调用，输出该批语义簇：

  ```json
  [{"label": "力的合成与分解", "question_ids": [...], "keywords": ["合力","分力","平行四边形"]}]
  ```

- **reduce 阶段**：把各批簇标签再合并（同名/近义簇归并、计数求和、代表问题重选），并生成一段 ≤500 字的教学总结（高频难点分布、建议复习方向）。簇与原始问题的关联只保留 `question_ids`（报告 JSON 内），展示时按 id 回查原文。
- **超时与降级**：单批超时/解析失败 → 该批退化为「未聚类」桶；整体 LLM 失败 → 报告状态仍为 `done` 但 `result.llm_status="degraded"`，只含确定性统计。模型名记录进报告。
- **并发控制**：同一时刻只允许一个 `running` 报告（DB 状态 + 应用层锁；数据只有 fmca 一个 agent，单飞即可）；生成接口限速。

### 6.3 报告表 `course_question_reports`

```text
id              VARCHAR(36) PK
agent_code      VARCHAR(32) NOT NULL
created_by      VARCHAR(36) NOT NULL           -- 触发教师
range_start     DATETIME NOT NULL
range_end       DATETIME NOT NULL
question_count  INT NOT NULL
status          VARCHAR(16) NOT NULL           -- running/done/failed
result_json     JSON NULL                      -- 趋势/高频/关键词/簇/总结/降级标记
model_name      VARCHAR(128) NULL
error           VARCHAR(500) NULL
created_at      DATETIME NOT NULL
finished_at     DATETIME NULL
KEY idx_qrpt_agent (agent_code, created_at)
```

生成是后台任务（FastAPI 后台任务或复用 task worker；v1 建议进程内后台任务 + 状态轮询，与 keywords 初始化任务同款模式，见 `backend/api/routers/keywords.py` 的任务状态发布）。

## 7. API 设计

新路由 `backend/api/routers/teacher_analytics.py`，`prefix="/api/v2/teacher/analytics"`，仅 agent 角色挂载（与 `message_feedback` 一致，Guest API 不挂）。全部接口依赖 `require_teacher`；`agent_code` 参数存在但后端固定校验为 `fmca`（其他值 422），并写审计。

| 方法与路径 | 说明 |
| --- | --- |
| `GET /questions?agent_code&from&to&keyword&user_id&page&page_size` | 全部提问分页列表（时间倒序），关键词走 `LIKE` 前缀转义匹配 |
| `GET /overview?agent_code` | 轻量实时统计：总量/今日/近 7 日趋势/活跃学生数（纯 SQL，无 LLM） |
| `POST /reports` `{agent_code, from, to}` | 触发分析报告生成，返回报告 id 与 `running` 状态 |
| `GET /reports?agent_code` | 报告列表（不含 result 正文） |
| `GET /reports/{id}` | 报告详情（含 result_json） |
| `DELETE /reports/{id}` | 删除本人创建的报告（admin 任意） |

授权与护栏：

- 非教师角色 → 403；`agent_code` 非 `fmca` → 422；不存在/他人报告 → 404（不泄露存在性）。
- 时间窗跨度上限（如 180 天）、`page_size` ≤ 100（沿用 `get_pagination` 惯例）。
- 审计动作：`teacher.questions.list` / `teacher.report.create` / `teacher.report.delete`，复用 `write_admin_audit`。

## 8. 前端设计（frontend_fmca）

仅 `frontend_fmca` 新增页面，**不触碰**四端共享的 `ne-full` 组件与 chat-UX 契约文件（否则触发 `test_chat_ux_module_consistency` 等防漂移契约与跨端同步义务）。

### 8.1 路由与守卫

```text
/teacher                → TeacherLayout（参照 admin/AdminLayout 样式）
  /teacher/dashboard    → 总览（统计卡片 + 近 30 天趋势折线）
```

## 10. 安全、隐私与性能

- **对象级授权**：教师分析能力固定收敛于 fmca（后端常量校验 `agent_code`），教师之间互不可见对方报告（除 admin）；其他智能体无任何新暴露面。
- **PII**：教师视图展示学生 `display_name`（教学场景需定位学生），游客提问标记匿名；不对教师暴露学生手机号/邮箱。
- **注入与 XSS**：问题文本是 UGC——列表渲染一律文本插值；LLM 总结走消毒 Markdown；关键词 `LIKE` 参数化。
- **成本与稳定性**：采集写入与 LLM 分析失败均不影响对话主流程；分析任务单飞 + 条数上限 + 分批超时；报告生成接口按用户限速（复用 Redis 限速器）。
- **架构边界**：`backend/services` 不 import `api` 层（`test_agent_architecture_boundaries` 约束）；编排逻辑在 `application/question_analytics`。
