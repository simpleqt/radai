## 1. 系统定位

本知识库在 **LightRAG + RAGAnything** 之上构建：

- **入库层**：LightRAG 负责文档解析、实体/关系抽取、chunk 向量与图写入。
- **检索层（生产默认）**：自研 **DirectRetriever 四路并行召回** + **Retrieval Profile 驱动的 Stage-2 过滤**，统一经 `retrieve_context` 对外服务。
- **回退**：`USE_DIRECT_RETRIEVER=false` 或 DirectRetriever 初始化/执行失败时，Stage-1 回退 LightRAG `aquery_data(mode="mix")`。

设计目标：在保留 LightRAG 存储与入库能力的同时，对白盒召回路径、融合权重、图扩展与过滤策略实现精细控制，并按知识库类型落地消融结论。

| 层级 | 技术选型 |
|------|---------|
| 检索编排 | `retrieve_context` + Retrieval Profile |
| Stage-1 召回 | DirectRetriever（默认）/ LightRAG（回退） |
| 向量库 | Milvus（chunk + keyword_index） |
| 图库 | NebulaGraph（每 KB 独立 Space） |
| KV / 状态 | Redis（BM25、text_chunks、doc_status） |
| 元数据 | MySQL（KB/文档记录） |
| 原文件 | MinIO（`backend/storage/` 为 MinIO 客户端抽象，非向量/图） |
| 重排序 | Qwen3-Reranker-8B（`FULL` Profile 可选） |
| 评测 | HotpotQA / 期刊论文库（Ragas）/ GraphRAG-Bench **官方 LLM 检索指标** |

## 3. 端到端数据流

### 3.1 入库 → 索引

```
文档上传 (MinIO/本地)
    → RAGAnything 解析 (MinerU/Docling)
    → LightRAG insert：chunk 向量 / 实体关系 / Redis KV
    → RAGIndexSyncManager：新实体增量写入 Milvus keyword_index + Redis BM25
```

关键入口：`RagService.insert_docx()` / `process_multimodal()` → `insert_content_list()`（`backend/rag/service.py`）。

### 3.2 检索 → 回答

```
用户 query + kb_id
    │
    ▼
① resolve_retrieval_profile(kb_id, kb_code)
    → Path-A~D 开关、FilterMode、是否 Stage-1 过采样
    │
    ▼
② PerKBKeywordExtractor.extract()
    → hl_keywords / ll_keywords / QueryType / weighted_seed_scores
    │
    ▼
③ Stage-1（默认 DirectRetriever 四路并行）
    → RawRetrievalData（entity / relationship / chunk + 原始分数标签）
    │
    ▼
④ PerKBContentFilter.filter_content(mode = Profile.content_filter_mode)
    │
    ▼
⑤ 截断 chunk_top_k → context_prompt + 图片 + stats
    │
    ▼
（可选）multi_kb_search：多库并发 + RRF 融合 → Agent LLM 生成答案
```

**统一入口**：`backend/api/routers/rag.py` → `retrieve_context()`。以下调用方行为一致：

| 调用方 | 位置 |
|--------|------|
| HTTP | `POST /api/v1/rag/retrieve`、`/retrieve_internal`、`/query_stream` |
| Agent | `multi_kb_search_tool`、`ProfiledAgentExecutor`、`LightweightQAAgent` |
| 遗留 | 旧单库 Agent 链路已下线，统一走 `retrieve_context()` + v2 Agent / Tool |

环境变量：

| 变量 | 默认 | 说明 |
|------|------|------|
| `USE_DIRECT_RETRIEVER` | `true` | Stage-1 走 DirectRetriever |
| `RAG_RETRIEVAL_PROFILE` | — | 全局强制 Profile |
| `RAG_KB_RETRIEVAL_PROFILE_MAP` | `{}` | JSON：`kb_id → profile`（`settings.rag_kb_retrieval_profile_map`） |
| `RAG_DEFAULT_RETRIEVAL_PROFILE` | `default` | 未匹配 KB 时的默认 Profile |

## 4. Retrieval Profile（按 KB 类型编排）

模块：`backend/rag/retrieval_profile.py`。

| Profile | Path-A | Stage-2 | Stage-1 过采样 | 适用场景 |
|---------|:------:|---------|:--------------:|----------|
| `default` | ✅ | `FULL`（PPR+Rerank+MMR） | ✅ | 未知 KB，向后兼容 |
| `general_qa` | ❌ | `RAW`（跳过 Stage-2） | ❌ | HotpotQA 等百科多跳 |
| `domain` | ✅ | **`MMR_ONLY`** | ✅ | 核电子学 / 期刊论文 / CSH |
| `lightweight` | ✅ | **`MMR_ONLY`** | ❌ | 多库轻量 Agent 检索 |

**自动匹配优先级**（高 → 低）：

1. `retrieval_profile_override` 参数  
2. `RAG_RETRIEVAL_PROFILE`  
3. `settings.rag_kb_retrieval_profile_map`  
4. 已知 `kb_id` 硬编码（见下表）  
5. `kb_code` 前缀：`hotpotqa_fullwiki*` / `hotpotqa*` → `general_qa`；`rag_nuclear_electronics*` / `NuclearElectronicsPaperRepository*` → `domain`  
6. `settings.rag_default_retrieval_profile`（默认 `default`）

**已知知识库 ID**（`backend/rag/retrieval_profile.py`、`eval/graphrag_bench/bench_data.py`）：

| 用途 | kb_id | Profile |
|------|-------|---------|
| 核电子学主库 | `<kb_id_ne>` | `domain` |
| 期刊论文库 | `<kb_id_paper>` | `domain` |
| CSH 水文地质库 | `<kb_id_csh>` | `domain` |
| GraphRAG-Bench medical | `<kb_id_bench_medical>` | `domain` |
| GraphRAG-Bench novel | `<kb_id_bench_novel>` | `general_qa` |

**生产要点（2026-05-22 落地）**：`domain` / `lightweight` 的 Stage-2 已由历史 `PPR_MMR` 改为 **`MMR_ONLY`**（跳过 PPR 与 Rerank API，仅 MMR 去重）。消融方案 `domain_baseline` 仍保留 `PPR_MMR` 作对照。

### 4.1 关键词提取（Stage 0）

模块：`backend/rag/keywords/extractor.py` → `PerKBKeywordExtractor`。

- **生产默认**：向量 + BM25 + RRF（0.7/0.3）+ 图邻域扩展 → `hl_keywords` / `ll_keywords` / `QueryType` / `weighted_seed_scores`（供 PPR 种子与 Path-A 双向向量）。
- **GraphRAG 评测对照**：`eval/graphrag_bench/keyword_sources.py` 提供 **hybrid**（生产）与 **LightRAG LLM** 提词；`keyword_compare.py` 输出 Jaccard。
- **结论（2026-05-30）**：医学库必须用 hybrid（ER 0.70 vs LLM 0.50）；勿将自研词注入 LightRAG `aquery_data`（`_our_kw`）。详见 §11.6 与 plans §4.5、§15.1。

## 5. DirectRetriever 四路并行召回（Stage-1）

> 实现：`backend/rag/retriever/direct_retriever.py`  
> 目标：绕过 LightRAG `aquery_data` 黑盒，直连 Milvus / Redis / NebulaGraph。

### 5.1 架构示意

```
查询 + 关键词 + QueryType
         │
    ┌────┴──────────────────────────────────┐
    │      四路并行（asyncio.gather）          │
  Path-A              Path-B              Path-C              Path-D
实体向量 ANN         实体 BM25           Chunk 语义向量       图扩展
(Milvus              (Redis +           (Milvus              (NebulaGraph
keyword_index)       关键词扩展)         chunks_vdb)          BIDIRECT + BFS)
    └──── RRF 融合 ────┘                   │                    │
         SeedEntity ──────────────────────┴────────────────────┘
                    │
         merge_entity_pool（边感知截断，pool_size=150）
                    │
         实体链路拉取 chunk + merge_chunk_pool（含 Path-C）
                    │
              RawRetrievalData
```

### 5.2 各路径说明

| 路径 | 数据源 | 核心行为 | 输出分数标签 |
|------|--------|----------|--------------|
| **Path-A** | Milvus `rag_{kb_code}_keyword_index` | query + hl 关键词双向向量 ANN，RRF 融合 | `_vec_score` |
| **Path-B** | Redis BM25 | 原始 query + 最多 5 个 hl 扩展，RRF(k=60) | `_bm25_score` |
| **Path-C** | Milvus `chunks_vdb` | 跳过实体层，直接 chunk ANN | `_vec_score`, `source_type=direct_vec` |
| **Path-D** | NebulaGraph | 种子实体 GO 多跳 + 内存无向 BFS 结构传导 | `_graph_score` |

**QueryType 策略矩阵**（`retriever/config.py`）：自适应 `entity_vec_top_k`、`score_floor`、`chunk_vec_mult`、`graph_depth`（COMPARISON/CONCEPT 深度 2，其余多为 1）。

**Path-A 与 Profile**：`general_qa` 默认关闭 Path-A（百科库实体向量噪声大）；`domain` 保持开启（垂直领域术语命中有效）。

**融合要点**（`fusion.py`）：

- **边感知实体池截断**：先保留高分 core，再按与 core 相连边数加分填入邻居，避免 Path-D 扩展边在纯分数截断下全部丢失（历史 Bug：PPR 子图边数≈0）。
- **Chunk 综合分**：实体链路分 + 向量分 + 实体覆盖度，QueryType 自适应权重 α₁/α₂/α₃。
- **双源召回奖励**：同时命中实体链路与 Path-C 的 chunk 得分 ×1.20。
- **PPR 种子**：关键词 `weighted_seed_scores` 与检索 `fused_score` 线性混合（`build_ppr_seed_weights`）。

## 6. Path-D 图扩展（NebulaGraph）

实现：`backend/rag/retriever/graph_expander.py`。

### 6.1 nGQL 与边过滤

- 统一边类型：`OVER relation`（语义在 `relation_type`、`description`、`weight` 属性）。
- 条件：`description != ''` 且 `weight >= graph_relation_weight_floor`（默认约 0.45）。
- **不再**按 `QueryType` 注入 `relation_type IN (...)` 白名单（存量边多为 `related_to`，白名单导致关系大量丢失）。

### 6.2 2026-05-25 双向属性 + 无向 BFS 传导

**问题**：旧版 `BIDIRECT` 仅 YIELD 终点属性，反向遍历时邻居属性丢失，种子分被错误覆盖，多跳传导失效。

**现行方案**：

1. nGQL 同时 YIELD 起点 `$^.entity` 与终点 `$$.entity` 全量属性。  
2. 在内存构建**无向邻接表** `adj`。  
3. 从 `seed_scores` 出发层序 BFS 传导：

   $$Score_{neighbor} = Score_{seed} \times (1 + \ln(\max(0, w-1))) \times 0.8^{hop}$$

4. 与物理边方向解耦，修复多跳召回精度。

**其他限制**：图扩展种子数上限 30（`graph_max_seeds`），防止 GO 查询随种子线性膨胀。

## 7. Stage-2 内容过滤

模块：`backend/rag/content_filter/per_kb_filter.py`。由 Profile 的 `FilterMode` 控制：

| FilterMode | 流水线 |
|------------|--------|
| `RAW` | 直通 Stage-1 → atomic_assembly |
| `MMR_ONLY` | MMR 多样性重排（λ≈0.7）★ domain 生产 |
| `PPR_MMR` | PPR → MMR（无 Rerank）★ 消融对照 |
| `FULL` | PPR → Rerank → Time-Aware → MMR → Evidence Rescue Bonus |

**PPR**（`ppr_filter.py`）：双源种子 personalization、QueryType/图密度自适应阻尼、语义反向边；实体 embedding 批处理上限 60。  
**Rerank**：Cross-Encoder 逐点打分；多跳 QA 易误杀半线索 chunk（HotpotQA 上 Recall 骤降）。  
**Evidence Rescue Bonus**：高 rerank、低 PPR 的「事实孤岛」chunk 加分（`ppr_ceiling=0.15` 为 HotpotQA 调优值）。

`FilterConfig.ppr_dynamic_edge_pruning` 为历史预留字段，**当前未接线**。

## 8. 多知识库检索 `multi_kb_search`

`backend/application/tools/providers/multi_kb_search_tool.py`：

- 未显式传入 hl/ll 时：**一次** QueryType 检测 + **一次** query embedding（以首个 KB 的 embedding 函数），再并发各库 `retrieve_context`。
- 内置：`MULTI_KB_PATH_A_QUERY_ONLY=1`（Path-A 每库 1 次整句向量）、默认关闭 Stage-1 过采样、进程内直调（无 HTTP 回环）。

**推荐 Agent 参数**：

| 参数 | 值 | 说明 |
|------|-----|------|
| `query` | 纯问题 | 勿传 runtime 元数据 |
| `kb_ids` | 按需 | 默认核电子学 + 期刊论文库 |
| `top_k` | 10 | 环境变量硬顶 12 |
| `chunk_top_k` | 6 | 融合后全局 chunk 上限 |
| `content_filter_mode` | `None` | 跟随 Profile（domain → MMR_ONLY） |

## 11. 测试结果与结论

### 11.1 期刊论文库 — DirectRetriever 消融

#### 规则匹配（evidence 子串，Top-K=10）

**2026-05-22（4 题抽样）** — 报告 `results/ablation_paper_4q_20260522.md`

| 方案 | F1 | ΔF1 |
|------|-----|-----|
| E0 PPR+MMR 基线 | 0.3376 | — |
| E1 RAW / E2 MMR_ONLY | 0.7865 | +0.4489 |
| A3 无 Path-D | 0.6045 | +0.2669 |
| A2 无 Path-C | 0.2181 | −0.1195 |

**2026-05-25（17 题全量，图扩展 BFS 修复后）** — 数据 `results/ablation_paper_17q.json`

| 方案 | F1 | Recall@10 | 延迟 |
|------|-----|-----------|------|
| **E1 RAW / E2 MMR_ONLY** | **0.6292** | **0.6216** | 1.8–2.5s |
| E0 PPR+MMR 基线 | 0.4011 | 0.3922 | 5.3s |
| A3 无 Path-D | 0.4919 | 0.4480 | 4.2s |
| A2 无 Path-C | 0.3781 | 0.4059 | 3.7s |
| A6 仅 Path-C | 0.4732 | 0.4873 | 2.4s |

要点：修复双向图传导后，**关闭 Path-D 反而使 F1 下降约 22%**（0.6292→0.4919），说明 Path-D 对垂直库多跳召回有显著正向贡献；Path-C 仍是底座（关闭后全面劣化）。

#### Ragas（17 题，Judge=`minimax-m2.7`，基线=`domain_no_ppr`）

**2026-05-22** — `results/ragas_ablation_17q_20260522.md`

| 方案 | CP | CR |
|------|-----|-----|
| E0 PPR+MMR | 0.1196 | 0.2941 |
| **E2 MMR_ONLY** | **0.3650** | **0.4706** |
| E1 RAW | 0.3086 | 0.4118 |

**2026-05-25（BFS 修复后）** — `results/ragas_ablation_17q.md`

| 方案 | CP | CR | ΔCP / ΔCR（相对 E2） |
|------|-----|-----|----------------------|
| **E1 RAW** | **0.4960** | **0.5294** | +0.163 / +0.176 |
| E2 MMR_ONLY（生产） | 0.3329 | 0.3529 | 基线 |
| E0 PPR+MMR | 0.1882 | 0.2941 | −0.145 / −0.059 |
| A3 无 Path-D | 0.2353 | 0.2745 | −0.098 / −0.078 |
| A2 无 Path-C | 0.0559 | 0.1765 | −0.277 / −0.176 |

要点：

1. **PPR 为最大拖累**：E0 相对 MMR_ONLY，CP 约 −44%、CR 约 −17%（2026-05-25 全量）。  
2. **生产选 MMR_ONLY 而非 RAW**：规则匹配 F1 与 RAW 持平，MMR 提供去重；Ragas 下 RAW CP 更高，但生产需在精度与多样性间折中，且 MMR 关闭（B3）CP 明显下降。  
3. **Path-D 在修复后不可或缺**：Ragas 下去掉 Path-D，CP/CR 均显著低于 MMR_ONLY 基线。  
4. **Path-C 为压舱石**：关闭后 CP 接近归零。

### 11.4 结论摘要（生产决策）

| # | 结论 | 落地状态 |
|---|------|----------|
| 1 | 垂直库（期刊/核电子学/CSH）**禁用 PPR**，Stage-2 使用 **MMR_ONLY** | ✅ `domain` / `lightweight` Profile |
| 2 | **Direct 四路优于 LightRAG 原生 mode**（期刊库 17 题） | ✅ 默认 `USE_DIRECT_RETRIEVER=true` |
| 3 | **Path-C（chunk 向量）不可关闭** | ✅ 四路默认全开 |
| 4 | **Path-D 在 BFS 修复后对垂直库召回关键** | ✅ 保持开启；nGQL 不用 relation_type 白名单 |
| 5 | 百科多跳（HotpotQA）关 Path-A + Stage-2 RAW 最优 | ✅ `general_qa` Profile |
| 6 | LightRAG 仅作入库与回退；评测对比保留 `eval_lightrag_modes*.py` | ✅ |
| 7 | GraphRAG-Bench full-ablation：medical prod 验证；novel prod 优于 FULL/hybrid，但 naive ER 更高（§11.5） | ✅ 2026-05-29 |
| 8 | 关键词：生产固定 **hybrid**；勿 LLM 提词（medical）、勿 `_our_kw` 注入 LightRAG（§11.6） | ✅ 2026-05-30 |
| 9 | Novel 库可选：评估 LightRAG naive/mix 专用 Profile（GraphRAG 场景） | 📋 待决策 |

**后续优化方向**（非阻塞）：修复 MMR embedding 加载；若重开 PPR 需先提升图谱质量；可选 `--generate` 补 Faithfulness / AnswerRelevancy。

### 11.5 GraphRAG-Bench — 全模块官方评测（qwen3.5-35b · `ablation_full_20260529`）

**设定**：medical / novel 各 30 题，每库 **23** 方案（Direct 全消融 + LightRAG 五 mode）；裁判 qwen3.5-35b。  
**汇总**：`eval/graphrag_bench/results/official_ablation_summary_ablation_full_20260529.json`  
**详表与分析**：[plans §15.2–15.3](../plans/知识库算法和架构.md)

#### 生产基线 vs 最佳方案（ER）

| 知识库 | 生产 `prod_profile` | 本库 ER 最高方案 | 最高 ER |
|--------|---------------------|------------------|---------|
| medical (`domain`) | CR 0.825 / ER **0.733** | direct_chunk_only* / lightrag_local | 0.817 / 0.733 |
| novel (`general_qa`) | CR 0.700 / ER **0.600** | **lightrag_naive** | **0.744** |

\*chunk_only 为实验配置（仅 Path-C + FULL），非生产 Profile。

#### 核心结论（官方 ER）

1. **Medical**：生产 MMR_ONLY 四路 **验证通过**（ER 0.733）；显著优于 hybrid（0.433）与 direct_full（0.533）；PPR/FULL 负优化、Path-C 为底座与期刊库结论一致。  
2. **Novel**：生产 RAW **合理**（ER 0.600），远高于四路+FULL（≈0.07）与 hybrid（0）；但 **LightRAG naive（0.744）/ mix（0.633）高于 prod**——若仅服务 GraphRAG-Novel，可考虑向量优先策略（见 plans §15.3）。  
3. **LightRAG mode**：两库上 **hybrid/global 均偏弱**；medical 上 naive/local/mix 与 prod 同档；novel 上仅 naive/mix 有效。
