# 提示词模板构建教程

本文档说明管理员如何在「提示词管理」中构建、修改和验证入库抽取 Schema。当前统一提示词管理入口为：

- RadAI 管理后台：`/admin/prompts`
- CSH-AI 管理后台：`/admin/prompts`
- 后端统一接口：`/api/v1/prompts/*`

当前已接入的模板分类是「入库抽取 Schema」。它不是普通聊天提示词，而是一份结构化 YAML。系统会根据 YAML 中定义的实体类型、关系类型、置信度和禁用规则，生成文档入库时使用的 LLM 抽取提示词。

## 1. 什么是入库抽取 Schema

入库抽取 Schema 决定一批文档在入库时应该抽取什么知识。

例如水文地质文档中，常见的实体可以是：

- `aquifer`：含水层、隔水层、地层单元
- `location`：区域、井位、剖面、采样点
- `parameter`：水位、渗透系数、浓度、流速
- `method`：试验、模型、监测、评价方法

常见的关系可以是：

- `located_in`：实体位于某区域或层位
- `has_parameter`：对象具有某参数
- `measured_by`：指标由某方法测得
- `affects`：过程、污染物或措施影响对象

Schema 的目标不是把所有词都抽出来，而是把后续检索、问答、图谱分析真正需要的核心对象和关系稳定抽出来。

## 2. 页面操作流程

1. 进入管理后台，打开「提示词管理」。
2. 左侧选择「入库抽取 Schema」。
3. 中间选择已有模板，或点击「新建模板」。
4. 填写模板 ID、名称、领域、版本。
5. 在「模板内容」中编辑 YAML。
6. 点击「保存」。
7. 新建知识库时，在「入库抽取 Schema（提示词模板）」下拉框中选择该模板。
8. 上传少量样本文档做试入库，检查抽取结果，再迭代模板。

## 3. 推荐构建步骤

### 第一步：确定模板边界

先写清楚这个模板服务哪一类文档，不要把多个差异很大的领域塞进一个模板。

好的边界示例：

- 地下水资源管理报告
- 场地污染修复方案
- 核电子学探测器论文
- 水文地质勘察报告

不推荐的边界：

- 所有地质文档
- 所有科研论文
- 所有项目资料

模板越泛，抽取越容易变成普通关键词共现；模板越贴近文档类型，图谱质量越稳定。

### 第二步：设计实体类型

实体类型应该是稳定的名词概念，数量建议控制在 6 到 12 个。

实体类型适合包含：

- 业务对象：含水层、地下水资源、污染物、监测井、管理单元
- 空间对象：区域、井位、剖面、采样点
- 指标参数：水位、开采量、水质浓度、渗透系数
- 方法措施：监测方法、治理措施、评价模型
- 文件中常见的编号或代码：项目编号、标准编号、模型代码

实体类型不适合包含：

- 过细的一次性名词
- 形容词，如严重、稳定、较高
- 完整句子或事件描述
- 页面布局词，如图 1、表 2、摘要、关键词

### 第三步：设计关系类型

关系类型表示实体之间的有向边，数量建议控制在 5 到 12 个。

每个关系建议配置：

- `description`：关系含义
- `aliases`：文档中可能出现的表达
- `allowed_source_types`：允许作为起点的实体类型
- `allowed_target_types`：允许作为终点的实体类型
- `min_confidence`：该关系进入正式结果的最低置信度

关系设计要具体，避免所有关系都用 `related_to`。如果只需要弱关联，可以保留一个 `co_occurs`，但不要让它成为主要关系。

### 第四步：设置置信度

常用建议：

| 字段 | 推荐值 | 说明 |
| :--- | :--- | :--- |
| `candidate_confidence` | `40` | 低于该值的候选会被丢弃。 |
| `min_entity_confidence` | `55` 到 `65` | 实体进入结果的默认门槛。 |
| `min_relation_confidence` | `60` 到 `70` | 关系进入结果的默认门槛。 |
| 单个关系的 `min_confidence` | `50` 到 `75` | 重要关系可更高，弱关联可更低。 |

如果抽取结果太少，可以先降低 5 分；如果噪声太多，优先提高关系置信度，而不是盲目增加实体类型。

## 4. YAML 字段说明

```yaml
schema_id: groundwater_management
label: 地下水管理
version: "1.0"
subject: groundwater_management
min_entity_confidence: 60
min_relation_confidence: 65
candidate_confidence: 40

entity_types:
  entity_name:
    description: 实体类型说明
    aliases: [别名1, 别名2]

relation_types:
  relation_name:
    description: 关系类型说明
    aliases: [表达1, 表达2]
    allowed_source_types: [entity_name]
    allowed_target_types: [entity_name]
    min_confidence: 65

forbidden_relations:
  - causality_without_evidence
```

字段含义：

| 字段 | 是否必填 | 说明 |
| :--- | :--- | :--- |
| `schema_id` | 是 | 模板 ID。只能包含小写字母、数字、下划线，且必须以字母开头。 |
| `label` | 建议填写 | 页面展示名称。 |
| `version` | 是 | 模板版本，建议用字符串，如 `"1.0"`。 |
| `subject` | 是 | 领域标识，通常与 `schema_id` 一致。 |
| `min_entity_confidence` | 是 | 默认实体置信度阈值。 |
| `min_relation_confidence` | 是 | 默认关系置信度阈值。 |
| `candidate_confidence` | 是 | 候选事实最低阈值。 |
| `entity_types` | 是 | 实体类型定义，必须是非空对象。 |
| `relation_types` | 是 | 关系类型定义，必须是非空对象。 |
| `forbidden_relations` | 建议填写 | 禁止抽取的关系模式。 |

命名规范：

- `schema_id`、实体类型、关系类型统一使用小写英文和下划线。
- 不使用中文作为实体类型或关系类型的键名，中文写在 `description` 和 `aliases` 中。
- `schema_id` 必须和模板 ID 一致，否则保存会失败。
- YAML 缩进使用空格，不要使用 Tab。

## 5. 完整示例：地下水管理

下面示例适合地下水资源管理、取水许可、监测监管、水位水质管理、超采治理等文档。

```yaml
schema_id: groundwater_management
label: 地下水管理
version: "1.0"
subject: groundwater_management
min_entity_confidence: 60
min_relation_confidence: 65
candidate_confidence: 40

entity_types:
  management_unit:
    description: 地下水管理单元、行政区、管控区或评价区
    aliases: [管理单元, 行政区, 管控区, 评价区, 地下水管理区]
  groundwater_resource:
    description: 地下水资源、地下水系统或地下水体
    aliases: [地下水资源, 地下水系统, 地下水体, 地下水]
  aquifer:
    description: 含水层、隔水层、承压含水层或潜水含水层
    aliases: [含水层, 隔水层, 承压含水层, 潜水含水层, 地层]
  monitoring_point:
    description: 监测井、观测井、采样点或监测断面
    aliases: [监测井, 观测井, 采样点, 监测点, 监测断面]
  water_use:
    description: 取水、供水、开采、用水行业或用水对象
    aliases: [取水, 供水, 开采, 用水, 用水户, 用水行业]
  parameter:
    description: 水位、水量、水质、埋深、开采量、补给量等指标
    aliases: [水位, 水量, 水质, 埋深, 开采量, 补给量, 指标, 参数]
  regulation_measure:
    description: 管控、限采、压采、回补、修复、保护等管理措施
    aliases: [管控措施, 限采, 压采, 回补, 修复, 保护, 治理措施]
  policy_or_standard:
    description: 政策、规划、标准、规范、许可证或管控要求
    aliases: [政策, 规划, 标准, 规范, 许可证, 管控要求]
  risk_or_problem:
    description: 超采、污染、地面沉降、水位下降、咸水入侵等问题
    aliases: [超采, 污染, 地面沉降, 水位下降, 咸水入侵, 风险, 问题]
  model_or_code:
    description: 模型、编号、标准号、项目号或代码
    aliases: [模型, 编号, 标准号, 项目号, 代码]

relation_types:
  located_in:
    description: 实体位于某管理单元、区域、含水层或监测点
    aliases: [位于, 所在, 分布于, 隶属于]
    allowed_source_types: [groundwater_resource, aquifer, monitoring_point, water_use, risk_or_problem]
    allowed_target_types: [management_unit, aquifer, monitoring_point]
    min_confidence: 65
  has_parameter:
    description: 对象具有水位、水量、水质、开采量等指标
    aliases: [具有, 指标为, 参数为, 表现为]
    allowed_source_types: [management_unit, groundwater_resource, aquifer, monitoring_point, water_use]
    allowed_target_types: [parameter]
    min_confidence: 60
  monitored_by:
    description: 管理单元、含水层或指标由监测点监测
    aliases: [监测, 观测, 采样, 由监测点监测]
    allowed_source_types: [management_unit, groundwater_resource, aquifer, parameter]
    allowed_target_types: [monitoring_point]
    min_confidence: 65
  regulated_by:
    description: 对象受到政策、标准、许可证或管控要求约束
    aliases: [依据, 受约束, 按照, 执行, 管理要求]
    allowed_source_types: [management_unit, groundwater_resource, water_use, regulation_measure]
    allowed_target_types: [policy_or_standard]
    min_confidence: 70
  mitigated_by:
    description: 风险或问题通过管理措施进行治理、缓解或控制
    aliases: [治理, 缓解, 控制, 修复, 压采, 回补]
    allowed_source_types: [risk_or_problem]
    allowed_target_types: [regulation_measure]
    min_confidence: 70
  affects:
    description: 取水、风险或措施影响地下水资源、含水层或指标
    aliases: [影响, 导致, 造成, 改善, 改变]
    allowed_source_types: [water_use, risk_or_problem, regulation_measure]
    allowed_target_types: [groundwater_resource, aquifer, parameter, management_unit]
    min_confidence: 70
  applies_to:
    description: 政策、标准、措施适用于某管理对象或区域
    aliases: [适用于, 面向, 针对, 覆盖]
    allowed_source_types: [policy_or_standard, regulation_measure]
    allowed_target_types: [management_unit, groundwater_resource, water_use, risk_or_problem]
    min_confidence: 65
  co_occurs:
    description: 同一 chunk 中共同出现的弱关联，仅用于兜底
    aliases: [共现, 相关, 同时出现]
    min_confidence: 50

forbidden_relations:
  - causality_without_evidence
  - policy_without_target
```

## 6. 编写质量检查清单

保存前检查：

- `schema_id` 与页面模板 ID 完全一致。
- `entity_types` 至少 1 个，建议 6 到 12 个。
- `relation_types` 至少 1 个，建议 5 到 12 个。
- 每个关系的 `allowed_source_types` 和 `allowed_target_types` 都能在 `entity_types` 中找到。
- 别名不要只写一个词，尽量覆盖文档中的常见说法。
- 不要把实体类型写得过细，例如每一种污染物都建一个实体类型。
- 不要把关系类型写得过泛，例如全靠 `related_to`。
- `co_occurs` 只能作为兜底弱关系，不要代替业务关系。

试入库后检查：

- 抽取出的实体是否是业务对象，而不是大量普通词。
- 关系是否有明确证据，而不是凭常识推断。
- 图谱中是否出现大量孤立实体。
- 搜索问答是否能命中关键指标、措施、区域和政策。
- 如果噪声多，先收紧关系类型和置信度；如果漏抽多，再补充别名和实体描述。

## 7. 常见问题

### 保存时报 `schema_id` 不一致

页面上的模板 ID 和 YAML 中的 `schema_id` 必须一致。例如模板 ID 是 `groundwater_management`，YAML 第一行也必须是：

```yaml
schema_id: groundwater_management
```

### 保存时报 YAML 格式错误

常见原因：

- 使用了 Tab 缩进。
- 冒号后没有空格。
- 列表缩进不一致。
- 中文标点写进了 YAML 结构字段。
- `aliases` 少了中括号或逗号。

### 抽取结果很多但质量差

优先调整：

- 减少过泛实体类型。
- 给关系增加 `allowed_source_types` 和 `allowed_target_types`。
- 提高 `min_relation_confidence` 或关系自己的 `min_confidence`。
- 将弱关系 `co_occurs` 的用途限制为兜底。

### 抽取结果太少

优先调整：

- 给实体和关系补充 `aliases`。
- 把过窄的实体类型合并。
- 适当降低 `min_entity_confidence` 或 `min_relation_confidence` 5 分。
- 检查文档是否真的包含该领域内容。

## 8. API 调用示例

管理员也可以通过统一接口管理模板。

查询分类：

```bash
curl -H "X-API-Key: <admin-api-key>" \
  http://localhost:8082/api/v1/prompts/categories
```

查询模板列表：

```bash
curl -H "X-API-Key: <admin-api-key>" \
  "http://localhost:8082/api/v1/prompts/templates?category=extraction_schema"
```

查询单个模板：

```bash
curl -H "X-API-Key: <admin-api-key>" \
  http://localhost:8082/api/v1/prompts/templates/extraction_schema/hydrogeology
```

创建模板：

```bash
curl -X POST http://localhost:8082/api/v1/prompts/templates \
  -H "X-API-Key: <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "category": "extraction_schema",
    "template_id": "groundwater_management",
    "label": "地下水管理",
    "subject": "groundwater_management",
    "version": "1.0"
  }'
```

更新模板：

```bash
curl -X PUT http://localhost:8082/api/v1/prompts/templates/extraction_schema/groundwater_management \
  -H "X-API-Key: <admin-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"content": "<完整 YAML 内容>"}'
```

## 9. 推荐迭代方式

1. 先从 3 到 5 篇代表性文档开始试入库。
2. 看抽取结果，不要一开始就大批量入库。
3. 根据漏抽和误抽修改模板。
4. 模板稳定后再用于正式知识库。
5. 重大调整时升级 `version`，例如从 `"1.0"` 改为 `"1.1"`。

一个稳定的模板通常需要 2 到 4 轮小样本迭代。不要追求一次写完，先让核心实体和关系稳定，再逐步扩展。
