# 第一部分 · 白话版:这套检索到底在干什么

## 1.1 问题定义:大海捞针

用户问一句话,比如"Fe(VI) 在碱性条件下为什么稳定?"。知识库里有几万到几十万个**文本块(chunk)**——每块是论文/报告里几百字的一段。检索的任务:**从几十万块里挑出最能回答这个问题的 10 块**,交给大模型去写答案。挑错了,大模型再聪明也答不对——这就是"垃圾进垃圾出"。

## 1.2 为什么一种找法不够:五个侦探的比喻

想象五个侦探用不同方法找线索,各有擅长与盲区:

| 侦探 | 找法 | 擅长 | 盲区 |
|---|---|---|---|
| **向量侦探**(Path-C) | 把问题和每个文本块都变成"语义指纹"(一串数字,叫**向量/embedding**),指纹越像越相关 | 换个说法也能找到("铁酸盐"≈"Fe(VI)") | 精确编号、型号、罕见词 |
| **关键词侦探**(Path-B) | 像 Ctrl+F,看哪些块包含问题里的词(算法叫 **BM25**) | 型号"XJ-3000"、参数名、编号,一字不差地找 | 换了说法就瞎("降解"vs"分解") |
| **实体侦探**(Path-A) | 先认出问题问的是哪个"东西"(实体,如 Fe(VI)),再找提到这个东西的块 | 确定问题主角 | 主角出现的地方太多,好多与问题无关 |
| **图谱侦探**(Path-D) | 顺着"知识图谱"的关系边爬:Fe(VI)—氧化→微污染物,把关系背后的证据块拉进来 | 需要"拐个弯"才能找到的证据 | 爬出来一堆"主题相关但答不了题"的块 |
| **媒体侦探**(Path-E) | 只在用户问图/表时出动,专找图片、表格块 | "图 3-2 说了什么" | 平时不出动 |

**核心思想:每个侦探交一份带评分的嫌疑名单,再公平地合并成一份终审名单。** 合并环节(叫**融合**)是整套算法的心脏,也是我们踩坑最多、优化最多的地方。

## 1.3 全流程七步走(先记住这个骨架)

```
① 理解问题:分词 + 算语义指纹(两件事同时做,省时间)
② 五路并发找:五个侦探同时开工,各交一份名单
③ 资格审查:实体/图谱侦探的独家线索要有旁证才收
④ 融合排名:五份名单合成一份(RRF 排名投票 + 分数加权)
⑤ 取全文精排:前 ~30 名调出全文,逐块细看再加减分
⑥ 锦上添花:可选交叉编码重排 / 补相邻上下文(父窗口)/ 跨文档补证据
⑦ 交卷:前 10 块 + 相关实体/关系,送给大模型写答案
```

## 1.4 跟着一个问题走一遍

问题:**"Fe(VI) 在碱性条件下稳定,其向 Fe(IV)/Fe(V) 的转化受限,导致氧化能力如何变化?"**

1. **理解问题**:分词得到 `[Fe(VI), 碱性, 稳定, Fe(IV), Fe(V), 转化, 氧化能力, …]`;同时把整句变成 4096 维向量。两件事并行,总共 ~100ms。
2. **五路并发**:
   - 向量侦探:全库比指纹,交回 30 块,第 1 名相似度 0.72;
   - 关键词侦探:查倒排索引,"Fe(VI)+碱性+转化"同时命中的块得分最高;
   - 实体侦探:认出主角是实体 `Fe(VI)`,列出它关联的证据块,同时把 `Fe(VI)` 交给图谱侦探当起点(专业说法:**种子实体**);
   - 图谱侦探:从 `Fe(VI)` 出发沿关系边爬一步,`Fe(VI)—转化受限→Fe(IV)/Fe(V)` 这条边背后的证据块入选;
   - 媒体侦探:没问图表,休息。
3. **资格审查**:实体侦探列的 50 块里,只有同时被向量或关键词侦探点名的才保留——因为"提到 Fe(VI)"不等于"回答了这个问题"。图谱侦探的独家发现保留 4 个名额(万一真是拐弯才能找到的关键证据),其余也要旁证。
4. **融合排名**:不直接比各家分数(向量分 0.72 和 BM25 分 8.3 没法直接比,量纲不同),而是比**名次**:每份名单里第 r 名拿 `权重/(60+r)` 分,几家都点名的块分数累加。我们的 v2 版还会看"名次背后的分数成色"——某家名单里第 1 名如果分数只有该家最高分的一半,贡献也打对折。
5. **取全文精排**:前 ~30 名从数据库调出全文。逐块检查:问题的词在正文里密不密?标题/章节名是否对上?文件名是否就是用户说的那份文档?每项对上都加分。
6. **锦上添花**:第 2 名所在文档里,它前后相邻的 2 块拼进来当上下文(答案常常跨段);如果开了重排器,一个专门的"精读模型"把 24 个候选和问题逐对精读一遍再排序。
7. **交卷**:前 10 块 + "Fe(VI)→Fe(IV)/Fe(V)"这条关系线索,一起交给大模型。

## 1.5 新手术语表(遇到不认识的词回来查)

| 术语 | 白话解释 |
|---|---|
| chunk(文本块) | 文档切成的几百字小段,检索的最小单位 |
| embedding / 向量 | 一段文字的"语义指纹",一串数字;意思越近指纹越像 |
| 余弦相似度 | 两个指纹的相似程度,0~1,越大越像 |
| ANN(近似最近邻) | 在几十万指纹里快速找最像的那批,Milvus 数据库干这个 |
| BM25 | 经典关键词打分:词在这块出现多、在别的块少 → 分高 |
| 倒排索引 | "词 → 出现在哪些块"的速查表,Redis 里存着 |
| 知识图谱 | "实体—关系→实体"的网,每条关系记着证据块编号,存在 NebulaGraph |
| top-k | 最终交卷的块数,一般 10 |
| RRF(排名倒数融合) | 多份名单合并法:比名次不比分数,第 r 名贡献 1/(60+r) |
| 水合(hydrate) | 候选块从"只有编号和分数"变成"有全文"的过程(查 MySQL) |
| rerank / 交叉编码器 | 把"问题+候选全文"成对送进模型精读打分,比指纹比对准,但慢,所以只精读头部候选 |
| MMR | 去冗余重排:新选的块既要相关,又不能和已选的太重复 |
| 召回 / 精度 | 召回=该找到的找到了多少;精度=找回来的里有多少真有用 |
| MRR | 第一个正确答案排第几的倒数,衡量"正确答案排得靠不靠前" |

# 第二部分 · 技术细节:每一步的具体算法与理由

## 2.0 总览图

```
retrieve(query, top_k)
│
├─ ① 预处理(并行):HanLP 分词 ∥ 查询向量化(Qwen3-Embedding HTTP)
│                  意图检测(媒体/图片/图表编号) recall_top_k 计算
├─ ② 五路召回(并行 asyncio.Task):
│     Path-A 实体向量(Milvus entity)──┐
│     Path-B 关键词 BM25(Redis 倒排)──┤
│     Path-C chunk 向量(Milvus chunk)─┼─→ 各路产出 {chunk_id: 归一分}
│     Path-D 图扩展(Nebula 一跳/两跳)─┤
│     Path-E 媒体(仅媒体意图触发)──────┘
│     +双边查询分解(默认关):双边题切两侧,各自向量分侧召回并入向量通道
├─ ③ 证据准入:实体/媒体须被独立通道佐证;图通道佐证优先+有限新颖额度
├─ ④ 融合:分数感知 RRF(fusion v2)/ 纯排名 RRF(v1),keyword 准入门槛
├─ ⑤ 水合截断:融合分取前 N;fusion v2 先给向量通道保底 ceil(0.6·top_k) 席
├─ ⑥ 水合精排:MySQL 取全文 → 词法/子句/标题/来源逐项加分 → 排序去重
│     (图上下文 Nebula 拉取与本步并行)
├─ ⑦ 可选 Rerank:交叉编码 API,0.72·rerank + 0.28·融合分 + 证据加成
├─ ⑧ 向量保底:头部保证 ceil(0.6·top_k) 个最强向量候选在场
│     +分侧保底(查询分解开启时):每侧最佳稠密命中保证在场
├─ ⑨ 父窗口:高置信锚点扩相邻块;决定性父证据可升第 1 位
├─ ⑩ 多证据模式(默认关):文档多样性 → 两跳注入(1 席,受保护)→ 链提升
└─ ⑪ 输出 SelfRetrievalResult(chunks[:top_k] + entities + relationships + timings)
```

之后流水线层的 Stage-2(`ContentFilterManager`)按 `FilterMode` 再过滤/重排,见 §2.12。

## 2.1 入口与运行时基础设施

`SelfDirectRetrieverV2(session, kb_id, graph_profile, enable_rerank, fusion_v2, multi_evidence, ...)`

- **图配置档** `graph_profile`:`legacy → seed_only → routed → filtered → optimized → pathrag` 递进,生产用 `optimized`(只走类型化关系 + 证据准入)。档位控制 Path-D 的边过滤和准入严格度。
- **可见性过滤**(`RetrievalFilter`):所有 SQL/Milvus/Redis/Nebula 查询都带 `is_visible=true AND commit_status='committed'`。*为什么:摄取用两阶段提交(先暂存、后原子翻转可见),检索只看已提交版本,更新文档时用户永远不会看到半新半旧的库。*
- **进程级缓存与连接**(`_runtime`):
  - Milvus 单连接别名 + collection 加载状态缓存(TTL 300s)——省掉每次查询的元数据 RPC;
  - **Milvus 微批**:同键 `(collection, kb, expr, limit)` 的并发查询向量合并成一次批搜索,按事件循环隔离(weakref 键控);
  - Redis BM25 结果缓存(键 `(kb_code, tokens, top_k)`,512 条,TTL 可调);父窗口缓存(30s/512 条);Nebula 共享连接池;实体上下文进程缓存。
- *为什么这么多缓存:检索是读密集热路径,总预算 ~400ms,连接握手和元数据往返不省下来就全花在路上了。所有缓存键都含 kb_code 与参数,不跨库跨版本污染。*

## 2.2 预处理(①)

1. **分词 ∥ 向量化并行**:HanLP(`msra_crf_electra_base`)分词走 `asyncio.to_thread` + 进程锁(HanLP 非线程安全);向量化调 `embed_texts`(Qwen3-Embedding-8B)。`asyncio.gather` 重叠两者。*为什么:两件事互不依赖,串行白付一份延迟;Phase 3 实测暖态总延迟 461→432ms。*
2. **意图检测**(纯规则,不调模型):`_is_media_query/_is_image_query` 判断是否图表问题;`_media_refs/_figure_refs` 抽"图 3-2 / Table 5"式编号。*为什么用规则:意图只影响加分和媒体路径开关,规则零成本零延迟,错了也只是少个加分项。*
3. **召回窗口**:`recall_top_k = top_k`(rerank 关)或 `min(top_k×2, 24)`(rerank 开)。*为什么:重排器比粗排准,给它更宽的入场名单才有翻盘空间;24 上限控住 API 成本。*
4. **种子参数**:`seed_weight_mode∈{vector,bm25,hybrid}`(默认 bm25)、`seed_vector_ratio`(默认 0.7)、`seed_keyword_limit`(默认 16)。

## 2.3 五路召回(②)

各路是独立的 `asyncio.Task`(带分项计时);任何一路抛异常都降级为空结果记 debug 日志。*为什么:一个外部依赖(Redis/Milvus/Nebula)抖动不该炸掉整个检索,其余通道还能兜底。*

### Path-A 实体向量 `_milvus_entity_recall`

- 查询向量搜 Milvus 实体集合,`limit = max(top_k×4, top_k)`;
- 实体带摄取时落盘的 `chunk_ids`(它在哪些块里出现),实体相似分投影到块:`chunk_score = max(块所属实体的相似分)`;
- 同时产出**种子实体**列表(给 Path-D 当爬图起点)和证据(`vector_scores`、`chunks_by_entity`)。
- *为什么降权保留:路径构成统计发现实体通道在全部数据集上"独占金标 = 0"——它找到的正确答案全部同时被向量/关键词通道找到,而它独有的贡献 94% 是噪声。它的真实价值是供种,不是供块。fusion v2 里它的融合权重从 0.35 降到 0.15,块分数还要过佐证审查(§2.4)。*

### Path-B 关键词 BM25 `_redis_chunk_scores`

- 摄取用 `tokenize_mixed_text`(HanLP + 英数混排规则)建 Redis 倒排 `{kb_code}:v2:bm25:*`;检索传**同一分词器**的 token。*为什么强调一致:建索引和查索引的切词不一致,"XJ-3000"可能被切成两半就永远查不到。*
- 三级降级:倒排 BM25(默认)→ corpus HSCAN 词法扫描(上限 5000 块,仅图检索模式)→ MySQL `ILIKE`(token 前 8 个,`limit=max(top_k×30,300)`)。*为什么:倒排最快;扫描保证倒排缺失时还有词法通道;MySQL 是最后兜底。*

### Path-C chunk 向量 `_milvus_chunk_scores`(主力)

- 查询向量搜 chunk 集合,`limit = top_k × 3`(env `SELF_RETRIEVAL_GRAPH_CANDIDATE_MULTIPLIER`,多库快查场景 ×2);
- 命中行的 payload 直接缓存成 `SelfIngestChunk`(`_milvus_chunk_row_cache`),水合时少查一次 MySQL;image 块和超长(≥8192 字符)块不缓存——MySQL 里的元数据更全。
- *为什么是主力:所有数据集上金标覆盖最高的单通道。消融方案 `vector_only` 就是只留它——一切优化的非劣基线:图检索加进来不能比纯向量差,这是第一优先级验收线(已达成,见第三部分)。*

### Path-D 图扩展 `_nebula_graph_scores`

- 种子:`seed_entity_ids[:min(top_k,5)]`(融合排序后的头部,见 §2.4);
- nGQL(一跳):

```
GO FROM <seeds> OVER relation_v2
WHERE properties(edge).is_visible == true
  AND properties(edge).status == "active"
  AND properties(edge).relation_type != "co_occurs"      -- 优化档:只走类型化关系
YIELD 边属性 + 两端实体属性 | LIMIT max(top_k×8, 30)
```

- 记分:边的 `evidence_chunk_ids`(摄取时记录的"这条关系是从哪些块里抽出来的")记满边权;尾端实体的 `chunk_ids`(邻居块)记 `weight×0.35`。*为什么折扣:邻居块只是"和这个实体有关",不是"陈述了这条关系"——不打折图通道会灌满候选集。为什么排除共现边:`co_occurs`(俩实体出现在同一块)是最弱的关系,曾是主要噪声源。*
- **两跳**(仅多证据模式):`GO 2 STEPS ... ORDER BY weight DESC | LIMIT limit×3`,**两跳行不进融合**(`_hop>1` 跳过记分),只供 §2.10 的末端注入。*为什么:实验把两跳边混进融合,图通道被稀释、佐证候选被挤出,指标回退——"前端拓宽"输给了"末端定向注入"。*
- 关系行按 `(src,dst,relation_id)` 去重并缓存,后续拉关系上下文时复用,不二次查图。
- *代价教训:nehard20q 上图扩展 hit 保持 0.90 但 MRR 0.541→0.248——图带来的"相关非金标"块挤占名次。这是降权、准入和 P0 重排评测的共同动因。*

### Path-E 媒体 `_milvus_media_scores` + `_media_scores`

- 仅媒体意图触发:媒体向量(`embed_media_texts` 独立嵌入,`limit=max(top_k×8,top_k)`)+ Redis BM25 合并;
- MySQL 媒体 `LIKE` 只在带精确编号(`media_refs`)时兜底。*为什么:没编号的自然语言图片问题退化成全媒体表扫描,代价不可控。*
- 非图片意图且无编号时,媒体分须被向量/关键词**佐证**才进融合。

## 2.4 种子融合与证据准入(③)

**种子实体融合** `_fuse_entity_seed_ids`——图爬得好不好,起点排序说了算:

```
lexical(entity) = max(BM25_chunk_score  for chunk in entity.chunk_ids)   # 实体的词法分=其证据块的最高 BM25 分
fused(entity)   = 0.7 · norm(vector_sim) + 0.3 · norm(lexical)           # 各通道 max 归一后加权
```

`bm25` 模式(默认)不调 Milvus 实体搜索,改走 Redis 反向索引 `chunk:{id}:entity_ids` 从 BM25 命中块反解实体——零向量开销的图供种。

**证据准入**(routed/filtered/optimized/pathrag 档):

- `_corroborated_scores(primary, *independent)`:实体通道的块**必须**同时被向量/关键词/媒体任一通道命中才保留。*一句话:提到主角 ≠ 回答问题,独立旁证是入场券。*
- `_admit_graph_scores`:图通道分两桶——有旁证的全收;**图独有**的按分取前 `max(2, min(5, (top_k+2)//3))` 个(top_k=10 → 4 个)。*为什么留独有额度:多跳关键证据可能只有图能到;限额防图垄断。*

## 2.5 融合(④,`_merge_component_scores`)

**为什么用 RRF 而不是把分数加起来**:五路分数(余弦 0.3-0.9、BM25 0-10+、边权 0-1)量纲不同,直接加权 = 让量纲投票。RRF 只比名次:通道内第 r 名贡献 `w/(60+r)`,多通道命中累加,最后整体 max 归一。60 是平滑常数,让第 1 名和第 5 名差距别太悬殊。

通道权重(`rrf_weights`):

| 通道 | 常规 | 图片意图 | fusion v2 |
|---|---|---|---|
| vector | 1.0 | 0.5 | 1.0 |
| keyword | 0.75 | 1.0 | 0.75 |
| entity | 0.35 | 0.15 | **0.15** |
| graph | 0.35 | 0.15 | 0.35 |
| media | 0.75 | 2.0 | 0.6 |

**fusion v2**(`self_fusion_v2_enabled`,**2026-08-13 起默认开**;此前 5 集验收两胜两平一噪声内略退、39 题集 +1.7,且默认开的查询分解只在 v2 上验证过——qd+v1 组合同会话实测头部金标 71 vs 75,v1 缺水合前向量保底)在此之上加三件事:

1. **分数感知 RRF**——名次相同,分数成色不同,贡献也应不同:

```
contribution = w · (0.5 + 0.5 · score/channel_max) / (60 + rank)
```

通道内垫底分(score≈0)只拿半份贡献。*解决的问题:弱通道第 1 名与强通道第 1 名"一票等值",单通道噪声稀释多通道佐证的强命中。*

2. **keyword 准入门槛** `_gate_keyword_scores`(`min_norm=0.25`):BM25 归一分 <0.25 且无旁证的不进融合。*证据:keyword 独占槽位噪声率 48-94%。*
3. **entity 权重 0.35→0.15**。*证据:独占金标为 0。*

## 2.6 水合截断与向量保底(⑤,`_select_hydration_candidates`)

融合池按分数截断到 `_hydrate_candidate_limit(top_k)` 才去 MySQL 取全文。**这是旧算法最致命的丢失点**:强向量候选被融合名次压出截断线,后面的精排再好也救不回(跨文档诊断:3 个金标死在这一刀)。

fusion v2 的**向量保底前移**:截断前先保留向量通道前 `ceil(top_k×0.6)` 名(须在融合池内),剩余额度按融合分填。*直觉:向量侦探是最可靠的一位,他强烈推荐的前几名必须进入面试环节,不许被合议庭的名次算法拦在门外。*

## 2.7 水合与逐块精排(⑥,`_row_to_retrieved_chunk`)

MySQL 取全文(Milvus payload 缓存命中的免查),**与图上下文拉取并行**(一个读 MySQL 一个读 Nebula,重叠后 graph_io 计时段 58→14ms)。

每块基础分 = 融合分,再逐项加减(全部规则):

| 信号 | 计算方法 | 加分 |
|---|---|---|
| 词法密度 `_lexical_score` | `0.85·(命中token/总token) + 0.15·(1/√(len/800))`(长文惩罚:同样命中 5 个词,300 字的块比 3000 字的更"浓") | 兜底 keyword_score |
| 双高共振 | 词法与向量同时很高(kw≥0.95 且 vec≥0.90 / kw≥0.80 且 vec≥0.85) | +0.18 / +0.08 |
| 标题上下文 `_title_context_score` | 章节路径末 4 级 + 媒体标题 + 正文前 6 行短行,做词法分;查询整串出现在标题 +1.0(压缩匹配 +0.8) | ≥1.20:+0.30;≥0.85:+0.18;≥0.55:+0.08 |
| 来源文档名 `_source_doc_score` | 文件名/路径词法分;文件名主干被查询包含 +1.0(用户点名了这份文档) | ≥1.20:+0.22;≥0.75:+0.12;≥0.45:+0.05 |
| 图表编号命中 | `figure_refs` 出现在正文 / extra 元数据精确匹配 | +0.25 / +0.45 |
| 媒体分 | `media_score ×`(图片意图 0.40,否则 0.22) | 按比例 |
| 块类型权重 | `{text:1.0, image:1.2, table:1.3, formula:1.1}`(可配);非图片意图时 image 封顶 1.0 | 乘法 |

**图片意图分支**:加 `子句覆盖分×1.2`(查询按标点拆子句,各子句 token 覆盖率的**调和平均**——调和平均对"某一子句是 0"极其敏感,专治只命中半句话的偏科块);image 块 +0.55 再按 kw/vec/来源补强;text/table 打 0.62-0.72 折。*为什么:图片题的正确证据是媒体块,但 OCR 文本块词法上常"更像",不压制会反客为主。*

**内容渲染** `_row_content_for_model_context`:table 块过 `_focus_table_evidence`(保留表头+查询命中行——一张 200 行的表只给模型看相关的几行);检测到 OCR 章节标题串则前置大纲;image 块渲染成结构化 `Image Content Analysis`(路径/标题/OCR/前后文/视觉摘要)。

**排序去重**:按 `(-score, file_name, chunk_index)` 排;`_dedupe_scored_chunks` 按 Image Path/媒体编号去重,图片意图再做描述二元组签名 Jaccard≥0.82 近重复过滤;非图片意图时图片块限流 `max(1, min(4, top_k//2))`。

## 2.8 可选二阶段 Rerank(⑦,`_rerank_scored_chunks`)

前 24 个候选(每块截 6000 字符,带来源前缀)成对送交叉编码 rerank API:

```
score = 0.72·norm(rerank) + 0.28·norm(融合分)
      + min((召回路径数−1)·0.02, 0.06)        # 多路佐证加成
      + 0.04(图路径与词法/向量路径同时命中)
```

API 失败静默保持原序。*为什么保留 28% 融合分:交叉编码更准但会犯"语义相近非证据"的错,融合分和证据加成兜底。为什么只精读 24 个:交叉编码逐对精读,量大延迟爆炸——粗排负责"别漏",精读负责"排准"。*

**2026-08-12 消融裁决(负面结果):当前 rerank 模型有害,保持默认关。** nehard20q 上 MRR 0.321→0.144、CP 0.574→0.443;跨文档集 hit 0.90→0.70、MRR 0.382→0.163——重排器把金标从头部往外推,其相关性判断与学科领域问题不匹配。Stage-2 FULL 全链在 hydro53q 上 CP −9 分的元凶也是链内的这一步 Rerank(与本消融独立印证)。换用领域适配的重排模型前,`self_rerank_enabled` 不应开启。

## 2.9 向量保底与父窗口(⑧⑨)

**最终向量保底** `_ensure_vector_floor`:精排/重排后,top_k 头部再保证向量前 `ceil(0.6·top_k)` 名在场(从尾部换出非保底成员,再按原相对序回排)。与 §2.6 呼应:一个保"进得了面试",一个保"坐得进决赛圈"。

**父窗口扩展** `_expand_parent_context_windows`:

- **高置信文档**:头部同文档命中 ≥2 次;或单锚点(排名≤上限、分数≥最佳×比例、独立路径数达标或为结构化媒体块);
- 锚点取 `chunk_index ± radius` 相邻块(媒体锚点用更大 radius;30s 缓存),按查询相关性选行、限 `max_chars` 渲染,锚点标记 `path_f_parent_window` 并记 `context_chunk_ids`;
- **决定性父证据提升** `_promote_stronger_parent_evidence`:至多一个带窗口的候选升到第 1,条件是其长度归一化结构化支持分超当前第 1 一个边际。*刻意窄于全局重排:只动"证据决定性强于现任第一"的场景。*
- *为什么窗口不加大 chunk:答案常跨相邻段。全库加大块尺寸稀释向量指纹、抬高存储;窗口只为高置信锚点按需付 token。*

## 2.10 双边查询分解(`self_query_decomposition_enabled`,默认关)

**针对的问题**:显式双边题("在一项研究中 X;另一项研究中 Y。请结合两者……")用**一个**查询向量检索,向量是两侧语义的平均——弱侧文档常年浮不上来。39 题基线的实锤:任意金标文档命中 0.95+,**全部金标文档命中只有 0.49-0.54**。

机制(两段式):

1. **分侧召回**(召回阶段):高精度规则切分双边题(`_split_bilateral_query`)——强标记(另一项/另一边/另一体系/;同时)直接切;裸"而"衔接仅当题面带合并意图词(一侧/两端/结合/连接/串联)才切,防单跳题误伤。**侧向量搭载主查询向量化的同一次批量 embed 调用**(零额外往返),两路侧检索与主召回并行(Milvus 微批合并),结果以**各自真实相似度** max-merge 进向量通道——B 侧强命中不再被全题平均分埋没。实测 39 题触发 36 题;非跨文档集 174 题仅触发 3 题且均为真多侧面问题,零有害误伤。
2. **分侧水合配额**(截断阶段):每侧在水合保留 `ceil(0.3·top_k)` 个自己的最强稠密命中——合并向量保底按绝对相似度排序,弱侧的 0.55-0.6 余弦会把保留席全部输给强侧的 0.65+。
3. **分侧保底**(头部阶段,`_ensure_side_representation`):排序后头部若缺某一侧的最佳稠密命中,从尾部换入(仅动成员资格、保持相对序,与向量保底同款手法)。

**同会话 A/B(39 题,144 金标)**:完全未召回 50→31(**−38%**),in_topk 61→75(**+23%**)——单项收益最大的机制。

**RAGAS 终审(本地判分,39 题)**:综合分 0.658→**0.681**(全方案最高)、CR +6.2、AC +4.3、Any Hit 0.897→0.974、文档覆盖 0.718→**0.833**、**全文档命中 0.487→0.692(+20.5pt)**。代价:CP −9.8(更宽召回带入部分噪声,被 CR/F/AC 增益覆盖)。

**延迟(2026-08-13 已修复)**:首版侧向量化串行于主向量化之后,触发题 +~380ms;并行化后(同批 embed + 侧检索与主召回重叠)实测触发题暖态 **420-424ms ≈ 非分解基线**,查询分解的延迟代价归零。

*为什么不用 LLM 分解:双边题有强句式 signature,规则切分免费且可控;自由形态多跳题(无显式双边结构)留给后续 LLM 分解升级,插口(`decomposed_sides`)已就位。*

## 2.11 多证据模式(`self_multi_evidence_enabled`,默认关)

**针对的题型**:"A 文档的发现 + B 文档的机理,合起来才能回答"。诊断:此类题 36% 金标任何路径都召不回——路径 `种子→桥实体→伙伴边` 的第二条边,一跳结构性够不着。

执行顺序:

1. **文档多样性上限** `_apply_doc_diversity`(max_share=0.8):单文档头部最多 `ceil(0.8·top_k)` 席,超出**顺延不丢弃**。*为什么不是 0.7:0.7 曾把金标(恰好是主导文档第 7 块)换出——集中度约束对"金标本身集中"的题是双刃剑,0.8 是实测平衡点。*
2. **两跳伙伴证据注入** `_inject_two_hop_partner_evidence`(预算 **1 席**):
   - 锚:头部块(含窗口覆盖)命中的边的两端实体,锚权=边权;
   - 候选:与锚共享实体的两跳边证据块,链分=`边权×max(锚权,0.1)`,取前 16 水合;
   - **余弦过滤**:候选内容批量 embed 与查询向量算余弦,< `0.52`(env 可调)剔除。*标定:探针实测金标伙伴 0.57-0.59、可弃尾 <0.53。*
   - **词面主排序、余弦次之、链分再次**。*关键发现:同主题非金标邻居的余弦(0.67)反而高于金标(0.58)——同论文相邻块都贴合主题,纯余弦会选错;词面重叠才是金标最强区分信号;零词面的远文档场景由余弦自然接管。*
   - **受害者选择**:从尾向头找核心通道(a/b/c/e)≤1 的头部块换出;≥2 核心通道的块与已注入块(`path_d_graph_2hop` 标记)**受保护**。*后者修复实测 bug:注入的金标被下一步提升当受害者换掉——注入和提升互相蚕食。*
   - *为什么 1 席:注入第 1 名(词面主导)通常可靠;第 2 名要在同边兄弟块间靠余弦决胜——已证明不可分,预算给提升更值。*
3. **证据链提升** `_promote_graph_evidence_chain`(预算 `2−已注入`):已水合、其证据边与头部证据边共享实体(链补全)的尾部块提升进头部,同分优先新文档。

**裁决**:证据 hit 0.80→0.90、覆盖 0.392→0.417、MRR 0.382→0.392;综合分持平(n=10 判分噪声 ±0.04);代价是两跳遍历延迟。**默认关,跨文档密集型库选配。**

## 2.12 Stage-2 过滤(流水线层)

Stage-1 结果按 KB 配置的 `FilterMode` 走 `PerKBContentFilter.filter_content`(实例按 KB 缓存):

| FilterMode | 流程 |
|---|---|
| `RAW` | 原样透传 |
| `MMR_ONLY` | 仅 MMR 去冗余重排 |
| `MMR_TIME_AWARE` | 时间感知加权 → MMR |
| `RERANK` / `RERANK_MMR` | 跳过 PPR 纯 Rerank(权重 100%)(→MMR) |
| `PPR_ONLY` / `PPR_MMR` | PPR 图过滤(→MMR) |
| `PPR_RERANK` / `FULL` | PPR → Rerank 融合(→Time-Aware→MMR) |

- **MMR**:贪心选择 `λ·相关性 − (1−λ)·与已选最大相似度`;**保护规则**:`_ppr_score≥0.08` 或 `_rerank_score≥0.78` 或 `_fused_score≥0.62` 的块免疫淘汰。*去冗余不牺牲强证据。*
- **PPR**(Personalized PageRank):以种子实体为个性化向量在图上迭代,按到达概率重排。
- **矩阵评测(hydro53q,本地判分,216 次零错误)**:`RAW 0.7652 ≈ MMR_ONLY 0.7651 > FULL(PPR) 0.7609 > PPR 全链 0.7464(CP −9 分)`。*结论:PPR 按图中心性(实体流行度)重排,与"这个查询要什么"弱相关;自研库的正确默认是轻量档。第二数据集复验通过后切生产默认(P0 进行中)。*

## 2.13 回退、输出与延迟

- **回退**:召回全空 → `_fallback_chunks` 按可见时间取最近块打词法分,永不空手。
- **输出**:`SelfRetrievalResult{chunks[:top_k], entities, relationships, query_embedding, timings}`;实体/关系供证据链展示与上下文装配;timings 每阶段毫秒级打点(诊断靠它)。
- **延迟画像**(暖态实测):tokenize ≈0(并行隐藏)/ embed 70-140ms / recall 160-210ms / graph_io ≈14ms(与水合重叠)/ hydrate 30-100ms / **总计 ≈430ms**。开 rerank +一次 API 往返;开多证据 +两跳遍历与一次批量 embed。
- **hybrid 模式**:`_stage1_hybrid_direct` 并行跑 legacy 与自研后合并(独立会话/连接栈)——迁移期兼容。

*摄取侧接线(2026-08-13 深夜)*:`self_synth_query_ingest_enabled` 开启后,新文档在提交阶段自动生成并写入合成查询,无需事后回填。它挂在 CommitWriter 的**外部旁路阶段**(与 milvus_entities/redis/nebula 并列):分块向量已经落库后才执行,任何失败只记 `external_failures=synth_queries`,绝不让摄取失败。三条正确性约束:①只处理 ≥80 字的文本块;②因 `chunk_id` 随 `commit_version` 变化,写入前按 `doc_id` 清空旧行(否则重摄取会留下永久孤儿——侧集合没有可见性字段);③文档删除时在 `delete_service` 同步清理侧集合。生成 prompt 与宽容 JSON 解析已抽到 `synth_query_index.py` 与回填工具共用。**存量库仍需跑一次回填**;两个开关独立,可先只开检索(用回填数据)或只开摄取(为将来积累)。

**生产接线·深度检索成为用户选项(2026-08-13)**:边界裁判已完成两层接线——
1. **全局开关**:`backend/rag/retriever_v2/boundary_judge.py` 生产模块,`SELF_BOUNDARY_JUDGE_ENABLED=true` 时对所有自研检索生效(默认关);
2. **每请求开关(前端可选)**:四套聊天前端(主/CSH/FMCA/audit)输入框新增「深检」按钮(联网按钮旁),开启后该次提问携带 `deep_retrieval: true` 字段,链路 `AgentRuntimeQueryRequest → AgentRequest → AgentRuntimeContext → multi_kb_search 工具 → retrieve_context → SelfDirectRetrieverV2(boundary_judge=True)`,只对这一次问答强制启用全文裁判;不开则完全走原路径,零开销。请求级缓存键包含该标志(深检结果不会误用于普通请求),远程知识库服务转发(`InternalMultiKBSearchRequest.deep_retrieval`)同步支持。用户语义:**勾选=用约 1 秒换更准的知识库检索**(跨文档/科研问答场景实测综合分 +3.2pt、全文档命中 +5.2pt)。
