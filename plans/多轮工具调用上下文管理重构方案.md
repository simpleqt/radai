# 多轮工具调用上下文管理重构方案

> **文档状态**：⚠️ **部分实现**（2026-05 / 文档同步 2026-05-31）  
> **已落地**（对照代码）：  
> - `ContextPruningMiddleware` — 状态提升 `retrieved_evidence` / `loaded_skills` + JIT 临时 SystemMessage（`context_pruning.py`）  
> - `SummarizationMiddleware` — 默认约 20 轮触发（FullFeatureAgent 注入）  
> - `LoopDetectionMiddleware`、`ToolGuardrailMiddleware`  
> **未完整落地**：统一 Tool Context Archive、按 `llm_models.max_input_tokens` 动态预算、专用子智能体总结器压缩管线等（下文多为目标设计）。  
> **排障**：见 [agent_engine_module.md](../docs/docs_backend/agent_engine_module.md) §常见问题  
> **相关**：[下一步开发需求.md](../docs/下一步开发需求.md) P0/P1

## 1. 背景与目标

当前 `NEFullFeatureAgent` 与 `CSHFullFeatureAgent` 已支持：

- 多轮会话
- 多工具调用
- 深度研究模式下的子智能体委派
- `SummarizationMiddleware` 历史摘要
- `ContextPruningMiddleware` 工具结果裁剪

但在真实多轮、多工具、多 skill 叠加场景下，仍然存在“工具上下文越积越大，最终直接把模型上下文窗口打满并中断”的问题。  
本方案的目标不是修改现有“对话历史管理语义”，而是**重构多轮工具调用上下文管理**，让系统在未来 skill 数量继续增长时，仍然能稳定控制上下文。

本次方案明确边界：

- 不修改现有用户对话历史的业务语义与展示逻辑
- 不要求每个 tool/skill 单独适配上下文压缩逻辑
- 通过统一中间层完成工具上下文采集、压缩、归档、回放
- 通过 MySQL 中 `llm_models.max_input_tokens` 动态获取上下文预算
- 在必要时引入“子智能体总结器”作为压缩手段，但不把它设计成唯一方案

## 2. 现状分析

## 2.1 现有主链路

当前主链路大致如下：

1. API 路由根据 `thread_id` 构建内部线程键。
2. 通过全局 `checkpointer` 读取/续写 LangGraph checkpoint。
3. `NEFullFeatureAgent` / `CSHFullFeatureAgent` 构建统一主图。
4. 图执行时依次经过：
   - `SummarizationMiddleware`
   - `LoopDetectionMiddleware`
   - `ClarificationMiddleware`
   - 自定义 `ContextPruningMiddleware`
5. 图状态通过 `ThreadState` 持久化，跨轮复用。

与本次问题直接相关的代码位置：

- `backend/custom/agents/ne_full_feature_agent.py`
- `backend/custom/agents/csh_full_feature_agent.py`
- `backend/core/agents/middlewares/context_pruning.py`
- `backend/core/agents/state.py`
- `backend/core/models/context_limits.py`
- `backend/core/models/factory.py`
- `backend/custom/api/v2/agent.py`
- `backend/custom/api/v2/csh_agent.py`

## 2.2 当前已具备的上下文能力

### 1）模型上下文上限已经可以从 MySQL 获取

当前系统并不是纯静态配置：

- `backend/db/models/llm_model.py` 中已有 `max_input_tokens`
- `backend/core/models/context_limits.py` 中已有 `resolve_max_input_tokens()`
- `backend/core/models/factory.py` 在创建模型时会将 `max_input_tokens` 注入 `profile.max_input_tokens`

这意味着：  
**“按模型上下文窗口动态做预算控制”这一基础能力已经存在，不需要从零开始。**

### 2）当前已经有一次工具结果裁剪

`ContextPruningMiddleware` 已尝试做两类事情：

- 把 `read_local_skill_file` 的输出提升为 `loaded_skills`
- 把 `multi_kb_search` 的输出提升为 `retrieved_evidence`
- 对超长 `ToolMessage` 做截断替换
- 在模型调用前，把 `loaded_skills` / `retrieved_evidence` JIT 拼回 `SystemMessage`

### 3）当前已经有历史摘要

两个全功能智能体都启用了：

- `SummarizationMiddleware(trigger=[("messages", 20)], keep=("messages", 20))`

说明当前系统已有“历史消息摘要”的基础能力，但它偏向**消息历史数量**，不等同于**工具上下文预算控制**。

### 4）当前已经存在子智能体基础设施

`backend/core/tools/task_tool.py` 已支持：

- 本地子智能体运行
- 子智能体独立 graph
- 独立 `recursion_limit`
- 在运行过程输出阶段性事件

所以“通过启动子智能体做总结”在架构上是可落地的，不需要重新发明执行框架。

## 3. 当前方案存在的核心问题

## 3.1 问题一：当前的压缩对象不对，压缩了消息表面，没真正控制注入预算

当前 `ContextPruningMiddleware` 虽然把部分 `ToolMessage` 替换成短文本，但同时又会在模型调用前将：

- `loaded_skills`
- `retrieved_evidence`

重新拼进 `SystemMessage`。  
这意味着：

- 表面上历史消息变短了
- 实际送给模型的输入不一定变短
- 一旦 `loaded_skills` 和 `retrieved_evidence` 越积越多，最终还是会顶满上下文

也就是说，当前更像是“消息形态转换”，不是“真正的预算治理”。

## 3.2 问题二：JIT 组装结果存在重复膨胀风险

当前 `ContextPruningMiddleware._patch_state()` 中：

- 先 `_process_state_elevation(state)`
- 再 `_assemble_jit_context(messages, state)`
- 然后 `state["messages"] = patched`

风险在于：

- JIT 拼装后的 `SystemMessage` 可能再次进入状态
- 下次模型调用时又基于已拼装消息继续拼装
- 动态上下文可能发生重复追加

如果这一行为被 checkpoint 持久化，多轮后会形成隐性膨胀。  
这类问题比单次超长更难排查，因为它表现为“会话越久越容易突然爆”。

## 3.3 问题三：`retrieved_evidence` 是只增不减的全量累积

当前 `ThreadState` 中：

- `loaded_skills: dict[str, str]`
- `retrieved_evidence: list[str]`

其合并逻辑本质上是追加或并集，没有 TTL、没有分层、没有预算淘汰。  
后果是：

- 同一轮多次 `multi_kb_search` 会不断累积
- 多轮会话会持续累积历史证据块
- 即使历史证据已失效，也会在后续 JIT 中继续参与组装

这不适合高频工具调用和未来大量 skills 场景。

## 3.4 问题四：当前上下文管理没有区分“对话上下文”和“工具工作上下文”

当前状态里，工具输出被放进与对话同一条线程态里，但没有进一步分层：

- 用户真正需要保留的对话语义
- 本轮推理临时使用的工作证据
- tool 执行过程中的原始输出
- skill 文件原文
- 子智能体过程性结果

这些内容混在一起后，系统只能做粗粒度摘要，做不到精确预算治理。

## 3.5 问题五：当前摘要触发规则太静态，不基于模型上下文上限

当前 `SummarizationMiddleware` 触发条件是：

- `messages >= 20`

这对于不同模型是不合理的：

- 32K 模型和 128K 模型不能用同一个阈值
- 长工具输出场景下，即使消息条数很少，也可能早已超预算
- 短消息场景下，20 条可能仍然很安全

所以应该从“消息条数驱动”改为“预算驱动”。

## 3.6 问题六：子智能体存在，但没有承担父智能体的上下文减负职责

当前子智能体主要用于任务委派，不用于：

- 汇总工具链中间结果
- 把多次检索/多 skill 输出整理成压缩摘要
- 将压缩后的结果回灌父智能体工作记忆

因此子智能体能力还没有真正成为“上下文控制器”的一部分。

## 3.7 问题七：未来新增很多 skills 时，逐个 tool 改造不可维护

当前 `ContextPruningMiddleware` 针对：

- `read_local_skill_file`
- `multi_kb_search`

做了定制逻辑。  
如果后续增加很多 skill/tool，例如：

- 学术搜索
- 结构化数据库查询
- 文档解析
- 图像理解
- 代码分析
- 报告生成

若仍采用“遇到一个工具就定制一段规则”，维护成本会持续失控。

## 4. 根因判断

当前问题的根因不是“缺少某一个摘要器”，而是**没有建立统一的工具上下文分层架构**：

- 没有统一的预算管理器
- 没有统一的工具输出归档层
- 没有统一的压缩触发机制
- 没有统一的 JIT 装配预算裁决器
- 没有把子智能体总结纳入标准流程

所以我对“是否通过启动子智能体进行总结来解决”的判断是：

**是，但只能作为整体方案中的一个压缩执行器，不能作为唯一方案。**

正确方向应该是：

1. 用预算管理器判断是否需要压缩
2. 用统一的工具上下文归档层接住所有重型输出
3. 由压缩执行器选择：
   - 规则压缩
   - 模板压缩
   - 子智能体总结压缩
4. 最终由上下文装配器按预算将必要信息回灌给主模型

## 5. 目标架构

## 5.1 架构原则

### 原则一：主对话历史不动，工具工作上下文重做

明确拆分为两条上下文线：

- `Conversation Context`
  - 用户问题
  - 助手最终回答
  - 少量必要澄清
  - 保持现有会话逻辑不变

- `Execution Context`
  - tool 原始输出
  - skill 原文
  - RAG 证据块
  - 子智能体阶段结果
  - 中间推理工作集

本次只重构 `Execution Context`。

### 原则二：先归档，后摘要，最后按预算回放

统一流程应为：

1. 工具输出先进入归档层，不直接永久留在 messages 中
2. 根据预算决定是否压缩
3. 压缩结果写入结构化工作记忆
4. 模型调用前只按预算回放“必要摘要”

### 原则三：预算驱动，不再使用固定条数驱动

所有压缩和注入动作都应围绕：

- `llm_models.max_input_tokens`
- 系统提示占用
- 对话消息占用
- 预留输出 token
- 预留工具工作集 token

来决策。

### 原则四：对 tool/skill 零侵入或低侵入

新增 skill 时，默认不需要修改该 tool 本身。  
统一由“工具输出采集器 + 上下文治理层”接管。

### 原则五：多级压缩，而不是一次性粗暴截断

压缩应分层：

- 原始输出
- 结构化提取
- 工作摘要
- 会话级阶段摘要

只有在确实超预算时，才逐级降维。

---

## 5.2 目标分层

建议新增以下逻辑层：

### A. Context Budget Manager

职责：

- 从 MySQL 读取模型 `max_input_tokens`
- 计算当前轮可用输入预算
- 划分预算桶
- 决定是否触发压缩/总结/淘汰

建议预算分桶：

- `system_prompt_budget`
- `conversation_budget`
- `execution_budget`
- `tool_result_budget`
- `summary_budget`
- `reserved_output_budget`

### B. Execution Context Ledger

统一承接工具输出，不让 tool 原始大文本直接长期堆入 `messages`。

建议记录单元：

```json
{
  "entry_id": "uuid",
  "source_type": "tool|skill|subagent|rag",
  "source_name": "multi_kb_search",
  "turn_id": "turn-uuid",
  "tool_call_id": "call-xxx",
  "created_at": 1710000000,
  "raw_ref": "checkpoint://...",
  "raw_text": "...",
  "size_chars": 12000,
  "size_tokens_est": 3600,
  "status": "raw|compressed|archived|dropped",
  "summary_refs": ["summary-1"],
  "tags": ["evidence", "skill", "transient"]
}
```

### C. Context Compression Orchestrator

统一判断何时压缩，以及采用何种压缩方式。

触发条件建议：

- 当前轮工具累计输出超过 `execution_budget`
- 单次工具输出超过单条阈值
- 同轮连续 tool burst 超过阈值
- 下一次模型调用前预计会超 `max_input_tokens`

### D. Compression Executors

压缩执行器采用多种策略：

1. `RuleBasedCompressor`
   - 去掉 JSON 冗余字段
   - 去掉 HTML/日志/重复片段
   - 提取前 N 条关键项

2. `TemplateCompressor`
   - 针对检索证据、skill 定义、表格结果，抽取固定字段

3. `SubagentSummarizer`
   - 当规则压缩后仍超预算时，启动子智能体做语义总结

### E. Context Assembler

在模型调用前，不直接拿全部 ledger 内容，而是：

1. 先装载对话历史
2. 再评估剩余预算
3. 只选择当前任务最相关的 execution summaries
4. 若仍超预算，再做二次压缩

### F. Tool Context Policy Registry

不是为每个 tool 写逻辑，而是为**工具类型**写策略。

例如：

- `search_like`
- `skill_like`
- `file_parse_like`
- `tabular_like`
- `report_like`
- `generic_large_text`

这样新增工具时，只需声明类型或由规则自动识别，不必重写中间件。

## 6. 子智能体总结在整体方案中的定位

## 6.1 结论

子智能体总结应该采用，但只在以下场景触发：

- 某类工具输出过大，模板压缩后仍过长
- 同一轮产生多个相关工具结果，需要跨结果归纳
- 深度研究模式中，多个子任务结果需要汇总成父智能体可消费的摘要
- 多个 skills 共同参与时，需要形成“本轮工作记忆摘要”

## 6.2 不建议的方式

不建议把所有工具结果都直接交给子智能体总结，原因：

- 成本高
- 时延大
- 额外增加一次模型调用链路
- 若没有预算门控，自己也会成为新的上下文膨胀源

## 6.3 建议的正确方式

采用“三级压缩链”：

1. **轻量规则压缩**
   - 低成本
   - 先做结构清洗

2. **结构化模板压缩**
   - 保留关键信息槽位
   - 适合检索结果、skill 文件、工具返回

3. **子智能体语义总结**
   - 仅在前两级后仍超预算时触发
   - 输出受控、短小、结构化

## 6.4 子智能体总结器的输入输出设计

输入不要直接给全部对话历史，只给：

- 当前轮用户目标
- 本轮相关工具结果摘要
- 必要的上一阶段工作摘要
- 明确的总结格式约束

输出建议固定为：

```json
{
  "task_goal": "当前子任务目标",
  "key_findings": ["..."],
  "evidence_points": ["..."],
  "open_questions": ["..."],
  "recommended_next_actions": ["..."],
  "citations": ["entry-1", "entry-2"]
}
```

这样才能稳定用于父智能体继续推理。

## 7. 基于 MySQL 上下文大小的预算控制设计

## 7.1 数据来源

当前已存在：

- `llm_models.max_input_tokens`
- `context_limits.resolve_max_input_tokens()`

因此建议新增统一预算解析入口，例如：

- `backend/core/context/budgeting.py`

示意逻辑：

```python
model_limit = resolve_max_input_tokens(model_name=current_model_name)
reserved_output = min(max_output_tokens, int(model_limit * 0.2))
safe_input_budget = model_limit - reserved_output
```

## 7.2 建议预算划分

以 `max_input_tokens` 为基础，建议按比例切分：

- `system + static prompt`: 15%
- `conversation context`: 30%
- `execution context summaries`: 35%
- `scratch / safety margin`: 20%

也可以按模型等级做分段策略：

- 小窗口模型：更积极压缩
- 大窗口模型：允许保留更多 execution summaries

## 7.3 压缩触发规则

建议不要再用 `messages >= 20` 作为主触发条件，而是改成：

### 条件一：预估输入超阈值

若：

- `estimated_input_tokens >= model_limit * 0.8`

则触发一级压缩。

### 条件二：执行上下文超桶

若：

- `execution_context_tokens >= execution_budget`

则只压缩 execution context，不动 conversation context。

### 条件三：单次工具结果过大

若某次 tool 输出超过：

- `max(model_limit * 0.08, 固定下限)`

则该条不进入原始 messages，仅进入 ledger。

### 条件四：多工具突发

同一轮连续工具调用次数超过阈值时：

- 触发阶段性工作摘要
- 把多个工具结果合并成一条执行摘要

## 8. 新的上下文数据模型设计

建议在 `ThreadState` 中新增执行上下文专用字段，而不是继续把所有内容塞入：

- `loaded_skills`
- `retrieved_evidence`

建议演进为：

```python
class ExecutionSummary(TypedDict):
    summary_id: str
    turn_id: str
    source_scope: str
    source_names: list[str]
    content: str
    tokens_est: int
    priority: int
    created_at: int
    citations: list[str]


class ExecutionContextState(TypedDict):
    active_turn_id: str | None
    ledger_entries: list[dict]
    summaries: list[ExecutionSummary]
    pinned_summary_ids: list[str]
    archived_entry_ids: list[str]
    budget_snapshot: dict
```

然后在 `ThreadState` 中增加：

- `execution_context`

保留现有：

- `messages`
- `clarification`
- `artifacts`
- `research_workflow`

这样可以做到：

- 对话历史继续按原逻辑保存
- 工具工作态单独治理

## 9. 新的工具上下文控制流程

## 9.1 单次工具调用流程

1. 工具返回原始结果
2. `ToolResultCaptureMiddleware` 拦截结果
3. 写入 `execution_context.ledger_entries`
4. 根据工具类型做轻量清洗
5. 返回一条短 `ToolMessage` 占位文本进入 `messages`
6. 不把完整原始结果长期塞进对话消息

占位文本示例：

```text
[ToolContextStored] multi_kb_search 已完成，结果已写入 execution ledger，可按需装配。

```

## 9.2 下一次模型调用前

1. `ContextBudgetManager` 读取模型预算
2. 统计：
   - system prompt 占用
   - conversation messages 占用
   - execution context 占用
3. 若 execution context 超预算：
   - 先压缩 raw entries
   - 再压缩 summaries
   - 必要时调用 `SubagentSummarizer`
4. `ContextAssembler` 仅选择当前轮最相关摘要注入

## 9.3 多轮会话时

每轮结束后做一次“轮次收敛”：

- 将本轮工具链结果整理为 `turn_summary`
- 把原始 raw entries 标记为 `archived`
- 默认后续轮次不再回放 raw，只回放 `turn_summary`

这样可以把“多次工具调用的大量细节”压成“每轮一份工作摘要”。

## 10. 对未来大量 skills 的通用治理方案

## 10.1 不按 tool 名写死，按内容类别治理

建议增加 `ToolContextPolicyRegistry`：

```python
POLICIES = {
    "search_like": SearchPolicy(),
    "skill_like": SkillPolicy(),
    "file_parse_like": FileParsePolicy(),
    "report_like": ReportPolicy(),
    "generic_large_text": GenericLargeTextPolicy(),
}
```

tool 只需要满足以下任一方式即可接入：

1. tool metadata 声明 `context_policy_type`
2. 中间件按工具名规则自动映射
3. 默认回落到 `generic_large_text`

这样新增 skill 时：

- 不必修改主上下文框架
- 最多只补一个策略映射
- 大多数工具甚至可以零改造接入

## 10.2 skill 文件的特殊治理

skill 文件通常有两个问题：

- 原文很长
- 每轮重复注入成本高

建议处理方式：

1. `read_local_skill_file` 原文进入 ledger
2. 同时生成 `skill_digest_summary`
3. 后续优先注入：
   - skill 约束摘要
   - tool 使用说明摘要
   - 必要示例
4. 仅当模型明确需要原文细节时，再临时回放原文片段

这比现在把 skill 原文直接长期放进 `loaded_skills` 更可控。

## 11. 对当前实现的具体重构建议

## 11.1 第一阶段：先止血

### 建议 1：停止将 JIT 拼装结果持久写回 `state["messages"]`

`ContextPruningMiddleware` 应改为：

- 只生成临时 `patched_messages`
- 仅用于本次 `request.override(messages=patched)`
- 不回写拼装后的 `SystemMessage` 到持久状态

这一步是优先级最高的止血项。

### 建议 2：为 `retrieved_evidence` 增加上限与轮次边界

至少应增加：

- 每轮最大证据块数
- 总证据块上限
- 超限后的替换策略

否则 `retrieved_evidence` 会一直膨胀。

### 建议 3：把 `SummarizationMiddleware` 的触发条件改为预算驱动

不要只用 `messages >= 20`。  
建议包装一层动态触发器，由 `ContextBudgetManager` 决定是否需要摘要。

## 11.2 第二阶段：建立统一执行上下文层

新增模块建议：

- `backend/core/context/budgeting.py`
- `backend/core/context/ledger.py`
- `backend/core/context/policies.py`
- `backend/core/context/compression.py`
- `backend/core/context/assembler.py`
- `backend/core/agents/middlewares/tool_context_capture.py`
- `backend/core/agents/middlewares/execution_context_manager.py`

## 11.3 第三阶段：接入子智能体总结器

建议新建一个专用总结器，而不是复用主智能体：

- `backend/core/context/subagent_summarizer.py`

职责：

- 输入受控执行上下文片段
- 输出结构化摘要
- 不访问完整会话历史
- 不直接对用户输出

## 11.4 第四阶段：对 NE/CSH 统一接入

由于 `NEFullFeatureAgent` 和 `CSHFullFeatureAgent` 结构高度一致，建议：

- 抽出公共上下文控制构建逻辑
- 两个 agent 共用同一套 execution context middleware

避免两边后续继续复制粘贴演进。

## 12. 推荐的中间件链路调整

当前建议演进为：

1. `DanglingToolCallMiddleware`
2. `ToolGuardrailMiddleware`
3. `ToolErrorHandlingMiddleware`
4. `ToolContextCaptureMiddleware`
5. `ExecutionContextManagerMiddleware`
6. `SummarizationMiddleware` 或其预算驱动替代层
7. `ViewImageMiddleware`
8. `SubagentLimitMiddleware`
9. `LoopDetectionMiddleware`
10. `ClarificationMiddleware`

其中：

- `ToolContextCaptureMiddleware`
  - 负责采集工具输出到 ledger

- `ExecutionContextManagerMiddleware`
  - 负责预算评估、压缩、JIT 选择性装配

与当前 `ContextPruningMiddleware` 相比，新的职责划分更清晰。

## 13. 建议的最小实现路径

## P0：快速修复

目标：先解决“越跑越大直接中断”。

实施项：

1. 修正 `ContextPruningMiddleware`，避免 JIT 内容回写持久消息
2. 给 `retrieved_evidence` 增加数量上限
3. 给 `loaded_skills` 注入改为摘要优先
4. 增加上下文预算日志

产出：

- 多轮会话稳定性立刻提升

## P1：预算化治理

目标：真正按 MySQL 模型窗口控制输入。

实施项：

1. 新增 `ContextBudgetManager`
2. 所有压缩触发改为预算驱动
3. 增加 `estimated_input_tokens` 统计日志

产出：

- 不同模型自动适配不同上下文窗口

## P2：执行上下文分层

目标：把工具工作态从对话消息中剥离。

实施项：

1. 建立 `execution_context`
2. 新增 ledger / summaries
3. 工具输出默认只入 ledger，不长期入 messages

产出：

- 工具调用越多，系统越稳定

## P3：接入子智能体总结器

目标：解决复杂技能链、多次检索、多子任务汇总问题。

实施项：

1. 新增 `SubagentSummarizer`
2. 在超预算或 tool burst 时触发
3. 输出结构化工作摘要

产出：

- 深度研究与复杂技能组合场景稳定性显著提升

## P4：策略注册化

目标：未来 skill 扩展不再频繁改主框架。

实施项：

1. 建立 `ToolContextPolicyRegistry`
2. 新工具默认自动归类
3. 仅少数特殊工具需要单独 policy

产出：

- future skills 扩展成本显著下降

## 14. 关键实现细节建议

## 14.1 如何避免修改每个工具

核心做法不是改工具，而是截获：

- `ToolMessage`
- tool metadata
- graph events

统一入口包括：

- middleware 的 `after_tool` / `wrap_tool_call`
- 或在 graph event stream 中拦截 tool end 事件

所有重型输出都通过一个公共函数进入 ledger，例如：

```python
store_tool_result(
    state=state,
    tool_name=tool_name,
    tool_call_id=tool_call_id,
    raw_output=content,
    policy_type=resolved_policy_type,
)
```

这样就不用在每个工具里单独调用“压缩器”。

## 14.2 如何保证与现有 checkpoint 兼容

建议：

- 继续使用当前 `checkpointer`
- 在 `ThreadState` 中增量增加 `execution_context`
- 保持 `messages` 字段结构不变

这样：

- 对话列表读取逻辑不需要改
- 会话恢复逻辑不需要改
- 只是图状态中新增一块 execution state

## 14.3 如何保证最终回答仍可溯源

虽然 raw tool output 不再长期注入模型，但仍应保留：

- ledger entry id
- summary 到 raw 的 citations
- 关键证据引用关系

这样后续若要：

- 展示证据来源
- 调试错误结论
- 复盘某轮推理

依旧可以追溯。

## 15. 对 NE / CSH 两个 Agent 的落地建议

两个 Agent 结构几乎一致，因此建议抽出公共基类或公共装配函数，例如：

- `FullFeatureAgentContextMixin`
- `build_execution_context_middlewares()`

统一负责：

- 创建预算管理器
- 创建 execution context manager
- 创建子智能体总结器
- 注入统一 extra middleware

这样后续不再需要在：

- `ne_full_feature_agent.py`
- `csh_full_feature_agent.py`

分别维护一套上下文治理逻辑。

## 16. 最终结论

针对“多轮工具调用上下文过长直接中断”的问题，推荐结论如下：

### 结论一

**可以引入子智能体进行总结，但不应把它当成唯一解法。**  
它应该是统一上下文治理架构中的一个“高级压缩执行器”。

### 结论二

**真正需要重构的是工具执行上下文，而不是用户对话上下文。**  
主对话历史保持现状，执行上下文独立分层治理。

### 结论三

**必须基于 MySQL 中 `llm_models.max_input_tokens` 做预算控制。**  
上下文治理要从“固定条数”升级为“动态预算”。

### 结论四

**不要再按工具逐个改造。**  
应建立：

- 统一工具输出采集层
- 统一执行上下文 ledger
- 统一压缩编排器
- 统一按预算回放装配器

### 结论五

落地顺序建议为：

1. 先修正当前 `ContextPruningMiddleware` 的持久化膨胀风险
2. 再上线预算管理器
3. 再拆出 execution context 分层
4. 最后接入子智能体总结与策略注册化

这是风险最小、收益最大的实施路径。

---

## 17. 一句话方案摘要

将“多轮工具调用上下文管理”从当前的“消息裁剪”升级为“预算驱动的执行上下文分层治理”：

- 原始工具输出先入 ledger
- 超预算时优先规则/模板压缩
- 必要时启动子智能体生成结构化工作摘要
- 模型调用前只按 MySQL 模型上下文预算装配必要 execution summaries
- 用户对话上下文保持不变

该方案能同时解决当前中断问题，并为后续大量 skills 扩展提供统一架构基础。
