## 一、检索与召回层优化 (Stage 0 & Stage 1)

### 1.1 从 Pointwise Reranker 升级为 Listwise/Pairwise 架构
* **痛点根因**：当前系统使用的 Cross-Encoder（如 `Qwen3-Reranker-8B`）是逐点（Pointwise）对 Chunk 进行评分。在多跳问答（如 HotpotQA）中，回答问题需要将两个或多个 Chunks 结合起来进行推理。如果单独评估仅包含“第一步线索”或“第二步线索”的单个 Chunk，重排序模型会认为其与原始 Query 语义关联度低，从而给出低分，将其挤出 Top-10，导致 Recall 从 `0.69` 骤降到 `0.36`。
* **具体优化方案**：
  1. **Listwise 提示词重排序 (Listwise Reranking / RankGPT)**：
     将 Stage 1 召回出的前 $N$ 个 Chunks 作为一个完整的有序列表（带有唯一标识符），利用轻量级大模型（如 `Qwen2.5-7B-Instruct`）的 Attention 机制一次性对它们进行打分和排序。由于所有的 Chunks 都在大模型的 Context 中，模型可以识别出 Chunks 之间的互补关系（例如：“Chunk A 提到了奥巴马的出生地，Chunk B 提到了该出生地目前的人口，两者结合能回答 Query”），从而将这些多跳关键证据链拉到最前排。
  2. **上下文句群拼接 (Contextual Chunk Merging)**：
     在重排序前，分析 Chunks 之间的关联关系。如果两个 Chunks 在图谱上是 1-hop 邻居关系，或者在物理文档的原始段落中是相邻的，可以在送入 Pointwise Reranker 前将它们**拼接成一个复合文本块（Super-Chunk）**进行打分。这使得 Pointwise 排序器能够在一个评估单元中看到完整的推理线索。

### 1.2 解决 Path-A 句向量搜短实体尺度失真 (Modality Gap) 的进一步方案
* **痛点根因**：句向量（通常用于表达复杂的 Query 语义）与图谱中的短实体名（如 "PMT"、"ADC" 等）在文本长度、语义密度上存在天然的不匹配（Modality Gap）。在百科等通用数据集中，直接做向量 ANN 容易召回大量毫无关联的噪点实体，导致 F1 负优化。
* **具体优化方案**：
  1. **引入轻量级实体链接模型 (Entity Linking / EL)**：
     不再仅依赖通用句向量去匹配实体。在 Stage 0 阶段，集成如 `GLiNER`（通用信息提取器）或 `spaCy-entity-linker` 等轻量、快速的实体识别与链接组件。直接定位 Query 中的专有名词，并在 NebulaGraph 实体库中执行**精确匹配 + 软拼写匹配**，直接激活高置信度的 `SeedEntity`。
  2. **HyDE (Hypothetical Document Embeddings) 实体描述生成**：
     利用 LLM 对 Query 进行意图重写，不生成完整的虚拟文章，而是专门生成 Query 中潜在实体的“虚拟描述”（通常为 1-2 句解释）。使用这段**虚拟描述的向量**去搜索 Milvus 中实体的 `description` 向量。由于两者都是“描述性文本”，从而完美消除了短实体名的尺度失真问题。

## 二、图检索与计算层优化 (Stage 1.5 & Stage 2)

### 2.1 引入语义引导的随机游走 (Query-Guided Random Walk) 机制
* **痛点根因**：当前 Path-D（图扩展）中，两跳扩展会引入大量“看似结构相连，但与实际问题毫无关系”的噪声分支，稀释了候选池。同时，数据探查发现百科语料中 94.4% 的边权重均为 1，且缺乏语义分类，直接裁剪会导致图谱断连。
* **具体优化方案**：
  1. **动态语义跳转权重**：
     在 NebulaGraph 扩展阶段或下游 PPR 计算中，计算每个候选节点描述与 Query 语义嵌入的余弦相似度 $Sim(u, Query)$。将原本仅取决于物理边权 $Weight(u, v)$ 的转移概率进行重分配：
     $$P_{transition}(u \to v) \propto Weight(u, v) \times f\!\left(Sim(v, Query)\right)$$
     这使得图传播权重主要沿着与查询意图最一致的“语义通道”进行传导，天然屏蔽无关的多跳分支。
  2. **局部社团检测去噪 (Leiden / Louvain Denoising)**：
     当 DirectRetriever 召回出局部子图（包含 $100\sim150$ 个实体及其边）时，在 NetworkX 中执行快速的 **Leiden 社区划分算法**。识别出该子图中的 3~4 个核心聚类簇。计算每个聚类簇中包含 Seed 实体的比例，对于完全不包含 Seed 实体的“长尾/孤立社团”，在 PPR 计算前直接将这些社团的节点 and 边**整块裁剪**，能够直接阻断结构噪声。

### 2.2 垂直领域 PPR “负优化陷阱”的软融合升级
* **痛点根因**：在医疗、小说等垂直领域，知识图谱的关系提取往往非常稀疏且伴随大量噪声（Hub 节点过度吸血）。现有的 PPR 机制采用硬过滤（`filtered_entities = filtered_entities[:max_entities]`），导致原本语义极为匹配、但因为图谱关系断连而获得低 PPR 分数的 Chunk 被直接过滤，Semantic Recall 从 `0.60` 暴跌至 `0.10`。
* **具体优化方案**：
  1. **Reciprocal Rank Fusion (RRF) 软融合替代硬过滤**：
     取消 Stage 2 中对 PPR 分数的硬性阈值截断。将 PPR 计算定位为“辅助特征”。对每一个 Chunk 计算三个独立的排名（Rank）：
     - $R_{semantic}$：Path-C 及向量召回的排名；
     - $R_{rerank}$：Reranker 的相关性评分排名；
     - $R_{ppr}$：该 Chunk 对应实体的 PPR 图得分排名。
     使用 RRF 算法进行无标度排名合并：
     $$Score_{RRF}(d) = \frac{w_1}{k + R_{semantic}(d)} + \frac{w_2}{k + R_{rerank}(d)} + \frac{w_3}{k + R_{ppr}(d)}$$
     其中常数 $k=60$。即使一个 Chunk 在图谱中处于断连的“孤岛”状态（$R_{ppr}$ 极低），但只要它的语义向量足够强（$R_{semantic}$ 和 $R_{rerank}$ 极高），它依然能保持前排位置，彻底杜绝硬过滤带来的误伤。
  2. **动态子图冷启动/修剪 (Active Subgraph Pruning)**：
     在构建 PPR NetworkX 图时，过滤掉与 Query 余弦相似度低于临界值（如 $0.20$）的实体，仅对“高语义相关”的活跃子图执行 Personalized PageRank，防止权重漫流到无关的全局 Hub 节点。

## 三、工程与性能优化 (Performance & System IO)

### 3.1 实施二跳邻居本地分布式缓存 (2-Hop Local Graph Cache)
* **性能瓶颈**：当 `DirectRetriever` 并发高、seeds 较多时，NebulaGraph 的 `GO` 语句网络 I/O 是最大的延迟来源。
* **具体优化方案**：
  * 在 Redis 中为高中心度实体（Degree > 20 的 Hub 节点，例如百科中的大词）预取并缓存它们的 **1-hop 和 2-hop 邻居及边关系列表**。
  * 在 `GraphExpander.expand` 中，优先查询 Redis 缓存。若缓存命中，直接在内存中组装邻域子图，只有在缓存未命中时才向 NebulaGraph 发送 nGQL 查询。这可以使 Path-D 图扩展阶段的平均数据库耗时从数十毫秒甚至数百毫秒压缩到接近 **$1\sim2$ 毫秒**。

### 3.2 实体链路分块管道化流式读取 (Pipelined Lazy Fetch)
* **性能瓶颈**：在 Stage 1 的融合阶段，系统会针对 Top 实体拉取关联的文本块内容（即使做了 Lazy Fetch 限制到 `chunk_top_k * 1.5`，通常仍有数十个 ID），对 Redis/Milvus 产生批量 IO 损耗。
* **具体优化方案**：
  * **分级流式拉取**：将 `fetch_entity_linked_chunks` 改为生成器（Generator）模式。优先并发拉取实体权重排名前 30%（最核心）的 Chunks，并直接送入 Rerank 和下游过滤，同时启动其余 Chunks 的异步后台拉取。
  * **首字延迟 (TTFT) 优化**：在流式问答场景下，这种“前轻后重”的拉取逻辑可以极大地缩短检索器的热启动时间，使用户能提前约 **0.5s~1.0s** 看到大模型的首 Token 输出。

## 四、超参扫描与数据驱动闭环 (MLOps)

### 4.1 引入 Optuna 贝叶斯黑盒超参优化管线
* **现状分析**：目前的优化主要依赖开发人员针对 $30$ 或 $100$ 题的 HotpotQA 样本进行手动的、离散的网格扫描（例如从 0.05 到 0.15 扫描 `ppr_ceiling`）。这种方式不仅耗时费力，而且无法覆盖多参数之间的交互效应（例如当 `entity_pool_size` 增大时，最佳的 `seed_mmr_lambda` 和 `ppr_weight` 应该如何协同调整）。
* **具体优化方案**：
  1. 在 `eval/datasets/hotpotqa/` 中集成 **Optuna 超参搜索库**。
  2. 定义评估目标函数（Objective Function）：运行消融评测脚本，输入参数配置，输出综合 $F_1$ 分数与 Recall 分数。
  3. 将以下参数定义为连续/离散搜索空间：
     * `seed_mmr_lambda` : `[0.10, 0.60]` (float)
     * `ppr_ceiling` : `[0.05, 0.30]` (float)
     * `ppr_seed_blend_ratio` : `[0.2, 0.8]` (float)
     * `edge_bonus_weight` : `[0.05, 0.30]` (float)
     * `rescue_bonus.base_bonus` : `[0.01, 0.15]` (float)
  4. 运行 $50\sim100$ 轮贝叶斯主动学习搜索，自动输出在 HotpotQA/医疗数据集上的**全局帕累托最优（Pareto-optimal）参数矩阵**，以 100% 数据驱动的方式锁死最优配置。
