# 智能体平台技术要求与功能要求

---

## 一、总体建设要求

智能体框架平台应面向核电子学、场地污染与水文地质等专业领域的智能问答、知识服务和复杂业务任务，构建统一、开放、可扩展的智能体运行与协作底座。平台应具备复杂任务理解、规划、分解与执行能力，支持多智能体协作、运行状态管理、智能路由、工具与技能编排、长短期记忆管理、异常处理及全链路可观测性，并能够统一衔接模型、知识库、检索、文件、会话及外部工具等平台资源，为不同产品线智能体的快速构建、灵活扩展、稳定运行和持续演进提供基础支撑。

1．平台基础架构要求

1）架构模式：系统应采用前后端分离架构，后端基于 Python、FastAPI、Uvicorn 提供统一服务能力，前端基于 Vue 3、TypeScript、Vite、Tailwind CSS 构建多端 Web 应用，需保证业务能力、界面展示和接口服务之间具备清晰边界，便于独立扩展和部署维护。

2）服务底座：系统应提供统一智能体服务底座，需同时支撑 RadAI 核电子学智能助手、CSH-AI 场地污染/水文地质智学助手和 Guest 访客演示模式，确保不同产品线能够复用统一模型、检索、文件和会话能力。

3）部署隔离：系统应支持主 API 与访客 API 分离部署。主 API 面向完整业务能力，需提供智能体问答、知识库管理、文档入库、模型管理、文件中心、MCP 等接口；访客 API 面向演示与轻量访问，仅开放登录、问答、会话和基础文件能力，并使用独立 Checkpointer 进行会话状态隔离。

4）接入方式：系统应支持 Web UI、REST API、SSE 流式接口和 MCP SSE 接入方式，需满足浏览器访问、程序化调用、外部系统集成和工具协议接入等不同使用场景。

5）模块扩展：系统应具备模块化扩展能力，智能体、知识库、文件、模型、数据集、工具、探索式学习等能力需以独立路由和服务模块组织，便于后续按业务域、产品线或部署形态进行扩展。

6）运行探测：系统应提供服务健康检查和配置查询能力，支持对主服务、访客服务、RAG 服务等运行状态进行基本探测，便于部署验收、运维监控和故障定位。

2．多产品线支撑要求

1）核电子学问答：系统应支持核电子学领域专业问答，需围绕核探测器、放大器、脉冲成形、能谱分析、核辐射测量等专业资料进行知识检索和回答生成，保证回答内容具备专业性和资料依据。

2）场地污染与水文地质问答：系统应支持场地污染和水文地质领域专业问答，需围绕地下水、污染物迁移、场地调查、修复技术、监测评估等内容进行知识检索和学习辅助。

3）前端复用：系统应支持不同前端入口复用同一后端能力，RadAI、CSH-AI 和 Guest 前端可分别调用对应智能体路由和会话接口，满足多产品线统一建设、差异化呈现的要求。

## 二、智能体交互与编排功能要求

1．智能体抽象层框架要求

1）框架定位：系统应提供统一的智能体抽象层，在业务智能体之上封装 ReAct、Plan-and-Execute、Supervisor/Worker 等通用智能体编排范式，为 RadAI、CSH-AI、Guest 等不同产品线提供一致的运行框架，避免将具体问答或研究场景固化为独立实现。

当前平台级工作流入口至少应保留 `lightweight`、`full`、`deep_research`、`plan_solve`、`multi_agent_parallel`、`multi_agent_alternating` 六类标准名称，其中 `plan_solve`、`multi_agent_parallel`、`multi_agent_alternating` 作为后续复杂编排和多智能体协同的保留扩展点，不应再通过领域专属 Agent 类单独实现。

2）ReAct 循环：系统应支持基于 ReAct 思想的推理、行动、观察闭环，将模型决策、工具选择、工具执行、结果观察和下一步调度抽象为标准执行过程，保证工具型智能体具备可扩展、可观测、可控制的运行机制。

3）状态图编排：系统应支持基于 LangGraph 状态图或等效状态机机制的智能体编排能力，能够将模型节点、检索节点、工具节点、规划节点、校验节点、人工中断节点等抽象为可组合节点，并支持条件路由、并行分支、循环控制和异常分支处理。

平台应在工作流层保留协调器扩展入口，支持后续在不修改主执行器内核的前提下扩展 `plan.created`、`coordination.started`、`coordination.completed`、`subagent.started`、`subagent.completed` 等标准事件类型，用于支撑 Plan/Solve、多智能体并行和多智能体交替协作模式。

4）工具抽象：系统应提供统一工具调用接口和工具注册机制，将知识库检索、文件检索、联网搜索、学术搜索、数据分析、报告生成等能力抽象为可声明、可授权、可限流、可审计的工具资源，便于不同智能体按权限和任务策略动态装配。

5）运行策略：系统应支持面向智能体运行时的策略抽象，能够根据任务类型、上下文规模、工具依赖、用户权限、响应时效和资源消耗等参数选择合适的编排图、工具集合、模型配置和 Checkpointer，实现智能体执行链路的统一路由和治理。

2．流式交互要求

1）流式输出：系统应支持 SSE 流式输出，问答过程中需持续返回状态、正文片段、工具调用进展、子任务进度、错误信息和完成事件，降低长耗时任务的等待感。

2）思考隔离：系统应支持对模型思考内容进行过滤或隔离展示，面向用户输出时应避免将内部推理标签、工具中间过程或非展示内容直接暴露为普通回答正文。

3）任务订阅：系统应支持长流程任务的进度查询和事件流订阅，用户可通过任务状态接口查看任务是否运行、完成、失败或取消，便于前端展示进度和处理异常。

4）上下文保持：系统应支持多轮会话上下文管理，能够按用户、线程、智能体和产品线维度维持会话状态，保证跨轮问答具备连续性。

3．会话与上下文要求

1）状态持久化：系统应基于 LangGraph Checkpointer 持久化智能体线程状态，主 API 与访客 API 应分别使用独立的 SQLite Checkpointer，保证会话状态可恢复且相互隔离。

2）会话管理：系统应支持会话列表、会话标题修改、会话删除、历史消息查询和会话回滚等能力，满足用户对历史对话的查看、整理和恢复需求。

3）管理查询：系统应支持管理员按授权范围查看会话统计、会话列表、会话详情并执行必要管理操作，需保证查询范围与角色权限、用户归属和产品线范围一致。

4）上下文治理：系统应提供上下文裁剪和工具结果隔离能力，对长文本检索结果、技能文件和工具调用内容进行按需装配，减少无关内容进入 Prompt，降低对话上下文污染。

## 三、知识库与 RAG 检索功能要求

1．知识库管理要求

1）基础管理：系统应支持知识库创建、列表查询、详情查询、信息更新、删除、默认知识库获取、知识库切换和统计信息刷新，满足专业资料库全生命周期维护需求。

2）文档状态：系统应支持按知识库查看文档列表，并能够返回文档解析状态、入库状态、错误信息、chunk 数、实体数和关系数等指标，便于管理员掌握资料处理进度和质量。

3）目录维护：系统应支持知识库目录管理，便于对论文、教材、报告、规范、图表等专业资料进行分层组织和持续维护。

4）智能体绑定：系统应支持智能体与知识库绑定管理，管理员可为不同智能体配置可访问知识库，并支持全量替换、追加绑定和删除绑定，保证不同业务智能体仅访问授权知识范围。

2．检索能力要求

1）统一入口：系统应提供统一检索入口，所有 HTTP 检索、智能体工具检索、轻量问答、全功能问答和探索式学习模块应统一调用 `retrieve_context` 进行上下文获取，保证检索策略和结果结构一致。

2）多库检索：系统应支持单知识库检索、多知识库并行检索和多库结果融合，满足跨专业资料库、论文库和业务知识库联合问答需求。

3）多路召回：系统应采用 DirectRetriever 四路并行召回机制，至少包括实体向量召回、实体 BM25 召回、chunk 语义向量召回和 NebulaGraph 图扩展召回，提高不同类型问题的命中率。

4）策略配置：系统应支持按知识库类型配置检索 Profile，能够在 `default`、`general_qa`、`domain`、`lightweight` 等策略之间切换召回路径、过采样策略和内容过滤方式。

5）内容过滤：系统应支持 Stage-2 内容过滤和重排序，能够根据 Profile 选择 RAW、MMR_ONLY、FULL 等模式，实现去重、多样性控制、图过滤、重排序和证据补救，减少重复或低相关上下文。

6）结果回传：系统应支持返回文本上下文、实体关系信息、相关图片和检索统计信息，便于模型生成可追溯、接地的专业回答，并支持前端展示引用依据。

3．检索性能要求

1）实时性：系统需能够高速、按时地存取和处理检索数据，应尽量保证关键问答、资料定位和上下文召回操作在规定时间内完成，满足专业问答、教学导学和资料查询等实时访问需求。

2）多级索引：系统应通过 Milvus 向量索引、Redis BM25/缓存、NebulaGraph 图谱和 MySQL 元数据协同，形成多级索引机制进行快速数据定位，提高知识检索速度和上下文召回效率。

3）启动预热：系统应在服务启动阶段支持 RAG 实例预热、关键词索引预加载和关键词图缓存预热，降低首次查询延迟，提升服务上线后的可用性。

4）召回收敛：系统应支持 Stage-1 过采样和最终 chunk 收敛，既保证召回覆盖度，又控制进入 Prompt 的上下文规模，避免过量资料影响模型回答质量和响应速度。

5）索引维护：系统应支持按知识库进行关键词索引初始化、构建、统计、缓存失效和删除操作，保证新入库资料能够被检索链路及时使用。

## 四、文档采集、处理与入库要求

1．文件上传要求

1）上传方式：系统应支持普通上传、批量上传和分块上传，分块上传应具备初始化、分片提交、进度查询、合并完成和取消能力，满足大文件、批量资料和网络不稳定场景下的上传需求。

2）待入库管理：系统应支持将上传文件进入待入库列表，管理员可查看待处理文件、批量移动、触发入库、查询入库状态和删除待入库记录，确保资料采集、审核和入库流程可管理。

3）文件类型：系统应支持常见专业资料文件接入，包括 PDF、DOCX、TXT、Markdown 以及图片类材料等，满足论文、教材、报告、图表和多模态材料入库需求。

4）存储记录：系统应使用 MinIO 保存原始文档、解析后图片和生成文件，并使用 MySQL 记录文件、知识库文档和任务元数据，保证文件对象与业务元数据可关联、可追踪。

2．文档解析与入库要求

1）入库链路：系统应支持 RAGAnything 和 LightRAG 入库链路，完成文档解析、分块、实体抽取、关系抽取、向量写入、图谱写入和状态记录，形成面向问答检索的知识资产。

2）多模态处理：系统应支持 Markdown 直入库和多模态文档处理，解析后的图片、表格、公式等内容应能够作为上下文或附件参与后续问答。

3）异步处理：系统应支持异步入库处理，能够通过 Kafka Worker、Ingest Worker 或启动任务处理器处理待入库任务，避免长耗时解析阻塞主问答链路。

4）进度跟踪：系统应支持入库进度和结果跟踪，能够记录成功、失败、处理中等状态，并保存错误信息以便运维排查和重新处理。

5）索引同步：系统应在文档入库后触发索引同步，将新增实体同步到关键词索引，并支持按知识库进行强制全量同步或定时同步，保证新增资料及时进入检索范围。

3．内容抽取要求

1）抽取任务：系统应提供内容抽取接口，支持单文件和批量抽取任务，满足资料预处理、内容检查和后续入库准备需求。

2）结果查看：系统应支持按抽取任务查看文本、表格、公式、图片等结果，并支持删除抽取结果，便于管理员校验解析质量。

3）业务衔接：系统应支持将抽取结果与后续知识库入库、问答上下文和文件管理能力衔接，避免重复处理同一资料。

## 五、文件、附件与工件管理要求

1．对话附件要求

1）附件上传：系统应支持用户在对话中上传附件，并能够按线程查看、删除和读取附件解析出的图片，满足临时资料辅助问答需求。

2）附件检索：系统应支持对话附件检索工具，使智能体能够在当前会话范围内检索长文档内容并参与回答，避免附件内容只能人工查看。

3）范围隔离：系统应将对话附件与用户、线程进行关联，需防止跨用户或跨线程误用，保证会话资料边界清晰。

2．个人文件中心要求

1）文件管理：系统应支持个人文件上传、列表查询、重命名、删除、图片读取和下载，满足用户对个人资料和生成结果的集中管理需求。

2）会话复用：系统应支持将个人文件附加到指定会话，用户可复用历史上传文件，无需重复上传，提高多轮研究和持续学习效率。

3）生成归档：系统应支持将智能体生成的报告、表格、代码包、演示文稿等保存到个人文件中心，便于用户下载、复查和二次使用。

4）私有访问：系统应默认将个人文件设为用户私有，仅允许本人或授权管理接口访问，避免个人资料被未授权用户读取。

3．线程工件要求

1）工件保存：系统应支持按线程保存智能体生成工件，包括深度研究报告、HTML PPT、图表、导出文档等，保证生成成果与具体任务、会话可关联。

2）作用域校验：系统应使用用户级和线程级对象存储前缀保存工件，读取和写入时应校验 `users/{user_id}/threads/{thread_id}` 作用域，防止越权访问。

3）代理访问：系统应支持线程工件 HTTP 代理访问，并应防止路径穿越和越权访问，确保对象存储资源能够安全返回前端。

## 六、模型、多模态与数据分析要求

1．模型管理要求

1）模型维护：系统应支持模型列表查询、模型新增、模型更新、模型删除和模型启停切换，满足模型资源统一纳管和运行策略调整需求。

2）Provider 接入：系统应支持多模型 Provider 配置，能够对接 OpenAI 兼容接口、DeepSeek、Claude、DashScope、本地模型服务或私有化模型服务，便于根据部署环境选择模型来源。

3）能力类型：系统应支持 LLM、VLM、Embedding、Rerank、ASR 等不同模型能力的配置化接入，保证问答、视觉理解、向量化、重排序和语音转写能力可组合使用。

4）配置管理：系统应支持通过数据库和配置文件统一管理模型名称、API 地址、密钥、上下文长度、推理开关和默认模型，便于运维人员进行统一配置和审计。

2．多模态能力要求

1）图像上下文：系统应支持图像上下文注入，用户上传图片或文档解析图片后，智能体可在回答中引用相关视觉内容，提高图表、公式、图片资料的利用率。

2）语音转写：系统应支持语音转写接口，用户可上传音频并获得文本结果，用于后续问答、记录整理或学习场景。

3）资料融合：系统应支持文档解析图片、图表和公式进入知识库上下文，提高多模态专业资料问答能力，减少纯文本检索对复杂资料的覆盖不足。

3．数据集与图表要求

1）数据集管理：系统应支持 Excel/CSV 实验数据集注册、上传、详情查询、预览、刷新和删除，满足科研实验数据和业务表格数据的统一管理需求。

2）访问绑定：系统应支持将数据集与智能体绑定，不同智能体可访问不同实验数据资源，确保数据分析范围与业务角色、智能体能力相匹配。

3）分析工具：系统应支持科研数据分析工具，能够对 Excel 数据进行查询、统计、图表生成和结果归档，为实验数据分析和报告生成提供支撑。

4）图表访问：系统应提供图表图片访问能力，支持将分析生成的图表作为文件或图片资源返回前端，并可用于会话回答、报告或工件归档。

## 七、工具调用与开放扩展要求

1．工具调用要求

1）工具类型：系统应支持智能体在回答过程中调用内置工具、知识库检索工具、文件检索工具、联网搜索工具、学术搜索工具、数据分析工具、报告生成工具和任务工具，满足复杂问题的分步骤处理需求。

2）多库工具：系统应支持多知识库检索工具，能够在当前选定知识库范围内并行检索，并对多库结果进行融合，提高跨库专业问答的覆盖度。

3）子智能体工具：系统应支持子智能体任务工具，全功能问答和深度研究场景可将复杂任务拆解给子智能体并接收结构化结果，提升复杂研究任务的处理能力。

4）调用控制：系统应支持工具调用次数限制、子智能体并发限制、循环检测、工具错误处理和澄清机制，降低异常工具调用对主流程的影响。

2．技能扩展要求

1）动态加载：系统应支持 Skills 动态加载，按用户选择的技能组合注入领域提示词、工具清单和执行约束，满足不同任务场景下的能力扩展需求。

2）领域隔离：系统应支持不同领域技能隔离，核电子学、水文地质、HTML PPT、深度研究等技能可按需加载，避免无关技能影响回答风格和工具选择。

3）文件作用域：系统应支持技能文件作用域控制，避免未授权技能内容或本地文件被跨用户、跨线程读取。

3．MCP 开放能力要求

1）MCP 服务：系统应支持 MCP SSE 服务，对外提供核电子学知识库查询等工具能力，满足外部智能体客户端的工具调用需求。

2）MCP 查询：系统应支持 MCP 配置查询和 MCP 查询接口，便于外部工具、IDE 或智能体客户端接入平台能力。

3）协议并存：系统应支持 REST API 与 MCP 并存，外部系统可按接入场景选择 HTTP、SSE 或 MCP 协议，提高平台开放能力的兼容性。

## 八、探索式学习功能要求

1．学习导航要求

1）主题生成：系统应支持按领域生成或返回学习主题，至少覆盖核电子学和场地污染水文地质两个学科方向，便于用户从专业领域进入结构化学习。

2）脑图组织：系统应支持思维导图生成、节点展开和知识点层级组织，帮助用户从主题进入结构化学习路径，逐步展开核心概念和关联知识。

3）资源关联：系统应支持学习资源关联，根据知识点从知识库中检索相关文档、片段或资料，并提供资源下载入口，保证学习内容具备资料依据。

2．知识详解要求

1）依据生成：系统应支持知识点详解，详解内容应优先基于知识库检索上下文生成，降低无依据生成风险，提高专业学习内容的可信度。

2）流式详解：系统应支持流式详解输出，用户可在生成过程中实时看到内容，提升长文本学习材料生成过程中的交互体验。

3）领域切换：系统应支持不同领域 subject/domain 参数切换，使 RadAI 和 CSH-AI 的探索式学习内容保持专业域一致。

3．练习与评价要求

1）练习生成：系统应支持基于知识点生成练习题，题目应结合知识库内容和当前学科场景，满足学习检测和复习巩固需求。

2）答案评分：系统应支持用户答案评分和反馈，给出答题结果、解释和改进建议，帮助用户定位理解不足。

3）学习缓存：系统应具备探索式学习缓存能力，对常用思维导图或主题结果进行缓存，提高重复访问响应速度。

## 九、安全、权限与隔离要求

1．认证要求

1）基础认证：系统应支持账号密码登录、登出、Token 验证、当前用户信息查询和密码修改，满足常规用户身份认证和会话管理需求。

2）统一认证：系统应支持 CAS 单点登录及回调处理，满足与统一身份认证平台集成的需求。

3）辅助认证：系统应支持短信验证码注册和找回密码等辅助认证流程，提升账号找回和注册场景的可用性。

4）接口认证：系统应支持 API Key 和 Bearer Token 两类接口认证方式。

2．权限控制要求

1）管理权限：系统管理类接口应进行管理员权限校验，包括知识库管理、智能体管理、模型管理、管理员会话管理等操作，避免普通用户执行管理操作。

2）分级授权：系统应支持按照管理员、领域管理员、普通用户、访客等用户组进行不同权限配置，并支持按产品线、知识库、智能体、会话、文件等对象限定可访问范围。

3）查询授权：系统查询功能应支持分级、分类、分字段授权，各层级管理员只能在授权范围内查询和管理对应业务对象的信息，包括会话、知识库、文件、模型、数据集和任务记录等。

4）审计上下文：系统应支持用户上下文注入，为每次请求生成 `request_id`，并在可识别时写入 `user_id` 和 `username`，便于审计、日志追踪和问题定位。

5）隔离控制：系统应支持用户级文件隔离、线程级工件隔离、访客服务隔离和技能作用域隔离，保证不同用户、线程和产品线之间的数据边界清晰。

6）越权防护：系统应防止文件越权访问，文件下载、工件读取、对象存储写入和图片读取应校验用户或线程作用域，避免跨用户、跨线程读取数据。

3．安全防护要求

1）工具安全：系统应具备工具调用安全控制能力，包括工具白名单、工具调用保护、子智能体数量限制和异常工具调用处理，防止工具链被异常输入或循环调用影响。

2）输入输出护栏：系统应具备输入输出护栏能力，对不合规输入、OCR 内容、工具输出和模型输出进行必要校验，降低不合规内容进入业务流程或展示给用户的风险。

3）敏感信息保护：系统应对 API Key、密码等敏感信息进行日志过滤，避免凭据进入普通日志或 Kafka 日志，保证运维排查过程不泄露敏感信息。

4）访客限制：访客模式应限制可用路由，不应暴露知识库管理、文档入库、MCP 管理和后台 Worker 管理能力，确保演示访问不影响正式业务能力。

## 十、数据存储与基础设施要求

1．多存储协同要求

1）关系数据：系统应使用 MySQL 存储用户、知识库、文档、模型、任务、会话、数据集等结构化元数据，保证核心业务对象具备稳定的数据记录。

2）向量数据：系统应使用 Milvus 存储 chunk 向量、实体向量和关键词索引等语义检索数据，支撑专业资料的语义召回。

3）图谱数据：系统应使用 NebulaGraph 存储实体关系图谱，支持图拓扑扩展、关系检索和知识图谱召回，提高复杂概念关联问题的检索能力。

4）对象数据：系统应使用 MinIO 存储原始文档、解析图片、对话附件、个人文件和智能体生成工件，保证大文件和非结构化对象可统一管理。

5）缓存数据：系统应使用 Redis 存储缓存、BM25 索引、文档状态和认证 Token 等快速访问数据，提高热点数据访问效率。

6）消息数据：系统应使用 Kafka 支持异步任务分发、结果回传和可选结构化日志输出，为文档入库、索引同步和日志采集提供消息通道。

7）会话状态：系统应使用 SQLite Checkpointer 保存 LangGraph 会话状态，并区分主 API 与访客 API，确保不同服务的会话状态互不混用。

2．一致性与同步要求

1）增量同步：系统应支持知识库入库后的增量索引同步，保证图数据库、向量数据库和关键词索引能够逐步一致。

2）定时同步：系统应支持定时索引同步调度，默认对活跃知识库进行周期性同步，降低索引长期不一致风险。

3）任务恢复：系统应支持启动阶段扫描未完成任务，处理 `PendingFile` 等遗留任务，减少服务重启导致的任务丢失。

4）初始化容错：系统应在外部依赖初始化超时时切换为后台继续执行，避免非关键初始化阻塞主服务启动。

## 十一、接口与集成要求

1．REST API 要求

1）接口覆盖：系统应提供覆盖认证、会话、智能体问答、知识库管理、RAG 检索、文档上传、文档入库、内容抽取、文件中心、模型管理、探索式学习、数据集、图表和管理员会话管理的 REST API，满足平台主要业务能力对外调用需求。

2）接口文档：系统应提供 OpenAPI/Swagger 文档能力，便于开发调试、联调验收和外部系统对接。

3）错误返回：系统应支持统一错误返回，接口异常应返回明确 HTTP 状态码和错误信息，便于调用方识别错误类型并进行处理。

2．SSE 接口要求

1）流式接口：智能体问答、RAG 流式问答、深度研究任务和 MCP 服务应支持 SSE 或 SSE 风格事件流，满足长文本生成和长任务进度反馈需求。

2）事件类型：SSE 事件应区分状态、内容片段、工具调用、任务进度、错误和完成等类型，便于前端进行精细化展示和状态管理。

3）断开处理：系统应处理客户端断开或响应体已开始发送后的异常，避免二次发送响应导致服务异常扩散。

3．第三方集成要求

1）HTTP 集成：系统应支持通过 HTTP API 接入外部业务系统，将智能问答、知识检索、文件处理和模型管理能力作为平台服务输出。

2）MCP 集成：系统应支持通过 MCP 协议接入外部智能体或工具客户端，便于外部智能体调用平台知识检索和工具能力。

3）依赖接入：系统应支持接入外部模型服务、文档解析服务、视觉模型服务、对象存储、数据库、消息队列和统一认证服务，满足本地化、私有化和混合部署需求。

## 十二、性能、稳定性与运维要求

1．性能要求

1）并发处理：系统应采用异步 Web 框架和异步数据库访问，支持并发 API 请求、并行检索和异步任务处理，保证多用户同时访问时核心接口保持稳定响应。

2）资源调度：系统应支持配置化线程池和多 Worker 运行方式，生产模式下主 API 可按部署资源调整 Uvicorn workers，满足不同硬件资源条件下的性能调优需求。

3）检索加速：系统应通过 DirectRetriever 四路并行召回、RAG 预热、关键词图缓存和结果过滤收敛，提升专业问答的响应效率，确保关键检索操作能够在规定时间内完成。

4）实时反馈：系统应通过 SSE 流式输出降低用户等待感，长耗时回答和深度研究任务应持续返回进度，保证用户能够实时了解任务执行状态。

5）后台处理：系统应将文档解析、入库、索引同步、深度研究等耗时任务放入后台流程处理，避免阻塞核心问答接口，提高系统整体吞吐能力。

2．稳定性要求

1）异常处理：系统应具备全局异常处理能力，未捕获异常应被记录并转换为标准错误响应，避免单个异常影响整体服务。

2）检索降级：系统应支持检索降级能力，DirectRetriever 不可用时可回退到 LightRAG 查询，确保专业问答在部分检索组件异常时仍具备基本可用性。

3）消息降级：系统应支持 Kafka 不可用时本地日志保留或任务降级策略，避免日志链路影响主业务。

4）对象兼容：系统应支持 MinIO 对象路径规范化和兼容旧路径读取，降低历史数据迁移和存储路径调整带来的访问风险。

5）错误诊断：系统应支持入库失败、模型请求失败、Rerank 失败等异常场景记录，并尽量返回可诊断错误，便于运维人员快速定位问题。

3．部署运维要求

1）部署形态：系统应支持本地开发、容器化依赖部署和分服务部署，满足研发调试、测试验收和生产上线等不同阶段需求。

2）服务启动：系统应支持主 API、访客 API、RadAI 前端、CSH-AI 前端、Guest 前端、Kafka Worker、Ingest Worker 等服务分别启动，便于按业务模块独立部署和扩缩容。

3）常用命令：系统应提供数据库初始化、测试、代码检查、主 API 启动、访客 API 启动、Worker 启动等常用命令，降低部署和运维操作复杂度。

4）日志能力：系统应提供本地文件日志，并支持按需将结构化业务日志发送到 Kafka，便于后续日志管理平台消费、检索和分析。

5）配置管理：系统应通过环境变量或配置文件管理 LLM、Embedding、Rerank、MySQL、Milvus、NebulaGraph、MinIO、Redis、Kafka、CAS、ASR 等外部依赖参数，确保不同部署环境可配置、可迁移。

## 十四、简要表述

本平台是一套面向专业领域知识服务的智能体平台，采用 FastAPI + LangGraph + LightRAG/RAGAnything 的技术路线，集成知识库管理、RAG 检索、多智能体编排、深度研究、探索式学习、文件工件管理、模型管理和 MCP 开放接口等能力。平台底层融合 MySQL、Milvus、NebulaGraph、MinIO、Redis、Kafka 和 SQLite Checkpointer，支持 RadAI、CSH-AI 与 Guest 多产品线部署，能够为专业问答、资料入库、教学导学、研究报告生成和外部系统智能能力集成提供统一支撑。
