# 地下水项目分析功能实现规划

## 1. 需求理解

目标是在现有 AI 中枢平台中新增一个“地下水项目分析”专用能力，支持用户创建项目文件夹并沉淀项目级资料，随后围绕已有钻井、区域背景与通用钻井标准知识库进行问答、解释和预测分析。

核心数据包括：

- 项目文件夹：按用户隔离，承载一个地下水工程/调查项目的全部资料。
- 钻井结构化表格：坐标、孔深、地层/岩性、水位、水文地质条件、含水层、采样/试验指标、施工信息等。
- 钻井描述：现场记录、编录文字、异常现象、施工备注。
- 钻井图片：岩芯照片、井位照片、柱状图、剖面图、区域图等。
- 区域背景信息：地形地貌、地质构造、补径排条件、含水层分布、污染源/补给源、历史工程资料。
- 通用知识库：钻井标准、地下水调查规范、水文地质评价标准等通用文档。

典型问题包括：

- “某个钻井的水文条件和周边钻井相比有什么异常？”
- “后续要在某地址/坐标附近打新钻井，基于已有钻井和区域条件，建议深度、可能地层、水位范围和风险是什么？”
- “根据标准文档，这个项目现有钻井资料缺哪些字段或质量控制项？”
- “给出新井位布设建议、预测依据、不确定性和需要补充采集的数据。”

## 2. 现有项目能力梳理

当前代码已经完成智能体平台标准化，地下水能力必须接入新运行时，不能继续复制旧的 `NEFullFeatureAgent`、旧 `/api/v2/agent` 路由或自定义 SSE 实现。

当前标准运行链路：

```text
HTTP Request
  -> AgentRuntimeQueryRequest
  -> AgentRequest
  -> AgentService
  -> AgentProfile
  -> AgentRuntimeContext
  -> WorkflowRegistry
  -> AgentWorkflow
  -> ProfiledAgentExecutor
  -> AgentEvent
  -> SSEEncoder
  -> Frontend
```

可复用的新平台能力：

- 统一执行入口：`backend/api/routers/agent_runtime.py` 提供 `/api/v2/agent-runtime/query`、Profile 信息和任务管理接口。
- Agent 配置：`backend/config/agents/*.yaml` 以 Profile 声明领域、默认 Skill、默认 KB、工作流、Prompt 和工具策略。
- 工作流：`backend/application/agent_workflows/` 已支持 `lightweight`、`full`、`deep_research`、`plan_solve` 和多智能体工作流。
- 统一执行器：`backend/application/agent_executors/` 根据 Profile 构建执行器，不需要新增地下水专用 Agent 类。
- Prompt 注册：`backend/application/agents/prompt_templates/` 与 `backend/config/prompts/registry.yaml` 支持按 Profile 装配领域提示词。
- Skill 注册：`backend/application/skills/manifest_loader.py` 从 `backend/skills/public|custom/*/SKILL.md` 读取平台级 `SkillManifest`。
- 工具注册：`backend/config/tools/registry.yaml`、`backend/config/tools/policies.yaml` 和 `PolicyToolAssembler` 按领域、工作流、Skill 策略装配工具。
- 标准事件流：所有执行结果统一转换为 `AgentEvent` 并由 `SSEEncoder` 输出。
- 请求级扩展参数：`AgentRequest.metadata` 会传入标准工作流执行器，可承载已校验的地下水项目上下文。
- 知识库、会话文件、表格分析、MinIO 文件存储等基础能力继续复用现有实现。

当前缺口：

- 没有“项目级”实体，现有文件主要绑定到用户或会话，无法稳定表达一个地下水项目的长期资料空间。
- 没有钻井结构化表、空间坐标、井位关系、项目背景文档之间的统一数据模型。
- 现有 Excel 工具偏通用数据集分析，缺少“钻井字段标准化、坐标/距离/邻近井筛选、地层/水位预测”等地下水专用工具。
- 新运行时尚无 `groundwater` Agent Profile、Prompt Profile、Tool Policy 和领域 Skill。
- 平台级 Skill 只扫描代码目录，尚无“按用户和项目动态解析项目 Skill 包”的请求级上下文组件。

## 3. 总体设计

优化后建议采用“一个项目一个 Skill 包”的架构。每个地下水项目在创建后生成一个项目目录，目录内包含该项目专属的 `SKILL.md`、钻井结构化数据、表格字段说明、区域背景摘要、图片清单和附件索引。地下水 Agent 进入某个项目时加载该项目 Skill，再结合通用钻井标准知识库回答问题。

这个方案的好处：

- 项目上下文天然隔离：不同项目的数据、背景、提示词和附件索引放在不同目录。
- 扩展性更好：新增项目不需要改 Agent 代码，只需要生成新的项目 Skill。
- 可迁移和可审计：一个项目目录就是一个完整资料包，可导出、备份、复查。
- Prompt 更稳定：项目的背景、字段口径、钻井编号、坐标系、数据质量说明都写入 Skill，减少每轮问答重复注入。
- 仍保留结构化查询：钻井表格同步写入数据库或项目 SQLite/JSON，供工具做距离、统计和预测。

推荐分层：

1. 项目 Skill 包
   存放项目说明、使用规则、字段解释、数据质量、背景摘要、钻井清单、图片索引和项目专用分析约束。

2. 项目数据文件
   存放规范化后的 `boreholes.csv/json`、`layers.csv/json`、`observations.csv/json`、`background.md`、`images.json`、`files.json`。这些文件是项目 Skill 的本地知识源。

3. 项目元数据数据库
   存放项目列表、权限、上传文件、Skill 路径、导入状态、最近更新时间，便于前端列表和权限控制。

4. 通用标准知识库
   钻井标准与地下水规范仍作为全局 KB 绑定到地下水 Agent，不写入具体项目 Skill。回答时明确区分“项目事实”和“标准依据”。

项目目录建议：

```text
data/groundwater_projects/{owner_user_id}/{project_id}/
  SKILL.md
  manifest.json
  data/
    points.csv
    points.json
    boreholes.csv
    boreholes.json
    layers.csv
    layers.json
    samples.csv
    samples.json
    measurements.csv
    measurements.json
    observations.csv
    observations.json
  docs/
    background.md
    borehole_descriptions.md
    table_schema.md
    data_quality.md
  images/
    images.json
  attachments/
    files.json
```

其中 `SKILL.md` 是 Agent 加载入口，其他文件由工具读取。`manifest.json` 记录项目名称、坐标系、文件版本、更新时间、数据摘要和可用工具。

推荐运行链路：

```text
用户选择项目
  -> 前端调用 /api/v2/agent-runtime/query
  -> agent_code=groundwater，metadata.groundwater_project_id={project_id}
  -> API/应用服务校验用户项目权限并生成 GroundwaterProjectContext
  -> AgentService 按 groundwater.yaml 选择标准 Workflow
  -> ProfiledAgentExecutor 按 Prompt Profile、SkillManifest、ToolPolicy 装配
  -> 地下水工具从请求级 ProjectContext 读取项目 Skill 和结构化数据
  -> multi_kb_search 查询通用钻井标准知识库
  -> AgentEvent/SSEEncoder 输出项目事实、标准依据、预测和不确定性
```

项目 Skill 与通用 Skill 的关系：

- `backend/skills/public/groundwater-project-analysis/SKILL.md`：领域通用 Skill，定义地下水分析角色、通用工具和回答规范。
- `data/groundwater_projects/{user_id}/{project_id}/SKILL.md`：项目实例 Skill，定义某个项目的背景、数据目录、字段口径和项目专属事实。
- 领域 Skill 是平台级 `SkillManifest`，进入全局 Skill 注册表；项目 Skill 是项目数据包入口，由请求级 `GroundwaterProjectContextResolver` 加载，不进入全局 Skill 注册表。
- Agent 每轮使用领域 Skill，并通过受控工具读取当前项目 Skill。项目 Skill 不替代标准知识库，只提供项目事实。

## 4. 六塘项目样本审查结论

已审查样本目录：`六塘项目数据信息/`。该目录可以作为后续项目上传标准的第一份基准样本。

### 4.1 文件组成与业务角色

| 样本文件 | 业务角色 | 主要内容 | 关联键 |
| --- | --- | --- | --- |
| 文件1 勘察报告.md | `region_background` | 项目概况、地质、水文地质、岩溶、规范依据、结论建议 | 项目级 |
| 文件2 钻井参数表.xlsx | `constructed_well_table` | 已建注入井、多相抽注井、抽水井及施工参数 | 井编号 |
| 文件3 地勘信息表.xlsx | `geotechnical_borehole_table` | JC01-JC24 地勘孔、坐标、高程、深度、水位、岩土分层描述 | 勘探点编号 |
| 文件4 各类井点位布设情况.xls | `planned_well_table` | 计划建设的各类井点位和坐标 | 计划井编号 |
| 文件5 调查点坐标.xlsx | `monitoring_point_table` | GW 调查点坐标 | 点位名称 |
| 文件6 上层检测数据.xlsx | `water_quality_matrix` | GW 点上层地下水检测结果 | 点位名称 + 层位 |
| 文件7 中层检测数据.xlsx | `water_quality_matrix` | GW 点中层地下水检测结果 | 点位名称 + 层位 |
| 文件8 下层检测数据.xlsx | `water_quality_matrix` | GW 点下层地下水检测结果 | 点位名称 + 层位 |
| readme.md | `project_readme` | 文件说明、字段语义、跨表关系和 Agent 使用指引 | 项目级 |

这说明项目核心实体不能只叫“钻井”。至少存在四类点：

- `constructed_well`：已完成施工的治理井，例如 Z、D、P。
- `planned_well`：计划建设但尚未施工的井。
- `geotechnical_borehole`：JC 地勘孔。
- `monitoring_point`：GW 地下水调查/采样点。

因此建议增加统一的 `groundwater_points` 点位主表，钻井参数、地勘分层、水样检测分别作为点位子数据挂接。

### 4.2 样本规模

- 已建治理井约 31 口：Z 类 24 口、D 类 3 口、P 类 4 口。
- 地勘孔 24 个：JC01-JC24，深度约 11-40m。
- 调查坐标点 15 个。
- 上层检测点 12 个。
- 中层检测点 11 个。
- 下层检测点 11 个。
- 每层检测表包含 22 项指标。

### 4.3 样本中必须被系统识别的数据特点

1. 文件2使用合并单元格表示一口注入井的长管和短管。导入时需要向下继承井编号、坐标、井深等公共字段，但把管段拆成子记录，不能错误识别成两口井。
2. 文件2末尾包含字段说明文字，不是钻井数据行。导入器必须通过井编号格式和有效坐标识别数据区，不能简单读取所有非空行。
3. 文件2中红色字体表示疑似错误。样本中 Z24、D18、P5、P6 等行存在红色标记，上传解析必须保留 `source_style_warning`。
4. 文件2包含 `无`、空白、`/`、`m-m` 等不同缺失表达，必须归一化但保留原始值。
5. 文件3是多行合并表头，真实数据从后续行开始；岩土分层情况集中在长文本列中，需要进一步解析为多条 layer。
6. 文件2/5坐标数量级约为 `3659xxxx / 271xxxx`，文件3坐标数量级约为 `271xxxx / 59xxxx`。即使说明均指向 CGCS2000，也不能在未确认带号、投影方式、X/Y轴语义前直接计算跨表距离。
7. 文件6-8是“指标为行、点位为列”的宽表，需要转成长表：`point_code + sample_layer + parameter + value`。
8. 检测值包含普通数值、`ND`、`/`、`8.86×10³` 等文本科学计数法：
   - `ND`：未检出，不能等同于 0。
   - `/`：未检测或无样品，不能等同于缺失数值。
   - 空白：缺失，需记录缺失原因未知。
   - 科学计数法：解析为数值，同时保留 `raw_value`。
9. 水质点位并非三层完全齐全：GW23 只有上层结果；GW27、GW29、GW30 有坐标但没有三层检测结果。这些应生成数据完整性告警，而不是导入失败。
10. 指标名称存在拼写差异，例如氯离子写成 `Cl-` 或 `CI-`，必须通过参数字典映射到统一编码。
11. 勘察报告内图片使用外部/内网 URL。正式上传时应把图片实体一并上传到项目存储，不能让项目 Skill 长期依赖原始临时 URL。
12. 文件4是旧版 `.xls`。当前运行环境没有 `xlrd`，不应把 `.xls` 作为结构化导入的推荐格式；后续上传标准应优先要求 `.xlsx`。

### 4.4 六塘项目生成后的 Skill 数据结构

```text
data/groundwater_projects/{user_id}/{project_id}/
  SKILL.md
  manifest.json
  data/
    points.json
    constructed_wells.json
    planned_wells.json
    well_components.json
    geotechnical_boreholes.json
    geology_layers.json
    water_samples.json
    water_quality_measurements.json
  docs/
    project_readme.md
    background.md
    hydrogeology_summary.md
    table_schema.md
    data_quality.md
  images/
    images.json
  attachments/
    files.json
```

项目 `SKILL.md` 中不应内嵌所有表格值，只写：

- 项目背景摘要。
- 坐标系和重要数据口径。
- 文件/数据集清单。
- 点位类型及数量。
- 数据质量告警。
- 工具调用规则。

大体量明细由 `groundwater_project_skill_read` 和结构化查询工具按需读取。

## 5. 数据模型规划

新增模型建议放在 `backend/db/models/groundwater.py`，并在 `backend/db/models/__init__.py` 导出。若当前项目使用手写 SQL migration，可在 `scripts/migrations/` 新增迁移脚本。

注意：数据库不再承担全部项目知识存储，数据库主要负责权限、列表、索引和高频结构化查询；项目完整上下文以 Skill 目录为准。

### 5.1 groundwater_projects

项目主表。

字段建议：

- `project_id`: String(36)，主键。
- `owner_user_id`: String(36)，关联 `users.user_id`。
- `name`: 项目名称。
- `description`: 项目说明。
- `region_name`: 区域名称。
- `coordinate_system`: 坐标系，例如 `WGS84`、`CGCS2000`、地方坐标。
- `center_lat`、`center_lon`: 项目中心点，可为空。
- `metadata`: JSON，存扩展信息，如行政区、调查阶段、业主单位。
- `skill_dir`: 项目 Skill 目录绝对路径或相对路径。
- `skill_name`: 项目 Skill 名称，如 `groundwater-project-{project_id}`。
- `manifest_path`: `manifest.json` 路径。
- `data_version`: 项目资料版本号，每次导入递增。
- `status`: `active/deleted/archived`。
- `created_at`、`updated_at`。

索引：

- `(owner_user_id, status, updated_at)`
- `project_id`

### 5.2 groundwater_project_files

项目与文件关联表，复用 `user_files.file_id`。

字段建议：

- `id`: BigInteger。
- `project_id`
- `file_id`
- `file_role`: `constructed_well_table / planned_well_table / geotechnical_borehole_table / monitoring_point_table / geology_layer_table / water_sample_table / water_quality_matrix / borehole_description / borehole_image / region_background / project_readme / report / other`
- `borehole_id`: 可选，关联某个钻井。
- `metadata`: JSON，存图片图注、图件类型、页码、解析状态。
- `created_at`

这样可以避免复制现有 MinIO/用户文件逻辑，也能让同一文件既属于个人文件库，又被纳入项目。

### 5.3 groundwater_points

统一点位主表。

字段建议：

- `point_id`: String(36)，主键。
- `project_id`: 外键。
- `point_code`: 原始点位编号，如 `Z11`、`JC01`、`GW03`。
- `point_type`: `constructed_well / planned_well / geotechnical_borehole / monitoring_point / other`。
- `coordinate_system`: 点位实际坐标系。
- `x_coord`、`y_coord`: 原始投影坐标。
- `longitude`、`latitude`: 转换后的经纬度，可为空。
- `ground_elevation`: 地面/孔口高程。
- `status`: `planned / constructed / active / abandoned / unknown`。
- `source_file_id`
- `metadata`: 原始值、坐标轴语义、带号、质量标记。

唯一约束建议为 `(project_id, point_type, point_code)`，避免不同业务类型偶然重号时错误合并。

### 5.4 groundwater_boreholes

钻井主表。

字段建议：

- `borehole_id`: String(36)，主键。
- `project_id`: 外键。
- `point_id`: 关联 `groundwater_points`。
- `code`: 钻井编号，如 `Z11`、`JC01`。
- `name`: 钻井名称。
- `longitude`、`latitude`: 经纬度。
- `x_coord`、`y_coord`: 投影坐标，可选。
- `ground_elevation`: 孔口/地面高程。
- `designed_depth`、`actual_depth`: 设计与实际孔深。
- `water_level_depth`: 静水位埋深。
- `water_level_elevation`: 水位高程。
- `aquifer_type`: 潜水/承压水/裂隙水等。
- `hydro_condition`: 水文地质条件摘要。
- `drilling_date`: 施工日期。
- `description`: 钻井描述摘要。
- `source_file_id`: 来源表格/文档。
- `metadata`: JSON，存原始字段、单位、置信度、数据质量标记。
- `created_at`、`updated_at`。

索引：

- `(project_id, code)` 唯一。
- `(project_id, longitude, latitude)`
- `(project_id, actual_depth)`

### 5.5 groundwater_well_components

井管/管段子表，用于表达六塘样本中“一口注入井包含长管和短管”的情况。

字段建议：

- `component_id`
- `borehole_id`
- `component_type`: `long_pipe / short_pipe / single_pipe / other`
- `wall_pipe_length`
- `screen_length`
- `screen_top_depth`、`screen_bottom_depth`
- `filter_top_depth`、`filter_bottom_depth`
- `seal_top_depth`、`seal_bottom_depth`
- `raw_values`

### 5.6 groundwater_borehole_layers

钻井分层/岩性/含水层表。

字段建议：

- `layer_id`: String(36)，主键。
- `borehole_id`
- `top_depth`、`bottom_depth`
- `thickness`
- `stratum_name`: 地层名称。
- `lithology`: 岩性。
- `color`、`structure`、`weathering`
- `water_bearing`: 是否含水/富水性。
- `permeability_desc`: 渗透性描述。
- `metadata`: JSON。

索引：

- `(borehole_id, top_depth)`
- `(borehole_id, bottom_depth)`

### 5.7 groundwater_samples

水样表。

字段建议：

- `sample_id`
- `project_id`
- `point_id`
- `sample_layer`: `upper / middle / lower / unknown`
- `laboratory_no`
- `sample_time`
- `sample_category`
- `metadata`

### 5.8 groundwater_measurements

水质检测长表。

字段建议：

- `measurement_id`
- `sample_id`
- `parameter_code`
- `parameter_name_raw`
- `value_numeric`
- `raw_value`
- `value_status`: `detected / not_detected / not_tested / missing / invalid`
- `unit`
- `detection_limit`
- `standard_value`: 可选，评价时填充。
- `exceedance_ratio`: 可选，由评价任务计算。
- `metadata`

### 5.9 groundwater_observations

水文/试验/水质观测表。

字段建议：

- `observation_id`

### 7.3 新平台必要的通用化改造

当前新框架已经具备 Profile、Workflow、ToolPolicy 和统一事件流，但仍有少量 `ne/csh` 时代的二元假设，地下水接入前需要做一次通用化：

1. 执行器领域标识通用化

   `ProfiledAgentExecutor._domain_key`、`_label`、`_graph_name` 和部分 `prompt_domain` 仍把未知领域回退为 `ne`。应改为基于 `AgentProfile.code/domain/ui_profile` 生成通用标识，避免地下水运行日志、图名称和运行参数伪装成 NE。

2. 请求上下文贯通

   当前 `AgentRequest.metadata` 会进入 `ProfiledAgentExecutor` 的额外参数，但尚未继续传给 `ProfiledGraphBuildConfig`、`ToolAssemblyPipeline` 和工具 Provider。需要新增通用 `ToolRuntimeContext`：

```text
ToolRuntimeContext
  request_id
  user_id
  agent_code
  domain
  thread_id
  request_metadata
  domain_context
```

推荐传递链：

```text
AgentRequest.metadata
  -> AgentService / DomainContextResolverRegistry
  -> AgentRuntimeContext.domain_context
  -> StandardAgentWorkflow
  -> ProfiledAgentExecutor
  -> ProfiledGraphBuildConfig
  -> ToolAssemblyPipeline
  -> context-aware Tool Provider
```

3. 工具 Provider 协议兼容

   扩展 `ToolProviderLoader/PolicyToolAssembler`：旧 Provider 仍可无参数创建工具；需要请求上下文的新 Provider 使用 `build_tools(runtime_context)` 或等价显式协议。不能使用模块级全局变量保存当前项目，也不能让模型传服务器路径。

4. Skill 强制加载规则配置化

   当前 `PromptBuilder` 和 `KB_SKILL_ENFORCEMENT` 对部分 Skill 存在硬编码。地下水规则应优先来自 `SkillManifest.guardrails` 或独立配置，不继续增加 `if groundwater` 分支。

5. 默认 Skill 语义统一

   明确“请求未传 `selected_skills` 时使用 Profile 默认 Skill；显式传空数组时表示关闭可选 Skill”。API 模型需要保留“未传”和“空数组”的区别，避免 `groundwater.yaml.default_skills` 被空数组覆盖。

## 8. 地下水专用工具规划

### 8.1 groundwater_project_skill_read

作用：读取当前项目 Skill 目录中的结构化文件和说明文档，是项目事实的主要入口。

输入：

- `resource`: `manifest / skill / boreholes / layers / observations / background / table_schema / data_quality / images / files`
- `borehole_code`: 可选，只读取某个钻井相关数据。
- `limit`: 可选，限制返回行数或条数。

实现：

- 从当前请求的 `GroundwaterProjectContext` 获取项目，不接受模型传入项目路径。
- 只允许读取项目目录下白名单文件，防止路径穿越。
- 大文件返回摘要，必要时提示使用 `groundwater_borehole_query` 做过滤查询。

输出：

- 文件摘要或结构化 JSON。
- 数据版本、更新时间。
- 来源路径，但不暴露服务器敏感绝对路径给前端用户。

### 8.2 groundwater_project_search

作用：检索项目背景文档、钻井描述、图片图注。

输入：

- `query`
- `file_roles`
- `top_k`

实现路线：

- 第一阶段：基于项目 Skill 目录下 `docs/*.md`、`images/images.json`、`attachments/files.json` 做轻量 BM25/TF-IDF 检索，可复用 `backend/services/chat_file_index.py` 的 `ChatFileIndex` 思路，扩展为 `ProjectFileIndex`。
- 第二阶段：将项目文档作为项目私有 KB 入库，复用 RAG 检索。

输出：

- 命中文档片段。
- 图片 URL/图注。
- 关联钻井编号。
- 来源文件名。

### 8.3 groundwater_borehole_query

作用：查询结构化钻井数据。

输入：

- `filters`: 钻井编号、深度范围、地层、含水层类型、距离范围等。
- `sql_like` 或受控查询条件。

能力：

- 列出项目钻井。
- 查询某钻井详情。
- 查询邻近钻井。
- 统计深度、水位、地层厚度。
- 对比多个钻井。

实现优先级：

1. 优先从数据库表 `groundwater_boreholes`、`groundwater_borehole_layers` 查询，性能更稳。
2. 如果数据库未同步或处于导入预览状态，可回退读取项目 Skill 目录中的 `data/*.json`。

第一期不建议让 Agent 直接执行任意 SQL，应封装受控参数，避免越权和注入风险。

### 8.4 groundwater_prediction

作用：基于目标位置和已有钻井进行新井预测分析。

输入：

- `target_location`: 地址、经纬度或项目坐标。
- `radius_m`: 邻近井半径，默认 1000m 或按项目尺度配置。
- `target_depth`: 用户给出的目标深度，可选。
- `analysis_focus`: `water_level / stratigraphy / aquifer / drilling_risk / full`

第一期算法建议采用可解释规则，不直接宣称高精度模型：

- 最近邻井筛选：按距离排序，取最近 N 个。
- 相似井筛选：综合地貌/地层/含水层/高程/区域背景标签。
- 水位预测：邻近井水位埋深/水位高程加权平均，权重可用 `1 / (distance + eps)`。
- 深度和地层预测：邻近井相同地层顶底板深度范围统计，输出范围而非单点。
- 风险识别：深厚覆盖层、软弱层、强透水层、承压水、资料稀疏、坐标系不一致等。

输出格式：

- `prediction`: 预测水位、建议深度、可能地层序列。
- `evidence_boreholes`: 使用的钻井编号、距离、关键字段。
- `project_skill_refs`: 读取的项目 Skill 文件，例如 `data/boreholes.json`、`docs/background.md`。
- `confidence`: `高/中/低` 与理由。
- `uncertainties`: 不确定性。
- `next_data_needed`: 建议补充资料。

后续可接入更专业模型：

- IDW / Kriging 插值。
- 剖面线地层插值。
- GIS 栅格/矢量图层。
- 地下水数值模拟结果读取。

### 8.5 groundwater_quality_check

作用：根据通用标准知识库和项目字段，检查钻井资料完整性。

输入：

- `standard_kb_ids`
- `check_scope`: `field_completeness / coordinates / layers / hydro_tests / images`

输出：

- 缺失字段清单。
- 异常字段清单。
- 标准依据片段。
- 修正建议。

### 8.6 groundwater_project_skill_update

作用：在项目资料变更后更新项目 Skill 目录。这个工具主要供后端接口调用，不建议开放给普通问答 Agent 随意调用。

输入：

- `update_type`: `rebuild / append_background / refresh_summary / validate`
- `payload`: 需要更新的内容。

能力：

- 重新生成 `SKILL.md`。
- 刷新 `manifest.json`。
- 更新 `docs/background.md`、`docs/table_schema.md`、`docs/data_quality.md`。
- 校验项目目录完整性。

安全约束：

- 只允许写入项目目录白名单文件。
- 所有写操作必须通过用户权限校验。
- 普通问答默认不注入该工具，避免模型误改项目资料。

## 13. 后续项目上传标准

后续上传支持两种方式：

1. 推荐：上传一个标准 ZIP 项目包。
2. 兼容：在项目页面分批上传文件，并为每批选择 `file_role`。

### 13.1 推荐项目包结构

```text
project-package.zip
  project.yaml
  README.md
  tables/
    points.xlsx
    constructed_wells.xlsx
    planned_wells.xlsx
    geology_layers.xlsx
    water_samples.xlsx
    water_quality.xlsx
  documents/
    investigation_report.pdf
    hydrogeology_background.md
  images/
    image_manifest.xlsx
    ...
```

不要求每个项目包含全部文件，但必须有 `project.yaml`，并至少包含一种项目数据或背景文档。

### 13.2 project.yaml 标准

```yaml
schema_version: "1.0"
project:
  name: "柳城县工业区-六塘片区地下水污染风险管控与修复项目"
  code: "liutang-groundwater"
  region: "广西柳城县六塘工业园区"
  description: "地下水污染风险管控和修复"

coordinate_reference:
  horizontal_crs: "CGCS2000"
  epsg: null
  zone: null
  x_axis_meaning: "northing"
  y_axis_meaning: "easting"
  vertical_datum: "1985国家高程基准"
  confirmed: false

files:
  - path: "tables/constructed_wells.xlsx"
    role: "constructed_well_table"
  - path: "tables/geology_layers.xlsx"
    role: "geology_layer_table"
  - path: "tables/water_quality.xlsx"
    role: "water_quality_long_table"
  - path: "documents/investigation_report.pdf"
    role: "region_background"
```

坐标信息必须尽量填写完整。仅填写“CGCS2000”而不填写投影带号、EPSG 或坐标轴语义时，系统允许上传，但空间距离分析状态标记为 `coordinate_unconfirmed`。

### 13.3 文件格式要求

- 结构化表格推荐 `.xlsx` 或 UTF-8 `.csv`。
- 不推荐 `.xls`；若上传 `.xls`，只作为附件保存，或由独立转换服务转为 `.xlsx` 后再导入。
- 文档支持 `.pdf`、`.docx`、`.md`。
- 图片支持 `.jpg`、`.jpeg`、`.png`、`.webp`。
- 单表第一行应为字段名，不推荐复杂合并表头。
- 不使用颜色作为唯一数据语义。异常标记应增加显式字段 `quality_flag` 和 `quality_note`。
- 单元格内不带单位，单位写在字段名或独立 `unit` 列中。
- 日期统一使用 `YYYY-MM-DD`。
- 编号字段按文本保存，避免 Excel 自动去掉前导零。

### 13.4 points 点位主表

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| point_code | 是 | 项目内点位编号 |
| point_type | 是 | `constructed_well/planned_well/geotechnical_borehole/monitoring_point` |
| x_coord | 条件必填 | 投影坐标 X |
| y_coord | 条件必填 | 投影坐标 Y |
| longitude | 条件必填 | 经度 |
| latitude | 条件必填 | 纬度 |
| coordinate_system | 是 | 坐标系 |
| ground_elevation_m | 否 | 地面/孔口高程 |
| status | 否 | `planned/constructed/active/abandoned/unknown` |
| description | 否 | 点位说明 |
| quality_flag | 否 | `normal/suspected_error/missing/unconfirmed` |

投影坐标和经纬度至少提供一种。不同坐标配置的数据应拆成不同文件，或逐行提供明确 `coordinate_system`。

### 13.5 constructed_wells 已建井表

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| point_code | 是 | 对应 points.point_code |
| well_type | 是 | `injection/multiphase/pumping/monitoring/circulation/other` |
| actual_depth_m | 是 | 实际井深 |
| borehole_diameter_mm | 否 | 孔径 |
| rock_entry_depth_m | 否 | 见岩深度 |
| initial_water_depth_m | 否 | 初见水位埋深 |
| stable_water_depth_m | 否 | 稳定水位埋深 |
| remark | 否 | 备注 |
| quality_flag | 否 | 数据质量标记 |
| quality_note | 否 | 异常说明 |

一口井有长管、短管或多段筛管时，不增加第二口井记录，应另传 `well_components` 表。

| 字段 | 必填 | 说明 |

| component_code | 是 | 井内组件编号 |
| component_type | 是 | `long_pipe/short_pipe/single_pipe/other` |
| wall_pipe_length_m | 否 | 井壁管总长 |
| screen_length_m | 否 | 滤水管总长 |
| screen_top_m | 否 | 开筛顶部深度 |
| screen_bottom_m | 否 | 开筛底部深度 |
| filter_top_m | 否 | 滤料层顶部 |
| filter_bottom_m | 否 | 滤料层底部 |
| seal_top_m | 否 | 止水层顶部 |
| seal_bottom_m | 否 | 止水层底部 |

### 13.7 geology_layers 地层表

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| point_code | 是 | 地勘孔/钻井编号 |
| layer_no | 是 | 分层序号 |
| top_depth_m | 是 | 层顶深度 |
| bottom_depth_m | 是 | 层底深度 |
| stratum_name | 否 | 地层名称 |
| lithology | 否 | 岩性 |
| color | 否 | 颜色 |

### 13.9 water_quality 水质检测长表

推荐上传长表，不再使用六塘样本中“指标为行、点位为列”的宽表。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| sample_id | 是 | 对应 water_samples.sample_id |
| parameter_code | 是 | 统一指标编码 |
| parameter_name | 是 | 指标名称 |
| raw_value | 是 | 原始检测结果 |
| value_numeric | 条件必填 | 可解析的数值 |
| value_status | 是 | `detected/not_detected/not_tested/missing/invalid` |
| unit | 是 | `mg/L`、`ug/L` 等 |
| detection_limit | 否 | 检出限 |
| method | 否 | 检测方法 |

值转换规则：

- `ND` -> `value_status=not_detected`，`value_numeric=null`。
- `/` -> `value_status=not_tested`，`value_numeric=null`。
- 空白 -> `value_status=missing`。
- `8.86×10³` -> `value_numeric=8860`，同时保留原始值。
- 不得把 `ND` 自动替换为 0；如统计模型需要替代值，应由分析步骤显式选择规则。

### 13.10 图片清单

`image_manifest.xlsx` 建议字段：

- `image_file`
- `image_role`: `site/photo/core/profile/map/column_chart/other`
- `point_code`
- `title`
- `caption`
- `taken_at`
- `source_document`

没有清单的图片允许上传，但只能作为项目级未分类附件，不能自动绑定到某口井或点位。

### 13.11 兼容六塘现有文件的导入策略

六塘现有文件无需人工全部重做，可增加 `liutang_legacy` 导入配置：

- 文件2：识别合并行并拆成 `constructed_wells + well_components`。
- 文件3：识别多层表头，将长文本岩土描述解析为 `geology_layers`，保留原始描述。
- 文件4：先转换为 `.xlsx`，再导入 `planned_wells`。
- 文件5：导入 `points`。
- 文件6-8：分别赋予 `upper/middle/lower`，将宽表转成长表。
- 红色字体写入 `quality_flag=suspected_error`。
- `ND`、`/`、空白和科学计数法按前述规则转换。

### 13.12 上传校验分级

- `error`：项目无法提交，例如没有项目名称、点位编号重复且无法区分、检测结果无法关联 sample。
- `warning`：允许提交但限制分析，例如坐标系未确认、某层检测缺失、红色疑似错误、部分点位无坐标。
- `info`：一般提示，例如存在未分类附件、报告图片 URL 尚未本地化。

上传接口返回：

- 解析成功文件数。
- 各数据集记录数。
- 字段映射结果。
- 跨表关联率。
- `error/warning/info` 清单。
- 是否允许提交。
- Skill 是否成功重建及最新 `data_version`。

## 14. 安全与权限

- 所有项目、钻井、项目文件接口必须校验 `owner_user_id == current_user.user_id`，管理员另行扩展。
- 工具执行时必须从受控 `ToolRuntimeContext` 取得 `project_id` 和 `user_id` 并再次校验，不能信任模型参数中的项目标识。
- 不允许 Agent 执行任意 SQL 查询项目表；结构化查询必须通过受控工具参数。
- 项目图片 URL 使用签名或权限校验，参考 `chat_files.py` 中图片签名思路。
- 项目 Skill 目录必须只允许写入 `GROUNDWATER_PROJECT_ROOT` 下的当前用户项目目录。
- `groundwater_project_skill_read` 只能读取白名单文件，禁止任意路径读取。
- 项目实例 Skill 只在请求级动态加载，不进入全局公共 skill 列表。
- `groundwater_project_skill_update` 默认不注入问答 Agent，只由上传/导入/重建接口调用。
- 删除项目采用软删除，保留审计和误删恢复空间。

## 15. 风险与边界

- 地址定位如果没有地图/地理编码服务，无法仅凭地址可靠转坐标。第一期应要求用户提供经纬度或项目坐标。
- 坐标系不一致会显著影响距离分析，必须在项目层记录坐标系并在回答中提示。
- 钻井样本稀疏时，只能输出低置信度范围预测，不能输出确定结论。
- 项目文档和结构化表字段可能冲突，回答中应说明以哪个来源为准，必要时列出冲突。
- 钻井图片如果没有绑定钻井或图注，模型只能作为辅助证据，不能自动推断空间位置。

## 16. MVP 范围建议

MVP 做到：

- 创建地下水项目，并自动生成项目 Skill 目录、`SKILL.md`、`manifest.json`。
- 上传钻井 Excel，导入钻井主表和分层表，同时写入项目 Skill 目录 `data/*.json`。
- 上传项目背景文档和图片，并按角色关联项目。
- 上传后自动刷新 `docs/background.md`、`docs/table_schema.md`、`docs/data_quality.md` 和项目 `SKILL.md`。
- 注册 `groundwater` Agent Profile，使用统一 Agent Runtime，并通过请求元数据解析当前项目 Skill 上下文。
- 工具支持：
  - 读取项目 Skill 目录。
  - 查询钻井列表/详情。
  - 查询邻近井。
  - 基于邻近井做水位/地层范围预测。
  - 检索通用钻井标准知识库。
- 前端提供项目选择、Skill 状态、资料上传、钻井表查看、聊天问答。

暂缓到第二期：

- 地图可视化。
- 自动地址地理编码。
- Kriging/专业空间插值。
- 项目私有 KB 全量入库。MVP 先使用项目 Skill 目录 + 轻量检索。
- 多用户协作和项目共享。

## 17. 验收用例

1. 用户创建项目“某区地下水调查”，系统生成 `data/groundwater_projects/{user_id}/{project_id}/SKILL.md` 和 `manifest.json`。
2. 用户上传 `boreholes.xlsx`，系统导入 10 个钻井和分层数据，并同步生成 `data/boreholes.json`、`data/layers.json`、`docs/table_schema.md`。
3. 用户上传区域背景 PDF 和 5 张岩芯照片，分别标记为区域背景和钻井图片，系统刷新 `docs/background.md`、`images/images.json` 和项目 `SKILL.md`。
4. 用户问“ZK03 的水文条件和周边钻井相比有什么异常？”，系统先加载项目 Skill，再返回 ZK03 与邻近井对比、异常依据、引用项目文件。
5. 用户输入新井坐标，问“这里建议打多深？可能遇到哪些含水层？”，系统返回邻近井列表、预测深度范围、水位范围、地层序列、不确定性。
6. 用户问“按钻井标准这个项目资料还缺什么？”，系统检索通用标准 KB，结合项目 Skill 目录中的字段说明输出缺失项。
7. 用户切换到另一个项目后，加载另一个项目 Skill，不能查询到前一个项目的钻井数据。
8. `GET /api/v2/agent-runtime/profiles` 能发现 `groundwater`，Profile、Prompt、SkillManifest 和 ToolPolicy 校验通过。
9. `POST /api/v2/agent-runtime/query` 未携带有效项目 ID 时返回明确的项目上下文错误，不启动地下水数据工具。
10. 地下水请求仍输出标准 `AgentEvent`，前端无需维护另一套 SSE 解析逻辑。
11. NE、CSH 回归测试通过，执行器领域通用化和上下文注入没有改变原有工具集合及回答事件契约。

## 18. 推荐优先级

P0：

- 数据模型、项目 CRUD、项目 Skill 目录生成、钻井导入、项目权限。
- `groundwater` Profile、Prompt、领域 Skill、ToolPolicy 与基础工具。
- 统一 `/api/v2/agent-runtime/query` 的项目上下文接入。
- 新井位邻近井预测 MVP。

P1：

- 项目文档/图片检索。
- 项目 Skill 重建与校验界面。
- 标准知识库绑定和质量检查。
- 前端项目工作台。

P2：

- 地图、空间插值、剖面分析、报告生成。
