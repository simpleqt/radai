## 一、背景

当前系统支持用户上传文件参与对话，也支持系统生成文件并提供下载，但存在以下问题：

1. 上传文件是一次性动作，用户无法方便地复用之前上传过或系统生成过的文件。
2. 已上传文件、已生成文件缺少统一归档位置，用户难以管理。
3. 文件在对话中使用后，与“个人资产”之间没有建立稳定关联，不利于二次引用。
4. 用户希望在上传入口直接从个人文件夹中挑选已有文件，而不是重复上传。

因此，需要建设一套“个人文件夹”能力，将用户上传的文件与系统生成的文件统一沉淀为用户私有文件资产，并在上传入口支持“从我的文件添加”。

---

## 二、目标与非目标

### 2.1 目标

本期方案实现以下能力：

1. 所有用户主动上传的文件，默认进入当前用户的个人文件夹。
2. 所有系统生成且允许保存的文件，可自动或手动进入当前用户的个人文件夹。
3. 用户可在“文件管理”中查看、搜索、重命名、删除、下载自己的文件。
4. 用户在聊天输入框的“添加文件”入口中，可选择：
   - 上传文件
   - 从我的文件添加
5. 选择“从我的文件添加”后，用户可从个人文件夹中选取历史文件并附加到当前会话。
6. 文件权限默认为用户私有，仅本人可见、可管理、可在对话中复用。

### 2.2 非目标

本期不包含以下能力：

1. 多用户之间的文件共享。
2. 团队空间、部门空间、公共素材库。
3. 文件在线编辑与版本对比。
4. 复杂目录树管理，V1 先采用单层个人文件列表，可预留“文件夹”字段。
5. 超大文件分片秒传、跨租户去重等高级存储优化。

---

## 三、核心用户场景

### 3.1 场景 A：上传新文件

1. 用户点击输入框左侧“添加文件”。
2. 选择“上传文件”。
3. 文件上传成功后：
   - 文件附加到当前会话；
   - 同时落入个人文件夹；
   - 在个人文件夹中记录来源为“用户上传”。

### 3.2 场景 B：复用历史文件

1. 用户点击“添加文件”。
2. 选择“从我的文件添加”。
3. 系统弹出个人文件选择器。
4. 用户可搜索、筛选、勾选一个或多个文件。
5. 确认后，这些文件附加到当前会话，无需再次上传。

### 3.3 场景 C：保存系统生成文件

1. 系统生成报告、表格、代码包、导出文档等文件。
2. 系统在生成结果区域展示“保存到我的文件”或默认自动保存。
3. 文件进入个人文件夹，来源标记为“系统生成”。
4. 用户后续可在文件管理中查找，也可在上传入口直接复用。

### 3.4 场景 D：个人文件管理

1. 用户在左侧导航进入“文件管理”。
2. 查看自己所有文件。
3. 可执行搜索、重命名、删除、下载、按来源筛选。
4. 删除文件后：
   - 从个人文件夹中移除；
   - 不影响历史对话消息的文本记录；
   - 若历史会话再次引用该文件，应提示文件已失效。

## 四、产品方案

### 4.1 入口设计

聊天输入区“添加文件”按钮展开后，提供两个一级入口：

1. `上传文件`
2. `从我的文件添加`

其中“从我的文件添加”为本次新增入口，对应用户截图中的交互。

### 4.2 文件管理页面

左侧导航增加或强化 `文件管理` 页面，展示当前用户的私有文件资产列表。

建议页面包含：

1. 顶部搜索框：按文件名模糊搜索。
2. 来源筛选：全部 / 用户上传 / 系统生成。
3. 类型筛选：文档 / 图片 / 表格 / 代码 / 其他。
4. 列表字段：
   - 文件名
   - 文件类型
   - 文件大小
   - 来源
   - 创建时间
   - 最近使用时间
5. 行操作：
   - 添加到当前会话
   - 下载
   - 重命名
   - 删除

### 4.3 个人文件选择器

点击“从我的文件添加”后，打开弹层或抽屉，建议能力如下：

1. 显示最近使用文件。
2. 支持搜索文件名。
3. 支持按类型、来源筛选。
4. 支持单选或多选。
5. 支持分页或滚动加载。
6. 选中文件后，回填到当前对话附件区。

## 五、系统设计

### 5.1 总体架构

```text
用户上传文件
    │
    ▼
文件上传服务
    │
    ├── 写入对象存储（OSS / MinIO / S3）
    ├── 写入文件元数据表 user_files
    └── 建立会话附件关联 session_files

系统生成文件
    │
    ▼
文件生成服务
    │
    ├── 输出文件到对象存储
    ├── 写入 user_files（source = generated）
    └── 可选建立 message_files / session_files 关联

用户进入“从我的文件添加”
    │
    ▼
个人文件查询接口
    │
    ▼
文件选择器
    │
    ▼
会话附件绑定接口

```

### 5.2 分层说明

1. 存储层
   - 文件二进制存储在对象存储。
   - 文件元数据存储在数据库。
2. 业务层
   - 负责上传、保存生成文件、查询个人文件、绑定会话附件。
3. 表现层
   - 包含文件管理页面、聊天上传菜单、个人文件选择器。

### 5.3 关键原则

1. 文件实体与会话附件解耦。
2. 同一个用户文件可被多个会话重复引用。
3. 上传一次，后续多次复用，不重复存储业务含义。
4. 权限校验前置到所有文件读取、下载、绑定接口。

## 六、数据模型设计

### 6.1 用户文件表 `user_files`

建议新增或扩展统一文件表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint / uuid | 文件主键 |
| user_id | bigint / uuid | 文件归属用户 |
| file_name | varchar | 展示文件名 |
| file_ext | varchar | 扩展名 |
| mime_type | varchar | MIME 类型 |
| file_size | bigint | 文件大小 |
| storage_key | varchar | 对象存储路径 |
| source | varchar | `upload` / `generated` |
| status | varchar | `active` / `deleted` / `expired` |
| hash | varchar | 可选，便于去重 |
| biz_type | varchar | 业务类型，如 report/image/export |
| created_at | datetime | 创建时间 |
| updated_at | datetime | 更新时间 |
| last_used_at | datetime | 最近一次加入会话时间 |
| generator_task_id | varchar | 生成任务 ID，可空 |
| extra_meta | json | 扩展信息 |

### 6.2 会话文件关联表 `session_files`

用于描述某个会话当前引用了哪些用户文件。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint / uuid | 主键 |
| session_id | bigint / uuid | 会话 ID |
| user_id | bigint / uuid | 用户 ID |
| file_id | bigint / uuid | 对应 `user_files.id` |
| attached_from | varchar | `upload` / `my_files` / `generated_auto` |
| created_at | datetime | 绑定时间 |

### 6.3 可选消息级关联表 `message_files`

若系统需要精确追踪“哪条消息引用了哪个文件”，可增加消息级关联：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint / uuid | 主键 |
| message_id | bigint / uuid | 消息 ID |
| file_id | bigint / uuid | 文件 ID |
| created_at | datetime | 创建时间 |

## 七、核心流程设计

### 7.1 上传文件并自动入个人文件夹

```text
前端选择本地文件
    ▼
调用上传接口
    ▼
服务端校验文件类型/大小
    ▼
写入对象存储
    ▼
创建 user_files 记录
    ▼
若当前在会话中，创建 session_files 记录
    ▼
返回 file_id、文件名、下载地址、会话附件信息

```

### 7.2 从我的文件添加到当前会话

```text
前端打开个人文件选择器
    ▼
调用个人文件列表接口
    ▼
用户勾选文件
    ▼
调用会话附件绑定接口
    ▼
写入 session_files
    ▼
更新 user_files.last_used_at
    ▼
前端展示已附加文件

```

### 7.3 系统生成文件保存到个人文件夹

```text
系统生成文件
    ▼
输出到对象存储
    ▼
创建 user_files（source=generated）
    ▼
若生成发生在某对话上下文，可选择自动绑定 session_files
    ▼
前端提示“已保存到我的文件”

```

### 7.4 删除文件

删除采用“软删除”优先：

1. 更新 `user_files.status = deleted`。
2. 默认不立即物理删除对象存储文件。
3. 定时清理超过保留期的数据。
4. 历史会话再次访问时返回“文件已删除或不可用”。

## 八、接口设计

以下为建议接口，实际可按现有后端风格调整。

### 8.1 上传文件

`POST /api/v1/files/upload`

请求：

- `file`: 二进制文件
- `session_id`: 可选，存在时自动绑定到当前会话

响应：

```json
{
  "file_id": "f_123",
  "file_name": "需求说明.docx",
  "source": "upload",
  "size": 102400,
  "session_attached": true
}
```

### 8.2 查询我的文件列表

`GET /api/v1/my-files`

查询参数：

- `keyword`
- `source`
- `file_type`
- `page_no`
- `page_size`

响应：

```json
{
  "list": [
    {
      "file_id": "f_123",
      "file_name": "需求说明.docx",
      "source": "upload",
      "size": 102400,
      "created_at": "2026-05-21 10:00:00",
      "last_used_at": "2026-05-21 10:30:00"
    }
  ],
  "total": 1
}
```

### 8.3 从我的文件添加到会话

`POST /api/v1/sessions/{session_id}/files/attach`

请求：

```json
{
  "file_ids": ["f_123", "f_456"],
  "attached_from": "my_files"
}
```

### 8.4 重命名文件

`PUT /api/v1/my-files/{file_id}`

请求：

```json
{
  "file_name": "新的文件名.docx"
}
```

### 8.5 删除文件

`DELETE /api/v1/my-files/{file_id}`

### 8.6 下载文件

`GET /api/v1/my-files/{file_id}/download`

### 8.7 保存生成文件

`POST /api/v1/generated-files/save`

请求：

```json
{
  "task_id": "task_001",
  "file_name": "分析报告.md",
  "storage_key": "generated/2026/05/21/report_001.md",
  "session_id": "s_001",
  "auto_attach": true
}
```

## 九、权限与安全设计

### 9.1 权限原则

1. 文件按 `user_id` 隔离。
2. 任何文件查询、下载、绑定、删除操作都必须校验文件归属人。
3. 非文件所有者不可访问该文件元数据和下载地址。

### 9.2 安全控制

1. 上传时校验文件大小、扩展名、MIME 类型。
2. 对高风险类型文件设置黑名单或隔离策略。
3. 下载地址使用短时效签名 URL，避免对象存储裸露。
4. 文件删除采用软删除，降低误删风险。
5. 记录操作日志，便于审计与问题排查。

## 十一、后端实现建议

### 11.1 服务拆分

建议抽象统一文件服务：

1. `FileStorageService`
   - 负责对象存储上传、下载、删除
2. `UserFileService`
   - 负责用户文件元数据管理
3. `SessionFileService`
   - 负责会话与文件绑定
4. `GeneratedFileService`
   - 负责系统生成文件入库

### 11.2 关键方法建议

```text
save_uploaded_file(user_id, file, session_id=None)
list_user_files(user_id, query)
attach_files_to_session(user_id, session_id, file_ids)
save_generated_file(user_id, task_info, auto_attach=False)
rename_user_file(user_id, file_id, file_name)
delete_user_file(user_id, file_id)

```

### 11.3 兼容现有上传能力

若当前系统已存在对话文件上传逻辑，建议按以下方式改造：

1. 保留原上传接口对前端的兼容。
2. 将“上传后只挂到会话”调整为“上传后先生成用户文件，再绑定会话”。
3. 会话附件层不再直接依赖临时文件，而是依赖用户文件主记录。

## 十三、风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| 存储成本增长 | 上传文件与生成文件长期保留 | 增加生命周期策略和配额控制 |
| 历史逻辑兼容性 | 旧会话可能依赖临时文件模型 | 做兼容层映射，渐进迁移 |
| 权限泄露风险 | 下载或查询接口若校验不严，可能越权 | 所有接口强制按 `user_id` 校验 |
| 删除后引用异常 | 会话中仍可能显示已删除文件 | 前端展示失效状态，后端返回明确错误码 |
| 生成文件来源不统一 | 不同生成链路保存方式不一致 | 统一接入 `GeneratedFileService` |

## 十四、验收标准

### 14.1 功能验收

1. 用户上传文件后，可在“文件管理”中看到该文件。
2. 系统生成文件后，可在“文件管理”中看到该文件。
3. 用户可从“从我的文件添加”中选取历史文件并加入当前会话。
4. 用户删除文件后，该文件不再出现在个人文件列表中。
5. 用户无法访问其他用户的文件。

### 14.2 体验验收

1. 从“添加文件”到“从我的文件添加”的路径不超过 2 次点击。
2. 个人文件选择器支持搜索，首屏加载时间可接受。
3. 上传成功与保存成功提示清晰明确。

## 十六、结论

本方案的核心是将“上传文件”“系统生成文件”“会话附件”三者统一到“用户文件资产”模型下管理。

通过引入个人文件夹与“从我的文件添加”入口，可以实现：

1. 文件统一沉淀，降低重复上传成本。
2. 文件可管理、可复用、可追踪。
3. 对话场景与文件管理场景打通，提升整体产品闭环。

建议按“后端模型与接口先行、前端入口与管理页随后接入”的方式分阶段落地。
