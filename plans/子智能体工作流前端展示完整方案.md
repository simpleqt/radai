# 子智能体工作流前端展示完整方案

> **文档状态**：✅ 已实现（2026-04）  
> **实现组件**：`SubagentWorkflowSwitcher.vue`、`SubagentWorkflowTimeline.vue`（集成于 `WorkflowTimeline.vue`）  
> 现行前端说明见 [docs/docs_frontend/ne_full_module.md](../docs/docs_frontend/ne_full_module.md)

## 1. 背景与问题

当前深度研究模式下，主智能体会并行委派多个子智能体执行任务。已有前端可以展示过程事件，但存在以下问题：

1. 多个子智能体事件混在同一条时间线中，用户难以区分每个子智能体的独立工作过程。
2. 现有展示逻辑隐含了固定数量思维（例如双路并行），不适配未来 N 个子智能体场景。
3. 当并发数量增加时，信息密度过高，阅读成本明显上升。

## 2. 目标

实现“可扩展到任意数量子智能体”的工作流展示能力，满足：

1. 默认只展示一个子智能体工作流。
2. 用户可以点击切换到任意子智能体查看其完整流程。
3. 支持 N 个子智能体，不依赖固定数量布局。
4. 保持与现有事件流兼容，支持渐进改造。

## 3. 非目标

本期不做以下事项：

1. 不改动子智能体调度策略与并发上限策略。
2. 不重构 SSE 协议整体结构，仅补充和规范必要元数据。
3. 不在本期实现复杂图可视化（例如 DAG 画布），采用可维护的列表时间线。

## 4. 设计原则

1. 可扩展：前端按 task_id 动态分组，支持任意数量子智能体。
2. 可识别：每个事件必须可归属到一个稳定分组。
3. 可回放：历史会话重载后，分组结果一致。
4. 低侵入：复用现有事件通道和消息模型，减少回归风险。
5. 渐进发布：先做前端分组可视化，再补齐后端元数据增强。

## 5. 总体方案

### 5.1 展示形态

采用“子智能体选择器 + 单智能体时间线”模式：

1. 顶部显示子智能体标签列表（可横向滚动）。
2. 默认选中一个子智能体。
3. 主面板仅显示当前选中子智能体的完整事件流。
4. 可选提供“全部”标签作为总览（默认不选中）。

### 5.2 分组主键

以 metadata.task_id 作为子智能体分组主键。

1. 有 task_id：归入对应子智能体分组。
2. 无 task_id：归入 orchestrator 主控分组。
3. 无法识别：归入 unknown 分组并记录告警日志。

## 6. 数据模型与协议约定

在现有 AgentProcessEvent 基础上，规范 metadata 字段：

1. task_id: 子任务唯一标识（必填，子任务相关事件）。
2. subagent_type: 子智能体类型（建议填）。
3. description: 子任务简述（建议填）。
4. trace_id: 链路追踪标识（建议填）。
5. message_index 和 total_messages: 子任务进度（已有可复用）。

### 6.1 事件归属规则

1. task_start/task_progress/task_end 必须带 task_id。
2. tool_start/tool_end/tool_result 若属于子智能体执行过程，建议透传 task_id。
3. 主控事件（规划、汇总、归档）允许无 task_id，归入 orchestrator。

## 7. 前端改造方案

### 7.1 组件结构

新增组件：

1. SubagentWorkflowSwitcher：子智能体选择器。
2. SubagentWorkflowTimeline：单子智能体时间线。

保留现有组件：

1. WorkflowTimeline：可作为兼容模式或基础映射逻辑来源。

### 7.2 计算逻辑

在消息级别新增计算：

1. groupsByTaskId: Map<string, AgentProcessEvent[]>。
2. groupMeta: 每个分组的状态、事件数、最后更新时间、标题。
3. selectedTaskId: 当前选中分组。

### 7.3 默认选中策略

按以下优先级自动选择默认分组：

1. 运行中分组优先。
2. 最近更新时间最新的分组。
3. 事件数量最多分组。
4. 最先创建分组。

### 7.4 交互细节

1. 点击切换分组时仅替换时间线数据，不重建整个消息卡片。
2. 流式过程中若当前选中分组收到新事件，自动滚动到底部。
3. 流式过程中若非当前分组更新，仅更新对应标签状态与计数。

### 7.5 移动端适配

1. 子智能体标签栏支持横向滚动。
2. 时间线保持纵向列表，卡片简化次要字段。
3. 默认折叠冗长摘要，点击展开。

## 8. 后端改造方案

### 8.1 事件生成处增强

在事件生成与转发链路统一补齐 metadata：

1. task_started: task_id, description。
2. task_running: task_id, message_index, total_messages。
3. task_tool_start/task_tool_end: task_id, tool, detail。
4. task_completed/task_failed/task_timed_out: task_id, result or error。

### 8.2 兼容策略

1. 若旧分支未提供 task_id，前端降级归入 orchestrator/unknown。
2. 新分支补齐后，前端无需改协议即可自动增强分组效果。

## 9. 日志与可观测性

增加两类关键日志：

1. 事件缺少 task_id 告警：便于定位协议不一致。
2. 前端 unknown 分组计数埋点：便于监控数据质量。

建议埋点指标：

1. subagent_group_count_per_message
2. unknown_group_event_ratio
3. group_switch_click_count
4. time_to_first_task_event

## 10. 分阶段实施计划

### Phase 1（前端可用版）

目标：先实现可切换视图，基于现有 task_id 分组。

1. 实现分组计算与默认选中策略。
2. 新增选择器与单智能体时间线展示。
3. 兼容无 task_id 事件降级展示。

交付物：

1. 可在一条消息中切换查看不同子智能体流程。

### Phase 2（后端契约增强）

目标：提高分组准确率与可解释性。

1. 统一补齐 metadata 关键字段。
2. 对缺失 task_id 的路径补日志和监控。

交付物：

1. 事件归属稳定，unknown 分组显著下降。

### Phase 3（体验优化）

目标：提升可读性与运维效率。

1. 增加全部总览标签。
2. 增加失败高亮与快速定位。
3. 增加性能优化（虚拟滚动可选）。

## 11. 测试方案

### 11.1 功能测试

1. 单子智能体：只出现一个标签并默认选中。
2. 多子智能体：出现 N 个标签，切换后时间线正确。
3. 流式更新：标签状态与计数实时变化。
4. 失败场景：仅对应分组显示失败，不污染其他分组。

### 11.2 回放测试

1. 历史会话加载后分组数量与实时一致。
2. 默认选中策略在重载后行为一致。

### 11.3 兼容测试

1. 无 task_id 旧事件可展示且不报错。
2. 混合事件（部分有 task_id）仍可正常分组。

## 12. 验收标准

1. 支持任意数量子智能体分组展示。
2. 默认仅展示一个子智能体流程。
3. 用户可点击切换任意子智能体。
4. 流式与历史回放结果一致。
5. 无明显性能退化或前端卡顿。

## 13. 风险与应对

1. 风险：后端部分事件缺少 task_id。
   - 应对：前端降级分组 + 后端告警补齐。
2. 风险：高并发事件导致前端渲染压力增大。
   - 应对：分组后只渲染当前选中组，必要时引入虚拟滚动。
3. 风险：不同消息复用状态造成串组。
   - 应对：selectedTaskId 按消息 id 作用域隔离。

## 14. 回滚方案

1. 保留旧版 WorkflowTimeline 渲染路径。
2. 通过前端配置开关切换新旧展示。
3. 出现重大问题时，一键回退到旧版单流时间线。

## 15. 实施清单

1. 前端实现分组与切换组件。
2. 前端接入消息级状态管理与默认选中策略。
3. 后端补齐 task_id 及扩展 metadata。
4. 新增日志与埋点。
5. 完成功能、回放、兼容测试。
6. 小流量灰度后全量发布。
